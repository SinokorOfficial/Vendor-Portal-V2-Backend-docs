    2026-09 변경 이력¶

    Redis 연결이 조용히 끊겨도 15분이 아니라 30~40초 안에 알아채고 재연결한다 (PR #181)¶

    2026-09-29 14:06~14:20 KST, 프론트 5xx 알림(5분 합계 10건 초과)이 울렸다. 5xx 71건, 로그인·세션 확인·조회·EIR 등 엔드포인트를 가리지 않았다. 원인은 백엔드 레플리카 하나의 Redis 연결이 경로 중간에서 응답 없이 끊긴 것이다. Redis 서버는 정상이었고(부하·복제 정상, 서버측 연결 수만 3→2→3), 다른 레플리카도 멀쩡했다. 앱(Lettuce)은 끊긴 줄 모르고 그 소켓에 계속 써서, 커널이 재전송을 포기할 때까지(리눅스 기본 약 15분) 그 레플리카로 간 요청이 세션 조회에서 60초씩 기다리다 500 이 났다. 그때까지 Lettuce 는 Spring Boot 기본값이라 끊김 감지 장치가 없었고 명령 타임아웃도 60초였다.

    • 새 config/session/RedisClientConfiguration — LettuceClientOptionsBuilderCustomizer 로 소켓 옵션만 얹는다: TCP_USER_TIMEOUT 30초 + keepalive(30초 유휴 후 10초 간격). Spring 이 만든 SSL·명령 타임아웃 적용 옵션은 별도 필드라 그대로 남고, connect-timeout 설정이 있으면 옮겨 담는다.
    • 명령 타임아웃 기본값 60초 → 10초(LettuceClientConfigurationBuilderCustomizer). spring.data.redis.timeout 이 있으면 그 값이 우선한다. 운영엔 이 설정이 없어 10초가 적용된다. EIR 의 Redis 호출은 단일 키 get/setIfAbsent/delete 뿐이고 외부 토큰 발급은 Redis 명령 밖이라 10초에 걸리지 않는다.
    • 로컬 재현(Redis 컨테이너에서 양방향 패킷 DROP + 서버측 CLIENT KILL = 운영처럼 "서버는 잊었는데 앱은 모름"): 수정 전 요청마다 60초 대기, 100초가 지나도 감지 못 함(운영과 동일) / 수정 후 요청은 10초에 실패, 끊김 감지 30.5초(요청이 오가는 중)·37.3초(유휴), 경로가 살아나면 0.3~1.5초에 재연결. Cannot apply TCP User Timeout 경고 0건(epoll 에서 실제 적용).
    • 적용 조건: 리눅스 epoll 네이티브 전송에서만 먹는다. 운영은 epoll 을 쓴다(사건 로그의 NativeIoException 이 증거). epoll 이 없으면 경고만 남기고 종전처럼 동작한다.
    • ⚠️ 끊김 자체를 막지는 않는다 — 모르는 채 15분을 30~40초로 줄일 뿐이다. 끊김 원인은 미확정(Infra #75 — DB 연결과 같은 초에 끊겨 컨테이너 환경 쪽으로 보인다).
    • 검증: 설정 연결 테스트 RedisClientConfigurationTest 3건(기본값 적용, 설정값 우선, SSL 과 함께 유지). 진단법은 Redis 연결 끊김 진단.

    파트너 첨부 다운로드에 API 포털을 호출자로 추가했다 — HBLNO·CNTR_NO 선택값, 첨부 없으면 JSON (PR #177·#178·#179)¶

    GET /api/partner/download 는 eBiz(E-Service) 전용이었다. API 포털은 B/L 암호문도 컨테이너번호도 갖고 있지 않아 두 파라미터의 @RequestParam 을 떼고 HBLNO 유무로 분기한다(있으면 기존 EBIZ 동작 그대로, 없으면 로그 채널 API + 파일명 {MNGT_NO}.zip). ★애너테이션 없는 단순 타입은 Spring 이 catch-all resolver 로 잡아 required=false 가 되는데, 파라미터명 추론이 -parameters 에 의존하므로 그 옵션이 빠지면 IllegalArgumentException 으로 죽는다. ★첨부가 없을 때 200 + 22바이트 빈 ZIP 이 내려가던 것을 {"MSG":"There is no attachment."} JSON 으로 바꿨다 — 업무 오류가 아니라 상태코드는 200 유지(cancelEir 선례)이므로 호출자는 Content-Type 으로 분기해야 한다. ★그래서 Content-Disposition 세팅을 조회 이후·스트리밍 직전으로 옮겼다(분기에서 미리 걸면 JSON 을 내보내면서 브라우저가 다운로드를 띄운다). ⚠️조회 조건이 MNGT_NO 하나뿐이라 "첨부 없음"과 "견적번호 오류"는 여전히 같은 응답이고, HBLNO 가 하던 약한 관문(유효 암호문 1개 필요)이 사라졌다 — 보안·인증 문서 의 공개 URL 절 참고. downloadAll 은 손대지 않았다(eBiz 전용, 항목별 continue 라 동작이 다름 — 첨부 2건 이상이면 ZIP 이 깨지는 문제는 워크스루에 기록).

    CRS 견적에 소유 검증을 넣었다 — 24개 프로시저 중 20개에 없었다 (Infra #51)¶

AppRequests 에는 Referer 필드가 없고 ClientIP 가 0.0.0.0(프록시 뒤)이라 화면·사용자 추적이 불가능하다(실측). 반대로 nginx 로그엔 소요시간이 없어 소요는 집계 쪽 avg/p95 로만 싣는다. ★건수는 count() 가 아니라 sum(ItemCount) — AppRequests 는 샘플링된다. ★URL_PART 는 클라이언트 입력이라 kqlEscape 필수이고, 매칭은 has 가 아니라 contains 다(has 는 토큰 단위라 sendM 같은 조각을 놓친다). 범용 KQL 통과 API 는 의도적으로 두지 않았다 — 워크스페이스에는 nginx 액세스로그(SSO 토큰이 실린 URL·사용자 IP)까지 들어 있어 브라우저에서 임의 KQL 을 받으면 그대로 유출 경로가 된다. 실패/미구성/범위오류는 ERROR(또는 SUMMARY_ERROR/ROWS_ERROR) 키로 부분 실패 표시(대시보드 패턴 동일). 로컬 실측: 운영 워크스페이스 대상 sendMail 조회로 200 4건(평균 550ms·p95 753ms)과 화면·실 IP 정상 반환 확인.

    PR #108 이 만든 ClientAbortExceptionTranslator 는 MultipartException 계열 전체를 회선 절단으로 보고 400 + MSG000429("네트워크 문제로 저장/업로드가 중단되었습니다. 다시 시도해 주세요")로 응답했다. 그런데 같은 MultipartException 이라도 Content-Type 이 애초에 multipart 가 아닌 계약 위반이면 재시도해도 100% 같은 실패다 — 실제로 사용자가 하루 40회까지 재시도하는 동안(에러로그 ERR_SN 로 확인) 원인이 계약 위반이라는 사실이 드러나지 않았다. ★supports(Class<?>) 는 클래스만 받아 원인을 못 가르고, 두 경우 모두 최상위 클래스가 MultipartException 으로 동일하다 — 차이는 cause 에만 있다. 인스턴스를 받는 doTranslateMessage 에서 원인 체인에 InvalidContentTypeException 이 있으면 형식 오류 문구로 응답한다(상태코드 400·errDiv 02·unknown 은 불변). ★getCause() 를 한 번만 보면 안 된다 — 스프링이 MultipartException 으로 감싸고 그 안에 Tomcat 이 ServletException 을 한 겹 더 끼운다(Request.parseParts: catch (InvalidContentTypeException e) → new ServletException(e)). 회선 절단은 catch (IOException) 으로 다른 가지를 타므로 이 규칙으로 정확히 갈린다. 문구는 신규 코드 MSG000431("요청 형식이 올바르지 않습니다. 관리자에게 문의 바랍니다.")을 쓴다. ★코드마스터 TB_CMS_DATA_DIC(DATA_DIV='2') 에 ko/en/zh 3행 등록이 배포보다 선행돼야 한다 — LanguageService.getMessage() 는 미등록 코드를 코드 문자열 그대로 반환하므로 미등록 상태로 배포하면 화면에 문자 그대로 "MSG000431" 이 뜬다(PR #105 의 LOGIN_DIV E03~E05 등록과 동일한 선행 절차). 로컬 실측: 같은 400·errDiv 02·unknown 을 유지한 채 문구만 "네트워크 문제로 저장/업로드가 중단되었습니다…" → MSG000431 분기로 갈리는 것 확인(등록 전이라 코드 문자열로 출력되는 것까지 확인).
