    마이그레이션·이관 트러블슈팅 (Migration Pitfalls)¶

    레거시(Spring Boot 2.3 / Java 11 / 온프렘, Nuxt 2 프론트)에서 V2(Spring Boot 3.5 / Java 21 / Azure Container Apps, Vite·Vue 3 프론트)로 이관하며 드러나 해결한 문제들을 모았다. 공통 패턴은 "레거시 환경(윈도우 ko_KR·온프렘 동일망·Spring 5)에선 안 드러나던 가정이, 새 환경(리눅스 컨테이너·VPN 경유 NAS·Spring 6)에서 표면화" 다.

    각 항목은 증상 → 원인 → 해결 → 근거(커밋/파일) 형식. 상세는 MIGRATION_REPORT.md·migration-analysis.md·ADR 참조.

    1. 프레임워크 마이그레이션 (Spring Boot 2.3 → 3.5 / Java 11 → 21)¶

    1.1 로그인 후 후속 요청이 401 — SecurityContext가 세션에 영속 안 됨¶

    • 증상: /api/login 200 직후 /api/session·/api/menuMap 등이 401(InsufficientAuthenticationException).
    • 원인: Spring Security 6에서 AbstractAuthenticationProcessingFilter의 securityContextRepository 기본값이 세션 비저장(RequestAttributeSecurityContextRepository)으로 변경. Security 5는 로그인 컨텍스트를 자동으로 세션에 영속했으나 6은 명시 설정이 없으면 Redis 세션에 안 남음.
    • 해결: WebSecurityBeansConfiguration.createLoginAuthenticationProcessingFilter()에 filter.setSecurityContextRepository(new HttpSessionSecurityContextRepository()) 추가 → spring-session-data-redis가 SINOKORSESSION을 Redis에 영속.
    • 근거: MIGRATION_REPORT.md §9.7.

    1.2 부팅 시 컨텍스트 로딩 실패 2건 (@Bean+@Autowired / localeResolver)¶

    • 증상: 컴파일은 통과하나 부팅 시 BeanDefinitionParsingException / localeResolver 빈 이름 충돌.
    • 원인: ①Spring 6은 @Bean 메서드에 @Autowired 동시 사용 금지(Spring 5는 허용). ②@EnableWebMvc + 별도 localeResolver @Bean이 DelegatingWebMvcConfiguration의 빈과 충돌.
    • 해결: ①@Autowired 제거(파라미터 자동주입). ②DelegatingWebMvcConfiguration 상속 + localeResolver() @Override.
    • 근거: MIGRATION_REPORT.md §9.2.

    1.3 순환참조 기본 금지 — 보안설정 ↔ AdminService 부팅 실패¶

    • 증상: 보안설정이 PasswordEncoder/예외핸들러 통해 AdminService에 순환 의존 → SB3 부팅 거부.
    • 원인: Spring Boot 2.6+/3은 순환참조 기본 금지(2.3은 묵인).
    • 해결: spring.main.allow-circular-references=true로 동작 보존.
    • 근거: MIGRATION_REPORT.md §9.6.

    1.4 javax → jakarta 전수 전환 + 프레임워크 6 API 변경¶

    • 증상: Jakarta EE 9+ 패키지 이동·Spring 6 API 변경으로 컴파일 오류 다수(인프라 슬라이스 92건).
    • 원인: javax.servlet/mail/transaction → jakarta.*, Security 5→6(WebSecurityConfigurerAdapter 제거·antMatchers→requestMatchers), AWS SDK v1→v2, Spring Integration IntegrationFlows→IntegrationFlow, Jackson PropertyNamingStrategyBase→PropertyNamingStrategies.NamingBase, WebClient HttpStatus::isError→HttpStatusCode::isError.
    • 해결: 근본 원인으로 수렴 후 일괄 치환. javax.transaction.Transactional→org.springframework.transaction.annotation.Transactional. javax.imageio/crypto/sql/net은 JDK 표준이라 유지.
    • 근거: MIGRATION_REPORT.md §9.8·§9.11.4.

    1.5 죽은 라이브러리 교체 (+ LLM 버전 환각 차단)¶

    • 증상: log4jdbc-remix·ChainedTransactionManager·구 pebble 등 SB3 미지원. 조사 단계서 환각 버전(pebble 4.1.1 등) 혼입.
    • 해결: log4jdbc→p6spy 1.12.1, ChainedTransactionManager→단일 매니저, pebble→io.pebbletemplates 3.2.4, AWS SDK v1→awspring 3.4.2. 적대적 검증 에이전트로 좌표/버전 확정(환각 4건 교정).
    • 근거: MIGRATION_REPORT.md §3.2·§3.3, migration-analysis.md §8.

    2. 동작 패리티 (PageHelper · 화면 이관)¶

    2.1 PageHelper 1.2.3 → 1.4.7: pageSize=0 전체조회가 빈 결과¶

    • 원인: PageHelper 1.4.x부터 pageSize=0(전체조회) 기본 비활성.
    • 해결: application.yaml에 pageSizeZero: true 명시(레거시 동작 복원). 삭제 시 회귀 — ADR-0003에 '삭제 금지' 명시.
    • 근거: adr/0003-pagehelper-pagesizezero.md.

    2.2 Oracle 페이징 합성 컬럼 PAGEHELPER_ROW_ID 응답 누출¶

    • 증상: 실 페이지 파라미터로 Oracle 페이징 시 응답 각 행에 PAGEHELPER_ROW_ID가 섞임(레거시는 ROW_ID였고 둘 다 누출).
    • 원인: PageHelper core 5.2.0에서 합성 컬럼 alias 변경. 매퍼 resultType=dmap가 모든 컬럼을 잡아 누출.
    • 해결: core/mybatis/PageHelperRowIdStripInterceptor(ResultSetHandler 인터셉터)로 PAGEHELPER_ROW_ID 제거. ⚠️ 수동 @Bean SqlSessionFactory라 자동 수집이 back-off됨 → VpDataBaseConfiguration.createSqlSessionFactory()에서 setPlugins(...)로 직접 등록 필요.
    • 근거: MIGRATION_REPORT.md §9.10.1·§9.11.1.

    2.3 ORDER BY 없는 GROUP BY 페이징의 행 순서 변화¶

    • 원인: PageHelper 5.3.3은 항상 2중 래핑(SELECT * FROM (SELECT …,ROWNUM … FROM(…)))이라 Oracle plan이 SORT→HASH GROUP BY로 바뀌어 정렬 부수효과가 사라짐. ORDER BY가 없어 순서가 plan 의존이던 잠재 결함이 드러남.
    • 해결: startPage 45건 전수 분류 → 프론트가 실제 호출하는 1건(MdmCustomerMgt.selectList)에만 ORDER BY 추가(미호출 건은 미변경).
    • 근거: MIGRATION_REPORT.md §9.11.2.

    2.4 비밀번호 초기화 화면(/login/pw-init) 이관 누락 (프론트)¶

    • 증상: 로그인 전 비번 초기화 흐름(메일→임시PW→변경) 불가.
    • 원인: Nuxt2→Vue3 화면 일괄 이관 시 1건 누락(인벤토리 오기재).
    • 해결: src/pages/login/pw-init/index.vue로 이관. 로컬 프론트+Azure 백엔드로 e2e 검증.
    • 근거: 프론트 커밋 8b2b25d.

    3. Azure 이관 / 인프라 (온프렘 → Container Apps, NAS/Oracle는 VPN 경유)¶

    3.1 리눅스 컨테이너 NLS 불일치 → ORA-01861¶

    • 증상: 날짜 다루는 프로시저(SP_GET_SUR_NOTICE 등) 호출 시 ORA-01861. DB 직접 실행은 정상, 앱에서만 실패.
    • 원인: 데이터소스에 NLS 초기화가 없어, 리눅스 컨테이너(US/UTC) ojdbc가 NLS_TERRITORY=AMERICA 세션으로 열림. 레거시(윈도우 ko_KR)는 세션 NLS가 한국이라 안 드러남.
    • 해결: VpDataBaseConfiguration HikariDataSource connectionInitSql로 세션 NLS 고정(ALTER SESSION SET NLS_LANGUAGE='KOREAN' NLS_TERRITORY='KOREA' NLS_DATE_FORMAT='RR/MM/DD' …).
    • 근거: 커밋 d6f1ace (PR#3).

    3.2 ACA 프로브 경로 /actuator → /application 불일치 (무음 헬스체크)¶

    • 증상: 프로브가 /actuator/health를 쳐 302(login redirect) → ACA가 3xx를 우연히 healthy로 처리. 실제 헬스 미검증.
    • 원인: management.endpoints.web.base-path=/application이라 actuator는 /application/*에 노출. /actuator/*는 보안필터에 걸려 302.
    • 해결: ①백엔드 management.endpoint.health.probes.enabled=true + security permit-all에 /application/health/{readiness,liveness} 추가. ②인프라 app-backend.bicep 프로브 경로를 /application/health/*로 교정.
    • 근거: 커밋 4e3375c(PR#2) + 우산 0085c40.

    3.3 통합 /application/health가 SMTP 미도달로 행(hang)¶

    • 증상: Azure에서 health가 ~35s 행 → 프로브 타임아웃.
    • 원인: actuator MailHealthIndicator가 통합 health에 묶여 온프렘 SMTP 미도달 시 대기.
    • 해결: management.health.mail.enabled=false.
    • 근거: 커밋 4e3375c(PR#2).

    3.4 백엔드 ingress internal 시 "App Unavailable" 404 (직노출 차단)¶

    • 증상: 백엔드 external=false 전환 시, 프론트가 .internal FQDN 을 프록시하면 백엔드가 아니라 ACA "Azure Container App - Unavailable" 404 페이지가 돌아옴(같은 env 내인데 라우팅 실패). 2026-06-23·08-19 재현.
    • 진짜 원인: nginx resolver 가 168.63.129.16(Azure 공용 DNS) 이었던 것. 공용 DNS 는 .internal FQDN 을 공용 인그레스로 해석 → 공용 인그레스는 "이 FQDN 은 external 앱 아님" → Unavailable. (초기엔 "internal→internal 라우팅 불가"로 오진하고 external=true 로 우회했음.)
    • 해결(2026-08-19): nginx resolver 를 컨테이너 자체 DNS(/etc/resolv.conf nameserver, ACA=127.0.0.11→클러스터 DNS)로 교체. 부트스크립트 frontend/docker-entrypoint.d/15-set-resolver.envsh(공식 nginx 엔트리포인트가 *.envsh 를 20-envsubst 보다 먼저 source)가 NGINX_RESOLVER 를 덮어씀. → .internal FQDN 이 사설 인그레스로 정확히 해석돼 백엔드 도달. app-backend.bicep ingress external=false 로 복귀(직노출 제거). FE #117/#118.
    • 덤: 백엔드 공용 FQDN 직호출이 원천 차단(404) → 프론트 nginx 경유만 가능. 프론트 /api 에 limit_req(정문 flood 완화)도 추가.
    • 근거: 우산 fc5282d·24b281f(구 external 우회), FE #117/#118 · Infra(external:false).

    • 증상: 배포로 리비전 교체 시 처리 중이던 요청(긴 다운로드·쿼리)이 드레인 없이 끊김. application.yaml 에 server.shutdown: graceful + spring.lifecycle.timeout-per-shutdown-phase 를 설정했는데도 동작 안 함.
    • 원인: ENTRYPOINT ["sh","-c","java $JAVA_OPTS -jar app.jar"] 에서 베이스(eclipse-temurin, /bin/sh=dash)가 java 를 자식으로 fork → 셸이 PID 1 로 남아 ACA 의 SIGTERM 이 JVM 에 전달되지 않음(로컬 프로세스 트리로 실측 확인). graceful shutdown 은 SIGTERM 을 받아야 시작된다.
    • 해결: exec 추가 → ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS -jar app.jar"]. java 가 셸을 replace 해 PID 1 이 되어 SIGTERM 을 직접 수신 → 드레인 실동작. $JAVA_OPTS 셸 확장은 그대로 유지됨.
    • 근거: PR #31.

    3.11 self-hosted Windows 러너 이전 + az acr build cp949 크래시¶

    • 배경: GitHub Actions 월 쿼터 소진으로 호스티드 러너 잡이 즉시 실패(2~3초/0스텝) → CI/CD 를 온프렘 self-hosted Windows 러너로 이전하며 deploy.yml 을 PowerShell 로 이식(runs-on: [self-hosted, Windows, vendor-portal-v2], shell: powershell; 본문은 Windows PowerShell 5.1 호환이라 PowerShell 7 불필요). az acr build 가 이미지를 ACR(클라우드)에서 빌드하므로 러너엔 Docker/JDK/Node 가 필요 없고 Git + PowerShell + Azure CLI 만 있으면 된다(az 는 MSI 1회 설치 후 러너 서비스 재시작).
    • 증상(프론트 배포): az acr build 가 스트리밍하는 빌드 로그에 UTF-8 전용 문자(프론트 vite 의 ✓ U+2713)가 있으면 UnicodeEncodeError: 'cp949' codec can't encode 로 죽는다. 백엔드(gradle) 빌드는 해당 문자가 없어 통과.
    • 원인: az 가 번들 Python 을 격리 모드(-IBm)로 실행 → PYTHONIOENCODING/PYTHONUTF8 등 환경변수를 무시한다. 리다이렉트 출력의 인코딩이 시스템 ANSI 코드페이지(한국어=cp949)로 고정됨.
    • 해결: 러너 시스템 로케일을 UTF-8(ACP/OEMCP/MACCP=65001)로 바꾸고 재부팅(intl.cpl → 관리자 옵션 → "Beta: 세계 언어 지원을 위해 Unicode UTF-8 사용"). 재부팅 후 GetACP=65001 → az 출력이 UTF-8 로 나가 정상. (대안: 빌드 스텝서 python -I -X utf8 -m azure.cli acr build ... 직접 호출 — 커맨드라인 플래그라 격리모드에도 적용.)
    • 미완(당시): ci.yml·docs-deploy.yml 이식엔 러너에 JDK 21(CI)·Python(문서) 필요 + 문서 발행 peaceiris/actions-gh-pages 는 Docker 컨테이너 액션이라 Windows 러너서 못 돌아 PAT git push 로 대체 필요. (그 뒤 실제로 이식됨: 문서는 Python venv provision + PowerShell git push, CI 는 스텁 유지.)
    • 후속(2026-07-23) — GitHub-hosted 복귀: GH Actions 분 복구로 3개 워크플로 모두 hosted(ubuntu-latest)로 되돌림(PR #60·프론트 #85). self-hosted(PowerShell/stub) 버전은 각 워크플로 하단 주석 블록으로 보관 → 각 줄 # 제거로 재전환. 즉 이 절 내용은 self-hosted 재전환 시 참고로 유지.

    4.1 FTP PDF/첨부 잘림 → 전체 버퍼링 + completePendingCommand¶

    • 증상: PDF 뷰어가 "문서를 로드하지 못함". 받은 파일이 헤더만 살고 꼬리가 잘린 깨진 PDF(특히 대용량).
    • 원인: retrieveFileStream() 라이브 스트림을 그대로 반환해 서블릿이 lazy 소비. Azure↔VPN↔NAS 저속 링크에서 전송 완료(226) 확인 전 스트림이 끊겨 부분 파일. 온프렘 동일망에선 빠른 전송이라 안 드러남.
    • 해결: 서버에서 전체를 ByteArrayOutputStream에 버퍼링 → completePendingCommand()(226 확인) → 분리 스트림 반환.
    • 근거: FileDataService.fetchNasBytes (PR#7에서 5개 FTP 다운로드 메서드를 이 코어로 통합).

    4.2 FTP 전송 극저속 → setBufferSize¶

    • 증상: 다운로드/뷰어가 느림.

    4.4 리버스 프록시 뒤 X-Forwarded 처리¶

    • 원인: nginx→ACA 다단 프록시 뒤라 스킴/호스트/클라이언트IP가 프록시 것으로 잡힘.

    • 근거: application.yaml.example:13.
    • 로그인 로그 함의: TB_CMS_LOGIN_LOG.LOGIN_IP = getRemoteAddr() + "," + X-Forwarded-For 를 콤마로 잘라 CLIENT_IP/PROXY(1)/PROXY(2) 로 표시한다. native 의 Tomcat RemoteIpValve 가 실제 클라이언트를 getRemoteAddr() 로 뽑고 사설 프록시(172.21.x 등)를 신뢰 내부프록시로 제거하므로 → CLIENT_IP = 실제 사용자 공인 IP(정상), PROXY(1) 은 공인 포워드 프록시 경유 시에만, PROXY(2) 는 3단 이상 공인 체인에서만 값이 생겨 실환경엔 사실상 빈다. (프론트 조회 화면은 이에 맞춰 PROXY(2) 숨김·PROXY(1)→PROXY IP — 프론트 PR #83.)

    4.5 EIR 이중 발급 — 다중 인스턴스 Redis 락 + 비멱등 전송¶

    • 증상: 한 번의 발급 클릭이 두 요청으로 갈라져 서로 다른 백엔드 인스턴스(PID 상이)에서 각각 SIPG 전송 → 같은 B/L·컨테이너에 EIR 2건, TB_EIR_RESPONSE_LOG 2행, SIPG receiptNo 2개.
    • 원인: ACA minReplicas=2 다중 인스턴스라 인스턴스 메모리 기반 가드로는 인스턴스 간 중복을 못 막는다. HttpClient 자동 재시도가 비멱등 발급을 조용히 재전송할 수 있고, execute() 예외를 catch 가 흡수하면 응답필드가 비어 컨트롤러가 락을 풀어 재발급 여지가 생긴다.
    • 해결: Redis 분산락(setIfAbsent=SETNX, 키 lock:eir:issue:{COMP}:{BL}:{CNTR}:{SEND}, TTL 60s)으로 인스턴스 무관 단일화. sendSIPGNew 는 disableAutomaticRetries() + execute() 실패 시 httpClient.close() 후 rethrow(흡수 금지). SIPG 전송 前 단계 예외에서만 락 해제(전송 후 예외는 도달 여부 불명이라 락 유지). RequestConfig 로 타임아웃 명시(조회 30s/전송 120s).
    • Redis 실체(중요): 토큰 캐시(token:*)·세션·이 락은 전부 단일 자동구성 StringRedisTemplate 이 쓰는 하나의 Redis 를 공유한다(커스텀 RedisConnectionFactory 없음). 운영 = Azure Managed Redis vp-prod-redis(포트 10000·TLS, SPRING_DATA_REDIS_HOST env), 로컬 = localhost:6379. ⚠️ 레거시(partner) Redis(221.143.40.13:6379)와는 별개 → 락은 V2 인스턴스 간엔 유효하나 레거시↔V2 크로스 중복은 못 막는다(두 시스템이 같은 Redis 를 봐야 가능). 락 TTL(60s) < 전송 타임아웃(120s)이라 전송이 60s 넘게 지연된 사이 재요청이 오면 이론상 재발급 여지가 있으나 프론트 재진입 가드로 실질 트리거는 좁다(레거시 값 계승, 현행 유지 결정).
    • 근거: EirService.tryIssueLock/getIssueLockKey/sendSIPGNew, EirController.issueEirNew/cancelEirNew(PR #71). 프론트 재진입 가드는 [프론트 트러블슈팅 §11]. 참고: 다중 인스턴스 토큰 발급 자체도 이미 lock:token:* 분산락으로 단일화돼 있다.

    4.6 레거시→V2 SSO 최초 진입 Tomcat 500 — JWT nbf clock skew¶

    • 증상: USER_DIV='V2' 사용자가 레거시 로그인 → V2 로 SSO 자동전환 시 최초 진입에서 HTTP 500(Tomcat 기본 에러 페이지), 새로고침하면 정상 로그인.
    • 원인: 레거시가 SSO 토큰 nbf(notBefore)를 발급 순간(LocalDateTime.now())으로 찍는데, V2 컨테이너 시계가 발급 호스트보다 1~2초 느리면 검증 시 now < nbf. auth0 검증기는 leeway=0 이라 IncorrectClaimException("The Token can't be used before .."). 이 예외를 JwtIssueService.verify() 가 삼켜 null 반환 → JwtVerifyAuthenticationProvider 가 jwt==null null 반환 → AuthenticationProviderChain.process(null) 이 다음 단계 null.getClass() 로 NPE → NPE 는 AuthenticationException 이 아니라 JwtAuthenticationFilter 의 catch(AuthenticationException) 가 못 잡음 → 컨테이너로 전파 → Tomcat 500. 세션 저장(saveContext) 前 단계라 실패하고, 수 초 뒤 새로고침 땐 now >= nbf 라 통과되어 로그인됨(=새로고침하면 되던 정체). TZ 무관(nbf 는 UTC instant 비교=순수 벽시계 skew).
    • 해결: ① JwtIssueService 검증기에 acceptLeeway(30) — 발급/검증 호스트 시계 오차(nbf/exp/iat) 흡수(500 제거). ② JwtVerifyAuthenticationProvider 검증 실패(blank·verify null·userId 누락) 시 null 대신 JwtAuthenticationException 던짐 → 체인 NPE(500) 대신 정상 인증실패(failureHandler). 앞으로 만료·서명불일치 등 어떤 토큰 문제든 raw 500 방지. — PR #84.
    • 일반화: 이 백엔드는 서버사이드 HTML 에러뷰가 없어 필터에서 던진 예외(인증 provider 가 실패 시 null 반환 → 체인 NPE 포함)는 앱 커스텀 에러페이지가 아니라 Tomcat 기본 500 으로 뜬다 → 브라우저 내비게이션에서 Tomcat 500 = 필터단 미포착 예외 신호. 인증 provider 는 실패 시 null 반환 금지(체인이 NPE).
    • 근거: JwtIssueService(생성자 verifier)·JwtVerifyAuthenticationProvider.authenticate. SSO 핸드오프 전반은 보안·인증.

    5. 프론트엔드 (Nuxt 2 / Vue 2 → Vite 5 / Vue 3)¶

    5.1 화면 간 인자 전달(receive-args)이 Vue 3에서 끊김¶

    • 원인: 레거시는 인스턴스 이벤트 버스(this.$on/$emit('receive-args'))로 인자를 전달했는데 Vue 3는 인스턴스 $on/$emit을 제거 → 배선이 통째로 죽음.
    • 해결: src/mixins/page/index.ts 베이스 mixin의 mounted/activated 훅에서 consumeArgs 후 onReceiveArgs(data) 직접 호출. <keep-alive> 캐시 탭 재진입 대비 activated도 필요.
    • 근거: 프론트 커밋 a74125a.

    5.2 DevExtreme 입력 위젯 write-back 누락¶

    • 원인: 레거시 Vue2 :value/@input 단방향이라 $emit('input')만 했는데, Vue3 v-model은 update:modelValue를 기대.
    • 해결: src/plugins/dev-extreme.ts 프록시에 update:modelValue+input 병행 emit.
    • 근거: 프론트 커밋 a74125a.

    5.3 FE-24 리포트: DevExpress 뷰어 폐기 → 자체 HTML 뷰어¶

    • 증상: DevExpress 21.1.12 뷰어 자산을 document.head에 주입하니 dx CSS가 전역 오염 → 메인 페이지 위젯(번들 devextreme 22.1.3)과 충돌.
    • 해결: DevExpress 뷰어 폐기 → 자체 HTML/CSS 리포트 뷰어(CmsHtmlReportPopup 공통 셸 + reports/ 분리 + REPORTS 레지스트리)로 전환.

    5.4 미사용 외부연동 死코드 식별 (S3 다운로드 · Azure GPT)¶

    • 배경: Azure 이관 시 외부연동이 실연결 검증 대상으로 남아 부담. 실제로는 운영 미사용.
    • 해결: 로직 변경 없이 폐기 주석만 부착해 실테스트 표면에서 제외.
    • 근거: 백엔드 a0ee613(PR#4), 프론트 8b2b25d.
