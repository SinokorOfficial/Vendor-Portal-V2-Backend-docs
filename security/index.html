    보안 · 인증¶

    VP 백엔드의 인증은 Spring Security 6 위에 직접 구현한 AuthenticationProvider 체인 + 세션(Redis) 영속 구조다. 일반 ID/PW 로그인과 JWT(SSO 링크) 두 경로를 별도 체인으로 처리하고, 인증된 사용자 정보(LoginUser)를 Redis 세션에 보존한다.

    시크릿 정책

    JWT 비밀키·Redis 비밀번호·MASTER_PASSWORD 등 실값은 gitignore된 application*.yaml 에만 둔다. 이 문서에는 설정 키 경로만 적고 실값은 싣지 않는다.

    전체 인증 구조¶

    인증 진입점은 두 개의 필터다. 둘 다 SecurityFilterChain에 addFilterAt으로 등록된다 (config/web/security/WebSecurityConfiguration.java:55-56).

    필터 등록 위치 트리거 사용 매니저
    JwtAuthenticationFilter BasicAuthenticationFilter 자리 Authorization 헤더 또는 ?token 존재 시 createJwtAuthenticationManager()
    LoginAuthenticationProcessingFilter UsernamePasswordAuthenticationFilter 자리 POST /api/login (JSON) createLoginAuthenticationManager()

    각 매니저는 ProviderManager를 상속한 LoginAuthenticationManager이며, 내부에 하나의 AuthenticationProviderChain 을 provider로 담는다 (config/web/security/beans/WebSecurityBeansConfiguration.java:129-159).

    CORS/CSRF

    http.cors(disable).csrf(disable) — 둘 다 비활성. 모든 경로는 permitAll 매핑을 제외하고 authenticated 다 (WebSecurityConfiguration.java:40-49).

    AuthenticationProviderChain (체인 팩토리)¶

    AuthenticationProvider를 직렬로 연결해 순차 통과시키는 단방향 링크드 체인이다.

    • 빌드 API: AuthenticationProviderChain.chain(p1).chain(p2)...build() — .next()가 아니라 .chain()을 반복 호출한다 (provider/AuthenticationProviderChainBuilder.java:12-27).
    • 처리 흐름 (provider/AuthenticationProviderChain.java:26-31):
    public Authentication process ( Authentication authentication ) {
    if ( provider.supports( authentication.getClass() ) ) {
        authentication = provider.authenticate( authentication );
    }
    return next != null ? next.process( authentication ) : authentication;
}
    1. provider.supports(auth.getClass()) 가 true면 authenticate() 실행 (false면 통과만)
    2. next가 있으면 그 결과를 다음 체인에 넘겨 재귀
    3. 마지막 노드의 결과가 최종 Authentication

    Note

    provider/core/AbstractAuthenticationProviderChain 는 @Deprecated 다. 현재 체인은 위 AuthenticationProviderChain 를 쓴다.

    실제 체인 구성¶

    WebSecurityBeansConfiguration.java:144-159 에서 두 체인이 만들어진다.

    flowchart LR
    subgraph 로그인["로그인 체인 (createAuthenticationProvider)"]
        A1[LoginUserDaoAuthenticationProvider] --> A2[LoginSuccessfulAuthenticationProvider]
    end
    subgraph JWT["JWT 체인 (createJwtAuthenticationProvider)"]
        B1[JwtVerifyAuthenticationProvider] --> B2[JwtSwitchingLoginUserAuthenticationProvider] --> B3[LoginSuccessfulAuthenticationProvider]
    end
    Provider supports 대상 역할
    LoginUserDaoAuthenticationProvider GuestAuthentication DAO/마스터PW 인증
    JwtVerifyAuthenticationProvider GuestAuthentication JWT 서명·클레임 검증 → JwtUserAuthentication
    JwtSwitchingLoginUserAuthenticationProvider JwtUserAuthentication JWT를 LoginUser로 전환(SSO)
    LoginSuccessfulAuthenticationProvider LoginUserAuthentication 최종 성공 처리(setAuthenticated(true), credential 소거)

    로그인 흐름 (ID/PW)¶

    sequenceDiagram
    participant C as 클라이언트
    participant F as LoginAuthenticationProcessingFilter
    participant M as LoginAuthenticationManager
    participant Dao as LoginUserDaoAuthenticationProvider
    participant Succ as LoginSuccessfulAuthenticationProvider
    participant Redis as Redis 세션

    C->>F: POST /api/login (JSON: p, c)
    Note over F: Content-Type=application/json,<br/>ContentLength>0 방어
    F->>F: GuestAuthentication(userId, pw) 생성
    F->>M: authenticate(GuestAuthentication)
    M->>Dao: 체인 process()
    Dao->>Dao: loadUserByUsername(userId)
    alt MASTER_PASSWORD 일치
        Dao-->>Succ: LoginUserAuthentication (마스터)
    else 일반 로그인
        Dao->>Dao: super.authenticate() (BCrypt 검증)
        Dao-->>Succ: LoginUserAuthentication
    end
    Succ->>Succ: setAuthenticated(true), credential 소거
    Succ-->>M: 인증 완료
    M-->>F: Authentication
    F->>Redis: HttpSessionSecurityContextRepository 저장
    F-->>C: 성공 응답
    Note over Dao: 실패 시 loginFailureService.loginFailure() 후 예외 재전파

    진입 필터는 POST /api/login JSON 요청만 시도한다. Content-Type이 application/json이 아니거나 본문이 비면 null을 반환해 인증 자체를 건너뛴다 (filter/LoginAuthenticationProcessingFilter.java:29-37).

    마스터 패스워드 (환경변수)¶

    LoginUserDaoAuthenticationProvider는 Spring의 DaoAuthenticationProvider를 확장하며, 일반 인증 앞단에 마스터 패스워드 분기를 둔다 (provider/LoginUserDaoAuthenticationProvider.java).

    • 주입: @Value("${MASTER_PASSWORD:}") — 환경변수 MASTER_PASSWORD (line 29-30). 미설정 시 빈 문자열.
    • 검증 조건 (line 68):
    if (masterPassword != null && !masterPassword.isEmpty() && userPw.equals(masterPassword)) {
    return createSuccessAuthentication((LoginUser) loadedUser);
}
    • 미설정(빈 값)이면 조건이 거짓 → 마스터 로그인 비활성. 일치 시 비밀번호 검증 없이 해당 사용자로 성공 처리.
    • 일반 경로는 super.authenticate()로 BCrypt 검증(createPasswordEncoder() = BCryptPasswordEncoder, WebSecurityBeansConfiguration.java:204-206).
    • AuthenticationException 발생 시 loginFailureService.loginFailure() 호출 후 재전파 (line 78-81).

    Warning

    MASTER_PASSWORD가 일치하면 평문 비교(equals)만으로 어떤 계정으로든 로그인된다. 운영 환경에서는 환경변수 설정 여부를 신중히 관리할 것.

    JWT (HMAC256)¶

    발급/검증은 JwtIssueService가 담당한다 (core/web/security/service/JwtIssueService.java). 라이브러리는 com.auth0.jwt(java-jwt).

    • 알고리즘: Algorithm.HMAC256(secret) (line 25, 60).
    • 비밀키: security.jwt-hmac256-secret → SecurityProperty.jwtHmac256Secret → 생성자 주입 (config/service/security/JwtServiceConfiguration.java:16-18).
    • 표준 클레임: jti(JWTId), sub(Subject), aud(Audience), iss(Issuer), iat(IssuedAt=now), nbf(NotBefore), exp(ExpiresAt), scope(배열).
    • 확장 클레임: 오버로드에서 userId, corpCd 추가(line 79-99). SSO용 추가 오버로드는 ssoCustCd, systemDiv, reqOptrNm, reqOptrTel, reqOptrEmail 까지 담는다(line 101-126).
    • 검증: verify(String) 은 실패 시 예외를 잡고 null 반환(line 66-73). verify(DecodedJWT) 는 예외 전파.

    JWT 필터 동작¶

    JwtAuthenticationFilter는 OncePerRequestFilter 다 (filter/JwtAuthenticationFilter.java).

    1. Authorization 헤더에서 토큰 추출, 없으면 ?token 파라미터, 둘 다 없으면 필터 통과(line 54-61).
    2. "bearer " 접두사 제거 — replaceFirst("bearer ", "") (line 26, 62).
    3. GuestAuthentication(null, token, X-Forwarded-For) 생성 — remoteAddr는 X-Forwarded-For 헤더 (line 63).
    4. authenticationManager.authenticate() → 성공 시 새 SecurityContext를 만들어 SecurityContextHolder에 설정한다. SSO 전환 결과(LoginUserAuthentication)일 때는 SecurityContextRepository(HttpSessionSecurityContextRepository)로 세션에도 명시 저장한다 — SB6는 요청 종료 시 컨텍스트를 자동 저장하지 않으므로(SecurityContextHolderFilter), 이 저장이 없으면 SSO 링크(?token=) 진입이 세션으로 이어지지 않아 재요청 시 로그인 화면으로 떨어진다. 실패 시 failureHandler 위임. 아울러 SSO 전환 성공 시 LoginSuccessService.loginSuccess() 를 직접 호출해 TB_CMS_LOGIN_LOG 에 S01(LOGIN_MSG='Login at V2')을 남긴다 — 종전엔 이 필터에 성공 핸들러가 없어 레거시→V2 SSO 유입이 로그인 로그에 전혀 안 남았다. LoginAuthenticationSuccessHandler 를 배선하지 않고 서비스를 직접 부르는 이유는, 그 핸들러가 200 응답 바디를 써버려 /api/link 의 sendRedirect 를 깨뜨리기 때문이다. 세션 재사용(프로바이더가 기존 인증 객체를 그대로 반환)은 새 로그인이 아니므로 인증 전후 객체를 참조 비교해 제외하고, 적재 실패는 catch 해 SSO 자체를 막지 않는다(fail-open).

    JWT 검증 Provider 방어 로직¶

    JwtVerifyAuthenticationProvider.authenticate() (line 40-83)는 java-jwt 3.x→4.x 마이그레이션 호환을 위해 단계별 방어를 둔다.

    • 타입/토큰/Bearer 접두사/verify==null 방어 후, 필수 클레임 userId 가 누락(isMissing())이거나 null(isNull())이면 거부(line 71-74) — 3.x의 "누락+null 모두 거부" 동작 보존.
    • 성공 시 JwtUser(JwtDetails) + remoteAddr로 JwtUserAuthentication 반환.

    SSO 전환¶

    JwtSwitchingLoginUserAuthenticationProvider는 jwtId가 "SSO"일 때만 동작한다(provider/JwtSwitchingLoginUserAuthenticationProvider.java:52).

    • 기존 세션이 LoginUserAuthentication이고 그 사용자가 토큰의 userId+corpCd와 동일할 때만 재조회 없이 재사용한다. 사용자가 다르면(예: 한 브라우저에서 A 세션 상태로 B의 SSO 토큰 진입) 기존 세션을 무시하고 토큰 사용자로 새로 로그인(스위칭)한다.
    • 전환 시 JWT 클레임(userId/corpCd/ssoCustCd/systemDiv/reqOptrNm/reqOptrTel/reqOptrEmail)을 =:=로 묶어 loadUserByUsername에 넘겨 LoginUser로 전환한다.

    외부 진입 형태

    소스 주석 기준 SSO 링크는 https://APP-HOST/api/link?token=<jwt> 형태로 쿼리스트링 토큰을 받는다 (JwtSwitchingLoginUserAuthenticationProvider.java:30-34).

    점진 전환(카나리) 운영 상태 — 2026-08-20 기준

    이 SSO 경로는 레거시→V2 점진 컷오버에 실사용 중이다: TB_CMS_USER.USER_DIV='V2' 로 지정된 사용자가 레거시에 로그인하면 JWT 를 발급받아 V2 로 무비밀번호 자동 유입된다(레거시 측 발급·리다이렉트 배포 포함, 운영 가동 중). 최초 진입 시 간헐 500 은 JWT nbf clock skew 였고 acceptLeeway(30) 로 해소됐다(PR #84, 마이그레이션 함정 §4.6).

    세션 (Redis 영속)¶

    Spring Security 6에서 인증 컨텍스트 저장 기본값이 비세션(RequestAttributeSecurityContextRepository)으로 바뀌어, 레거시(Security 5)의 세션 영속을 복원하기 위해 HttpSessionSecurityContextRepository를 명시 설정한다 (WebSecurityBeansConfiguration.java:86-89).

    설정 키 값 근거
    spring.session.store-type redis application.yaml:60
    spring.session.redis.flush-mode on-save application.yaml:61-62
    spring.session.timeout 7200 (초, 2시간) application.yaml:63
    server.servlet.session.timeout 120m application.yaml:11
    server.servlet.session.cookie.name SINOKORSESSION application-default.yaml.example:6-9
    spring.data.redis.host / port (개발 호스트) / 6379 application.yaml:54-58 (운영은 application-prod.yaml)
    • SINOKORSESSION은 세션 쿠키 이름이다(프로파일 yaml에서 설정). spring-session-data-redis가 HttpSession을 Redis로 영속화하여 후속 요청 인증을 유지한다.
    • Redis 비밀번호는 spring.data.redis.password (gitignore된 yaml의 실값 또는 __REDIS_PASSWORD__ placeholder).

    탭 신원 대조 (X-Client-User → 409)¶

    SINOKORSESSION 은 탭이 아니라 브라우저 단위 쿠키다. 같은 브라우저에서 다른 계정으로 로그인하면 먼저 열려 있던 탭의 세션까지 통째로 덮어써지는데, 그 탭의 화면 상태(USER_ID/CORP_CD/COMP_CD/CUST_CD 봉투)는 옛 계정 그대로 남는다.

    ⇒ 세션은 새 계정, 봉투는 옛 계정 → 그 탭의 요청이 남의 데이터에 닿는다.

    로컬 실측: TSN21 세션에 봉투만 CUST_CD=TSN01 로 바꿔 SP_GET_EST 를 호출하면 209,141건(전부 TSN01 의 견적)이 나왔다.

    동작¶

    프론트   요청 헤더  X-Client-User: TSN01     (이 탭이 아는 계정)
백엔드   세션 userId(TSN21) 와 대조
         다르면 → 409 + X-Session-Mismatch: TSN21,  비즈니스 로직 진입 안 함

    SessionIdentityGuardFilter.java — AuthorizationFilter 뒤에 둔다(WebSecurityConfiguration.java). 즉 인증·인가가 끝나 SecurityContext 가 확정된 뒤에 대조한다.
    헤더 없음 검사하지 않고 통과. 캐시된 옛 프론트 번들·파트너 API(JWT)·외부 딥링크가 이 헤더를 모른다
    세션이 LoginUser 가 아님 통과. 미인증·파트너 JWT 는 대조할 대상이 없다
    로그인 요청 애초에 도달하지 않는다. AbstractAuthenticationProcessingFilter 가 체인을 끊고 응답한다
    불일치 409 + X-Session-Mismatch(실제 세션 계정)

    설계 근거¶

    • 요청 검증이지 응답 검증이 아니다. 응답 시점엔 저장이 이미 커밋된 뒤라 되돌릴 방법이 없다. 같은 비교를 더 늦게 할 뿐이라 상위 호환이 아니다.
    • 409 이고 401 이 아니다. 로그인은 살아 있다(다른 계정으로). 401 로 /login 에 튕기면 멀쩡한 새 탭의 세션까지 끊는다. 일반 업무오류(WebException)도 409 라 프론트는 X-Session-Mismatch 헤더로 구분한다.
    • 에러로그(TB_CMS_ERROR_LOG)에 적재하지 않는다. 예외를 던지지 않고 필터에서 직접 응답 바디(ResponseErrorVo)를 쓴다 — 탭 두 개는 장애가 아니라 흔한 사용자 상황이다. 추적은 WARN [SESSION] 로그로 한다.
    • 헤더를 필수로 만들지 않았다. main push 마다 자동배포되는 구조라, 필수화하면 배포할 때마다 열려 있던 모든 탭이 전부 409 를 맞는다. 남는 구멍은 '캐시된 옛 번들' 하나이고 새로고침하면 닫힌다.

    프론트 짝(BroadcastChannel 로 옛 탭을 새로고침)은 프론트 인증 문서 참고.

    이건 신원이 어긋난 요청만 끊는다

    신원은 맞는데 봉투만 틀린 경우(CUST_CD/COMP_CD 를 클라이언트가 정한다)는 이 필터가 막지 못한다. 봉투를 세션에서 강제로 채우는 조치는 별건이다.

    ★인가가 없다 — 공통 프로시저 관문¶

    SecurityFilterChain 은 인증만 건다 (WebSecurityConfiguration.java:42-49).

    authorize.requestMatchers( "/**" ).authenticated();   // 이게 전부다

    메서드 레벨 권한 애노테이션(@PreAuthorize·@Secured·@RolesAllowed)은 전 소스에 0건이고, 메뉴 권한을 API 에서 검사하는 곳도 없다.

    그래서 공통 프로시저 관문은 로그인만 되어 있으면 어떤 PACKAGE.PROCEDURE 든 실행한다.

    POST /api/vendor/comm/executeVendorCommonProcedure
  { "DATASET": [ { "PACKAGE": "...", "PROCEDURE": "...", "PARAM": {...} } ], ... }

    화면에 메뉴가 없는 것은 방어가 아니다

    menuAuthGuard 는 프론트 라우터 검사다. 백엔드에 대응물이 없다. 협력사 역할에 승인 화면 메뉴가 없어도, 자기 화면의 요청을 복사해 파라미터 하나만 바꾸면 승인자 전용 분기가 그대로 실행된다. 실측: 협력사 계정이 봉투를 위조조차 하지 않고 APP_YN='Y' 만 추가해 111개 회사 18,558건을 받았다(Infra #51).

    ⚠️이 관문은 CRS 외에 TES/FDS/EIR/CFS 도 함께 쓴다.

    파라미터 신뢰 모델¶

    프로시저를 새로 만들거나 고칠 때 반드시 이 표를 기준으로 판단한다.

    파라미터 출처 신뢰
    p_user_id VmsCommonController 가 세션에서 덮어쓴다 ✅ 유일하게 신뢰 가능
    p_comp_cd · p_cust_cd · p_corp_cd · p_company_cd 클라이언트 JSON 본문 ❌ 위조 가능
    업무 키(p_estimate_no, p_eq_no, 입력커서 행 …) 클라이언트 ❌ 위조 가능

    ⚠️getCorpCdCurr() 는 클라이언트가 보낸 CORP_CD 가 있으면 그걸 쓰고 비었을 때만 세션값으로 채운다 — CORP_CD 도 신뢰 대상이 아니다.

    ⇒ p_cust_cd 로만 거르는 프로시저는 방어가 없는 것과 같다. 소유 판정은 p_user_id 를 통해야 한다.

    견적 소유 판정 (PKG_CRS_ESTIMATE)¶

    위 신뢰 모델에 따라 CRS 견적 패키지에 소유 게이트를 넣었다(2026-09-23, Infra #51). 전수 감사에서 24개 프로시저 중 20개에 소유 검증이 없었다.

    판정자 3개¶

    패키지 스펙에 선언되어 있다 ⇒ 패키지 밖에서도, SQL 문 안에서도 호출할 수 있다(MyBatis 매퍼에서 SELECT ... FROM DUAL 로 부르는 용법 포함).

    fn_is_approver     (p_user_id)                            -- 승인자인가
fn_can_access_cust (p_user_id, p_comp_cd, p_cust_cd)      -- 본인 매핑 OR 승인자
fn_can_access_est  (p_user_id, p_comp_cd, p_estimate_no)  -- 승인자 OR 견적 company_cd 소유
    • 승인자 = 역할 CRS02 이고 TB_CMS_USER.CORP_CD <> 'REPAIR'. REPAIR 는 모든 수리 협력사가 공유하는 법인이라 법인만으로는 권한 경계가 되지 않는다.
    • 소유는 접두어(estimate_no like cust_cd||'%')가 아니라 견적의 실제 company_cd 로 판정한다 — 거래처코드가 다른 코드의 접두어가 되는 경우를 피한다.
    • 견적이 존재하지 않으면 'N' 이다(고아·미존재 = 차단). 신규 생성 경로에는 fn_can_access_est 가 아니라 fn_can_access_cust 를 쓴다.
    • p_comp_cd 가 어느 스키마(liner/hliner/hsl)를 볼지 고르는 스위치다. 셋 중 하나가 아니면 'N'.
    • 승인자는 모든 게이트를 통과한다.

    ★p_comp_cd 가 불량이면 협력사만 조용히 막힌다 — 승인자는 통과한다

    승인자 분기가 선사 스위치보다 앞에 있어서 생기는 비대칭이다.

    FN_CAN_ACCESS_EST('TSN01' , NULL  , 'TSN01…') → N
FN_CAN_ACCESS_EST('TSN01' , 'HALk', 'TSN01…') → N   -- 오타
FN_CAN_ACCESS_EST('TSN01' , 'SNKO', 'TSN01…') → Y
FN_CAN_ACCESS_EST('pcfinc', NULL  , 'TSN01…') → Y   ← ★승인자는 통과

    증상이 "특정 협력사만 데이터가 안 보이는데 관리자가 보면 정상" 으로 나타난다. 에러도 로그도 남지 않는다.

    포털 경로는 p_comp_cd 가 ui.activeCompany(SNKO/HALK/HSLI) 라 이 상황이 생기지 않는다. 문제는 p_comp_cd 를 테이블 컬럼에서 꺼내 쓰는 호출부다 — 예컨대 TB_CMS_ATFILE.COMP_CD 에는 .100 스냅샷 기준 NULL 2,203행과 대소문자 오타(HALk) 1행이 있었다(Infra #55 실측).

    ⇒ 컬럼값을 p_comp_cd 로 넘기는 호출부는 배포 전에 불량값 0건을 확인할 것.

    두 판정자의 가드 순서가 다르다 — 의도적으로 읽을 것¶

    p_* 가 뜻하는 것 승인자 검사 위치 NULL 일 때
    fn_can_access_est p_estimate_no = 읽을 대상 NULL 가드 뒤 승인자면 'Y'
    fn_can_access_cust p_cust_cd = 기록될 회사 NULL 가드 앞 승인자라도 'N'

    fn_can_access_cust 를 쓰는 곳(sp_set_Est · sp_set_est4exl · _new)에서 p_cust_cd 는 판정 대상이 아니라 company_cd 로 기록되는 값이다. NULL 을 통과시키면 company_cd = NULL 인 견적이 생긴다. 그래서 승인자라도 끊는다.

    ⇒ 새 게이트를 달 때 "그 파라미터가 읽을 대상인가, 기록될 값인가" 로 가드 순서를 정한다.

    ℹ️승인자 pcfinc 의 메뉴에는 CrsEstimate·CrsEstUploadExl 이 없어 위 세 프로시저에 UI 로 도달하지 않는다(2026-09-23 menuMap 실측 8개).

    거절을 어떻게 알리나 — 백엔드 계약¶

    VmsCommonService 는 프로시저의 OUT VARCHAR2 가 1개면 그것을 resultCd 로 읽는다.

    resultCd 백엔드 처리 결과
    'N' errorMessage(retMsgs) → WebControllerException 409 · ERR_DIV '01' · 사용자에게 메시지 노출 ✅ 업무거절
    'E' ProcedureException 500 · "오류가 발생하였습니다" 로 뭉개짐 · 에러로그에 시스템 에러로 적재 ❌

    사유 메시지는 P_RS_ERR 커서에서, 없으면 첫 번째 OUT 커서에서 읽는다. ★컬럼명은 반드시 MSG 다 — joinCursorMsg 가 row.getString("MSG") 로 읽는다.

    인가 거절에 raise_application_error 를 쓰지 말 것

    시스템 에러로 분류돼 500 + 범용 문구가 되고, 사용자는 왜 막혔는지 알 수 없다. OUT VARCHAR2 가 없는 프로시저는 빈 커서 또는 MSG 커서로 돌려보낸다. ★거절 경로에서도 OUT 커서를 하나도 빠짐없이 열어야 한다 — 안 열면 백엔드가 커서를 소비하다 깨진다.

    패키지 함수를 늘릴 때 — 컴파일 함정 둘¶

    PLS-00307(선언이 너무 많다) — 스펙 선언과 바디 정의의 헤더가 파라미터 이름·타입·기본값까지 정확히 일치해야 한다. 어긋나면 Oracle 이 짝을 못 지어 별개의 두 서브프로그램이 되고, 호출이 모호해진다. 실제로 겪었다.

    PLS-00231(SQL 문에서 못 부른다) — 스펙에 없는 body-private 함수는 SELECT/UPDATE/open ... for select 안에서 호출할 수 없다. if 조건·대입 같은 PL/SQL 절차문에서는 된다. 위 판정자 3개는 스펙에 있으므로 이 제약을 받지 않는다. 다만 sp_get_Est 는 함수가 body-private 이던 시점에 작성돼, 선언부에서 v_is_approver 로 한 번 계산해 WHERE 에 변수로 넘긴다 — 지금은 불필요하지만 무해하고, 전량 스캔 쿼리라 행마다 함수를 호출하지 않는다는 이점이 남는다.

    왜 12개만 막았나 — 나머지 8개는 검토 후 제외했다¶

    감사에서 20개가 걸렸는데 게이트는 12개다. 빠진 8개는 잊은 게 아니라 판단해서 뺀 것이다.

    프로시저 노출되는 것 제외 사유
    sp_get_Comp_Info 거래처 마스터(업체명·연락처·공임단가) 유일하게 실질적. 다만 p_user_id 추가 = 스펙 변경이 필요해 이득 대비 위험이 크다
    sp_get_Eq_No 컨테이너 B/L 조회 정상 업무가 "아직 내 견적이 없는 컨테이너를 쳐서 B/L 을 끌어오는 것" 이라 소유 축소 = 기능 삭제. 대상 테이블에 소유 컬럼도 없다
    sp_match_file2est 그 기간 그 컨테이너의 견적 존재 여부 읽기 전용이다. 쓰기는 전부 세션 임시테이블(tmp_crs_matchfile2est, user_id 로 자기 행만)
    sp_get_Est4Cleaning 아직 견적이 없는 컨테이너 후보 not exists (… est_mst …) 조건이라 견적이 아니다
    sp_get_New_Est · sp_get_Est_No 다음 채번 번호 번호뿐
    sp_get_disabled_ext 그 관리번호에 뷰어 불가 확장자가 있나 file_fext 9종 중 무엇이 있나. 그뿐
    sf_get_waive_status 면제 상태 함수라 관문으로 호출 불가. sp_get_Est SELECT 목록에서 행마다 불려 게이트를 달면 전량 스캔이 함수 호출 폭탄이 된다

    ⇒ 견적 자체(조회·상세·리포트·저장·삭제·승인·REMARK)에 대한 접근은 12개로 전부 닫혔다. 남은 8개는 견적이 아니라 주변 데이터다.

    이 게이트가 막지 못하는 것¶

    • 다른 시스템이 liner.t_oceq_repair_est_* 에 직접 쓰거나 liner.dpk_repairnew.* 를 직접 호출하는 경로 — 의도된 범위 밖이다.
    • 자기 매핑에 정식 등록된 거래처 간 접근. TB_CMS_USER_CORP_MGT 가 곧 권한이다.

    공개 URL (permit-all)¶

    공개 경로는 Java config가 아니라 application.yaml의 security.request-permit-all-mappings에 method별로 선언한다. SecurityFilterChain이 이를 순회하며 permitAll()을 등록하고, 나머지 /**는 authenticated로 묶는다 (WebSecurityConfiguration.java:42-49).

    Method 공개 URL 패턴
    GET /login, /jsp/**, /application/health(+/readiness·/liveness — ACA 프로브, 인증 없이 200), /api/partner/**
    POST /api/login, /api/auth/**, /api/file/getBase64ImageList, /api/code/selectCorpCode, /api/partner/**

    별도로 정적 리소스는 WebSecurityCustomizer로 시큐리티 필터에서 완전 제외된다 — 정규식 ^/.+[.](?:html|js|css|ico|png|jpg|jpeg|gif|font|woff|woff2)$ (WebSecurityConfiguration.java:33-36).

    파일 API 공개 범위 축소 (2026-09-04, PR #122)

    종전엔 /api/file/** 전체가 GET·POST 로 열려 있어 그 아래 9개 엔드포인트가 모두 무인증이었다. 실제로 무인증이 필요한 것은 외부 사이트가 링크로 여는 수리 이미지 뷰어(CmsImageCarouselPopup)가 호출하는 getBase64ImageList 하나뿐이라 그것만 남기고 닫았다. 함께 닫힌 것 중 핵심은 selectFileList+downloadFileNas 조합(관리번호만 알면 첨부 목록을 열거해 원본 파일을 받아갈 수 있었다)과 uploadFile/deleteFile(s)(컨트롤러 첫 줄 getSession() 의 ClassCastException 으로 "우연히" 막혀 있었을 뿐 접근제어가 아니었다)이다. GET 목록에서 /api/file/** 를 되살리지 않은 이유는 해당 매핑이 전부 @PostMapping 이라 GET 허용이 처음부터 무의미하기 때문이다. 같은 PR 에서 /api/crs/repair/disabledFileExtList 는 엔드포인트째 제거(사용처 0).

    /api/eir/** 공개 해제 (2026-09-11) — Infra #17 종결

    신규 EIR 발급 테스트용 임시 공개("테스트 이후 삭제" 주석)를 PoC 종료로 닫았다. GET·POST permit-all 2줄 제거 → 세션 인증 복귀.

    닫기 전 실제 노출(정리가 아니라 구멍이었다): POST /api/eir/issueEirNew·cancelEirNew 는 세션을 쓰지 않고 본문의 USER_ID/COMP_CD 를 그대로 신뢰해, 무인증 호출자가 실제 EIR 을 SIPG 에 발급·취소하고 남의 ID 로 로그를 남길 수 있었다. GET /api/eir/getValidToken 은 살아있는 SIPG 토큰을 세션 검사 없이 반환했다. getCachedToken 은 getSession() 의 ClassCastException 으로 "우연히" 막혀 있었을 뿐 접근제어가 아니다(uploadFile 과 같은 패턴). /test/** 와 달리 이 경로는 nginx 가 /api/ 를 백엔드로 넘기므로 인터넷에서 실제로 도달 가능했다.

    안전성 근거: 7일치 액세스로그의 /api/eir/** Referer 는 전부 V2 화면(EirExportIssue 2,295 · EirImportIssue 469 · EirResponseLog 3)이고 외부 호출자는 0건이었다. 외부 사이트가 쓰는 EIR 취소는 /api/partner/cancelEir(PartnerController)라 이 변경과 무관하며 계속 열려 있다.

    함께 처리: ①issueEirNew·cancelEirNew·getEirInfo 의 주체를 getSession().getUserId() 로 전환(서버 권위 — 화면은 원래도 세션 사용자를 보내므로 동작 변화 없음). ②사용처 0인 GET /api/eir/getValidToken 엔드포인트 제거(토큰 반환 표면 소멸). getCachedToken 은 EirResponseLog 가 실제로 사용하므로 존치.

    /test/** 공개 해제 (2026-09-07)

    TestController(/test/autono·/test/sendMail·/test/upperSnakeCase)가 GET·POST 양쪽에 무인증으로 열려 있었다. 그중 GET /test/autono 는 @Transactional 로 채번을 실제 수행하는 쓰기 엔드포인트다.

    실제 도달 가능성은 없었다 — 프론트 nginx 가 백엔드로 넘기는 접두는 /api/ 뿐이고(그 밖은 SPA try_files 폴백), 백엔드 ingress 는 external=false 라 다른 입구가 없다. 운영 로그의 /test/swagger·/test/openapi 200 은 스캐너 탐색이 SPA 폴백(index.html)을 받은 것이지 백엔드 응답이 아니다.

    그래도 permit-all 은 "이 경로는 인증 없이 열어도 된다"는 선언이라, nginx 에 /test 프록시가 하나 추가되거나 백엔드가 직노출되는 순간 무인증 쓰기 엔드포인트가 된다. 도달 불가에 기대는 방어를 지우고 선언 자체를 없앴다. 엔드포인트는 로컬 개발용으로 존치(이제 세션 필요).

    네트워크 레벨 노출 (2026-08-19 하드닝)

    위 permit-all 은 애플리케이션 인증 레벨이다. 그와 별개로 네트워크 레벨에서 백엔드 Container App 은 external=false(internal ingress)로, 인터넷에서 백엔드 FQDN 직호출이 불가하다 — 오직 프론트 nginx(/api 프록시) 경유로만 도달한다. 따라서 permit-all 경로(/api/partner/** 등)도 프론트를 거쳐야 하며, 프론트 정문엔 limit_req(IP당 rate limit)가 걸려 있고, 파트너 API 호출은 호출자 IP 가 TB_CMS_API_LOG.CALL_IP 에 기록된다(X-Forwarded-For 체인, PR #78 — 조회 SP 측 출력 포함·CmsApiLog 화면에서 확인). 상세: migration-pitfalls §3.4.

    다만 /api/partner/** 와 POST /api/file/getBase64ImageList 는 외부 사이트가 링크로 직접 여는 경로라 무인증을 유지해야 한다(컷오버 후 partner.sinokor.co.kr 이 V2 를 가리키면 그 링크가 여기로 온다). 따라서 이 둘은 네트워크 레벨 차단의 예외가 아니라 의도된 공개이며, 관리번호 추측에 대한 방어는 별도 과제다 — 추적: Infra 이슈 #20.
