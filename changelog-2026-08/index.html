    2026-08 변경 이력¶

    dsh 도메인 신설 — 홈 대시보드 달력 개인 메모 API (PR #111, 프론트 #157 과 한 쌍)¶

    UserDashBoard 달력의 개인 메모를 담당하는 15번째 도메인. HomeController/HomeService/HomeDao + 매퍼 4파일 전부 신규이고 기존 파일 수정은 0이다. ★"복구"가 아니라 신설이다 — 프론트에는 fnSelectMemo/fnSaveMemo 와 EScheduler 배선이 이미 다 있었는데 그것들이 부르는 /api/dsh/Home/* 는 V2 에도 레거시에도 존재한 적이 없다(레거시 프론트도 mounted() 의 호출이 똑같이 주석). 즉 이 기능은 어느 쪽에서도 한 번도 동작한 적이 없고 테이블만 남아 있었다. TB_CMS_USER_MEMO 가 이미 있고 컬럼이 프론트 기대와 정확히 일치해(운영 데이터 0건) DDL 없이 붙었다. 경로가 도메인 규칙이 아닌 Home 인 것은 프론트를 고치지 않으려고 기존 호출 계약에 맞춘 것이다. ★MEMO_SN 은 테이블에 시퀀스도 PK 도 없어 사용자별 MAX+1 로 채번하므로 사용자 안에서만 유일하다 — 수정·삭제는 반드시 (USER_ID, MEMO_SN) 두 컬럼으로 걸어야 한다. USER_ID/CORP_CD 는 요청 본문이 아니라 세션에서 채운다(남의 메모 조회·수정 차단). 프론트와 동시 배포 필요(백엔드가 늦으면 404 지만 quiet:true+.catch 라 달력만 빈 채로 뜬다). 상세: dsh 코드 워크스루.

    문서 — 날짜 인자·커서 컬럼 자동 절단(setDateColumn) 함정 명문화¶

    VmsCommonService 가 IN 파라미터·IN 커서 컬럼을 이름 접미사만 보고 자른다는 사실(_DT8/_DI12/_DM6/_DY4, value.replaceAll("[-T:]","").substring(0,N), 길이검사 없음)이 문서 어디에도 없었다. 자릿수 미달이면 StringIndexOutOfBoundsException 500(운영 에러로그 실측 18건, 2025-07-16~2026-01-21), /·. 구분자는 예외 없이 2026/08/ 로 조용히 썩는다. VSL_DT 만 equals 예외이며 TES 커서가 여기에 yyyyMMddHHmm 12자를 의도적으로 실으므로 규칙을 endsWith("_DT") 로 넓히면 예외 없이 시각이 사라진다. 백엔드는 미수정이고 프론트가 전송 직전 관문에서 막았으므로(FE PR #158) 프론트를 거치지 않는 호출은 여전히 500 이 난다. → vps 코드 워크스루 §2-3.

    SIPG 통신 실패를 502 + 전용 문구(MSG000430)로 구분 응답 (PR #109)¶

    SIPG ESB 연결 불가/타임아웃(HttpHostConnectException 등)이 범용 500("시스템에 장애가 발생 하였습니다")으로 응답돼 포털 장애로 오인되던 문제. ExternalServiceException + 전용 번역기 신설 — EirService 의 SIPG HTTP 호출 4곳(getTokenNew/checkTokenValidate/sendSIPGNew/getEirInfoFromSIPG) execute 실패 catch 에서 IOException 만 래핑 → 502 Bad Gateway + MSG000430("SIPG 서버 오류로 통신할 수 없습니다. 잠시 후 다시 시도해 주세요…"). unknown=true 유지(프론트 모달 자동 표시)·ERR_DIV 02 기록 유지, 5xx 유지라 외부 의존성 다운 경보(vp-prod-fe-http-5xx 류)는 계속 발화(의도). 검증=도달불가 URL 로 connect timeout 30s → 502+실문구(ko), 원복 후 실토큰 발급 200 무회귀. 레거시에도 동일 반영(사용자 커밋). 상세: eir 코드 워크스루.

    업로드 중 클라이언트 회선 절단을 500 대신 400 + 전용 문구(MSG000429)로 (PR #108)¶

    운영 사례(2026-08-26): 사용자가 파일 업로드 중 회선이 끊기면 멀티파트 수신 실패(MultipartException)가 범용 500("오류가 발생하였습니다")으로 응답돼, 서버 잘못이 아닌 이벤트가 5xx 메트릭 경보(Sev2)를 울리고 사용자 문구도 무정보였다(실측: 2초간 500 14건 — HTTP/2 한 커넥션에 다중화된 병렬 업로드가 절단 시 전멸하는 구조; 전부 컨트롤러 도달 전 사망이라 DB/FTP 잔재 0, 동일 사용자가 1분 내 재시도해 14건 전부 성공). ClientAbortExceptionTranslator 신설 — MultipartException(용량 초과 MaxUploadSizeExceededException 은 제외)·ClientAbortException → 400 + MSG000429("네트워크 문제로 저장/업로드가 중단되었습니다…"). unknown=true·ERR_DIV 02 유지. ★ClientAbortException 은 IOException 계열이라 IOExceptionTranslator 보다 먼저 등록해야 한다.

    SSO 유입도 로그인 로그에 적재 — 레거시→V2 전환 사용자 집계 누락 해소 (PR #106)¶

    JwtAuthenticationFilter 에 성공 핸들러가 배선돼 있지 않아, 레거시에서 USER_DIV='V2' 사용자가 SSO(/api/link?token=)로 무비번 유입되면 TB_CMS_LOGIN_LOG 에 아무 기록도 남지 않았다. 그 결과 LOGIN_MSG='Login at V2' 건수가 "V2 URL 로 직접 로그인한 사용자"만 세어 실제 V2 접속자가 과소집계됐다(운영 실측: 레거시 로그인 다수에 대응하는 V2 행이 없음). 필터가 SSO 전환 성공 시 LoginSuccessService.loginSuccess() 를 직접 호출하도록 수정. ★LoginAuthenticationSuccessHandler 를 배선하지 않은 이유 = 그 핸들러가 200 응답 바디를 써서 /api/link 의 sendRedirect 를 깨뜨린다(SSO 자동로그인 실패). 세션 재사용(프로바이더가 기존 인증 객체를 그대로 반환하는 경로)은 새 로그인이 아니라 인증 전후 객체 참조 비교로 제외했고, 파트너 API 의 stateless JWT 는 JwtUserAuthentication 이라 instanceof LoginUserAuthentication 에서 걸러진다(안 그러면 API 호출마다 로그인 로그가 쌓인다). 적재 실패는 catch 해 SSO 자체를 막지 않는다(레거시 v2SsoLink 와 동일한 fail-open). SSO 와 직접 로그인을 구분하는 마커는 두지 않았다(목적이 "V2 접속자 파악") — 레거시 잔류 사용자는 레거시 행(LOGIN_MSG IS NULL)으로 센다. 부수효과: SSO 유입 시에도 initPasswordFailCount 가 돌아 LOGIN_FAIL_CNT 가 초기화된다(정상 인증이므로 타당). 로컬 실측: SSO 토큰(jti=SSO) 왕복으로 302 리다이렉트 유지 + S01/Login at V2 1건 적재, 동일 세션 재유입 시 추가 적재 없음 확인.

    로그인 실패 사유 세분화 — LOGIN_DIV E02 → E02~E05 + 사용자 안내 문구 분리 (PR #105)¶

    종전 loginFailure 는 비밀번호 오류만 E01 로 가르고 나머지 전부를 E02("사용자 권한 오류")로 뭉뚱그려, 로그만 봐서는 원인을 알 수 없었다(실측: 과거 E02 7,264건 중 2,616건은 계정이 실제 존재하는 행). 사유별로 코드를 나눈다 — E02 계정 없음 / E03 비활성(USE_YN='N') / E04 5회 실패 잠금 / E05 유효기간 만료. 함께 계정없음과 비활성의 사용자 문구도 분리했다(종전엔 둘 다 "User information corresponding to the ID does not exist or is disabled." 하나 → 각각 "The user ID does not exist." / "This account is disabled. Please contact the administrator."). 유효기간 만료 문구도 한글 → 영문("The account validity period has expired. Please contact the administrator.")으로 통일했다(로그인 실패 계열은 -25.02.07 부터 무조건 영문 출력 관행). 구현은 사용자 응답을 건드리지 않는 방식을 택했다: 사유 코드를 LoginFailureReasonException(순수 RuntimeException)에 실어 cause 체인으로 전달하고 loginFailure 가 꺼낸다 — provider 가 InternalAuthenticationServiceException 으로 감싸므로 상태코드(401)·type·errDiv 가 그대로다. E04 는 LoginAuthenticationException 타입만으로 확정(getPreChecker 가 던지는 유일한 타입). 계정없음/비활성 판별용으로 USE_YN 필터 없는 selectUserUseYn 을 신설했다(selectUser 의 USE_YN='Y' 필터는 제거하면 비활성 계정이 로그인에 통과하므로 그대로 두고, 아이디/비밀번호 찾기가 공유하는 selectUserByUserId 도 건드리지 않음). 분류 실패 시 기존 E02 로 폴백 — loginFailure 에서 예외가 새면 인증 필터 밖으로 전파돼 401 대신 Tomcat 기본 500 이 나가기 때문이다. 로컬(.100) 실측으로 E01·E02·E03·E04 4케이스의 HTTP 401·문구·LOGIN_DIV 기록을 확인했다(E05 는 .100 에 만료 계정이 없어 미실측, E02/E03 와 동일 경로). 코드마스터 TB_CMS_CD_DTL(MSTR_CD='LOGIN_DIV') 에 E03~E05 등록이 별도로 필요하다(미등록 시 CmsLoginLog 화면에 raw 코드 표시·검색 콤보 누락 — 화면 코드 수정은 불필요). 레거시에도 동일 반영(사용자 커밋).

    백엔드 Container App 을 external=false(internal ingress)로 돌려 인터넷에서 백엔드 FQDN 직호출을 차단했다(오직 프론트 nginx /api 프록시 경유만 도달). 2026-06-23 에 internal 전환이 "App Unavailable" 404 로 막혔던 진짜 원인은 nginx resolver=168.63.129.16(Azure 공용 DNS)이 .internal FQDN 을 공용 인그레스로 오해석한 것 — 프론트 부트스크립트(docker-entrypoint.d/15-set-resolver.envsh)가 resolver 를 컨테이너 DNS(/etc/resolv.conf, ACA=127.0.0.11→클러스터 DNS)로 덮어써 해결(FE #117/#118, --chmod 는 az acr build BuildKit 미사용이라 RUN chmod 로). 짝으로 프론트 /api 에 limit_req(IP당 rate limit, 키=X-Forwarded-For) 추가 — 정문 flood 완화. 선행 실측 작업으로 파트너 API 호출자 IP 를 TB_CMS_API_LOG.CALL_IP 에 기록(백 #78, getClientIp()=X-Forwarded-For 체인; CmsApiLog 화면 IP 컬럼=프론트 #116; 조회 SP 측 CALL_IP 출력 컬럼 추가는 DB 작업으로 완료). 외부 호출(EBIZ 다운로드/취소)은 전부 partner.sinokor.co.kr 도메인 경유라 백엔드 잠금과 무관 확인. 상세: migration-pitfalls §3.4·보안·인증.

    TES 엑셀 업로드 검증 4종 완성 + 공통화 (PR #77, 프론트 #113)¶

    VmsExcelChkFacade 의 강취료/결해속비/예선료 검증 스텁(uploadChkTesLineHandleExpn/uploadChkTesLashingExpn/uploadChkTesTugExpn)을 구현하고, 검수료(uploadChkTesInspExpn)에만 있던 VSL·PORT·WHARF 대조를 공통 chkVslPortWharf 로 추출해 4종이 공유한다(4종 모두 붙여넣기 그리드에 VSL/PORT/WHARF 컬럼 보유). 공통화하며 로직도 개선: ① 마스터를 값 Set 으로 1회 구축해 행당 O(1) 대조(종전 행마다 마스터 전체 × 전 컬럼 선형 스캔), WHARF 는 SPORT 별 그룹 Map ② 첫 불일치에서 중단하지 않고 항목별 오류 라인을 모아 한 번에 보고(앞 10개 + "외 N건", 수정→재업로드 왕복 축소; PORT 불일치 행은 WHARF 검사 생략) ③ 양쪽 trim+대문자 정규화(엑셀 붙여넣기의 뒤 공백·소문자 거짓 실패 흡수) ④ 판정 범위는 종전 containsValue 와 동일(마스터 행의 아무 컬럼 값 일치 시 통과) 보존, 고아가 된 checkValueExists 제거. 프론트 짝(PR #113): 4개 화면 $axios.post→$post 전환으로 COMP_CD(activeCompany) 자동 주입 — 종전엔 COMP_CD 부재로 항상 LINER(SNKO) 스키마 기준 검증되던 것이 현재 선택 선사 기준으로 정확해짐 + 예선료 팝업 TYPE:'INSP_EXPN'(검수료) 오배선을 'TUG_EXPN' 으로 정정(정정 전엔 신설 예선료 분기를 타지 않음).

    공통팝업 선사 스키마 키 CORP_CD → COMP_CD 통일 (PR #76, 프론트 #112)¶

    CmsCommonPopup 계층에서 선사(SNKO→LINER·HALK→HLINER·HSLI→HSL 스키마) 지정 키를 COMP_CD 로 통일했다(정석 규칙: COMP_CD=조회 대상 선사·스키마 결정자 / CORP_CD=유저 소속법인 — 그간 선사가 CORP_CD 키에 실려 두 뜻이 과적재). 컨트롤러 top-level 승격 SEARCH.CORP_CD→SEARCH.COMP_CD, 서비스 스키마 switch 키 CORP_CD→COMP_CD(Port/Vessel/Location/CntrType/Currency/CurrencyNation/CustomerCode/RepairCompany), 매퍼 ${CORP_DIV}→${COMP_DIV}. 프론트 공통팝업이 조회 시 COMP_CD=activeCompany 를 항상 실어 보내므로 기본 동작 동일, activeCompany 외 선사는 코드박스 :params="{COMP_CD}" 로 명시(프론트 CmsCommonPopup 이 PARAM.COMP_CD 우선 — PR #112 와 한 쌍). 기존 :params CORP_CD 사용처 전수조사 결과 값이 전부 activeCompany 라 결과 무변, 예외였던 AmendPopup(인보이스행 선사 명시)은 미사용 확인. 아래 #72 항목의 CORP_CD 승격·${CORP_DIV} 서술은 이 PR 로 COMP_CD/${COMP_DIV} 가 됐다.

    VMS 공통 프로시저 실패 사유를 P_RS_ERR 커서에서 읽도록 수정 (PR #75)¶

    프로시저가 p_rs_cd='E' 로 실패해도 화면엔 구체 사유가 안 보이던 문제. executeVmsCommonProcedure 경로가 실패 시 P_RS_ERR OUT 커서의 메시지를 응답에 실어 프론트 경고창에 실제 실패 사유가 표시된다.

    CmsUserMgt 거래처 코드박스 REPAIR용 selectRepairCompany 팝업 엔드포인트 (PR #72·후속 정정 #73, 프론트 #106)¶

    사용자관리 corp 탭 CUST_CD 코드박스를 회사구분(CORP_CD)에 따라 분기 — REPAIR 는 신설 selectRepairCompany, 그 외는 기존 selectCustomerCode 를 호출한다. selectLocation4Feeder/selectCustomerCode 패턴을 그대로 따른다: 컨트롤러가 {SEARCH:{...}} 안의 CORP_CD(프론트가 해당 corp row 의 CORP_CD 전달)를 top-level 로 올리고, 서비스가 그 값으로 회사별 스키마를 스위치(SNKO→LINER·HALK→HLINER·HSLI→HSL 의 .T_OCEQ_REPAIR_COMPANY, default=LINER — DMap.getString 이 미존재 키에 "" 를 반환하므로 회사코드 없이 호출돼도 default 로 안전), 매퍼는 FROM ${CORP_DIV} 로 COMPANY_CD→CODE·COM_NAME→NAME 조회(SEARCH_KEYWORD LIKE). 프론트 코드박스(RepairCompany/CustomerCode 분기)와 한 쌍(PR #106).

    CI: azure/login @v2 → @v3 (PR #74, 프론트 #108)¶

    GitHub hosted 러너의 Node 24 강제 전환으로 v2 액션의 OIDC 로그인이 깨져 배포가 실패하던 것을 v3 로 올려 해결.

    EIR 발급/취소 이중 발급 방지 — Redis 분산락 + 비멱등 전송 하드닝 (PR #71)¶

    한 번의 전송 클릭이 두 요청으로 갈라져 서로 다른 ACA 레플리카(minReplicas=2)에서 각각 처리되어 같은 B/L 에 EIR 2건 발급 + TB_EIR_RESPONSE_LOG 2행 + SIPG receiptNo 2개가 생기던 문제. 다중 인스턴스라 인스턴스 메모리 가드로는 못 막아 Redis 분산락(tryIssueLock/releaseIssueLock, 키 lock:eir:issue:{COMP}:{BL}:{CNTR}:{SEND}, TTL 60s)으로 차단하고 부수 결함도 함께 수정: SIPG 타임아웃 명시(RequestConfig, 조회 30s/전송 120s — 미설정 시 무한 대기), sendSIPGNew disableAutomaticRetries(비멱등 요청 조용한 재전송 차단) + execute() 실패 시 httpClient.close()로 커넥션 누수 차단(단 sendSIPGNew 는 예외를 흡수하지 않고 rethrow — 흡수 시 RESPONSEFIELD 가 비어 컨트롤러가 락을 풀면 이중 발급 위험), insertEirLog 에 CNTR_NO/IMEX 적재(그간 NULL), updateEirInfo 가 토큰을 파라미터로 받아 컨테이너마다 토큰 재검증 왕복 제거. 컨트롤러는 락 실패 시 [DUPLICATE] 건너뜀 · SIPG 전송 前 예외만 락 해제(전송 후 예외는 도달 불명이라 유지) · 취소 성공 시 발급락도 해제. 레거시(sinokor-backend) 커밋 이식이며 vp 패키지·@Value 시크릿 외부화·jakarta import 보존, 프론트 재진입 가드와 한 쌍(프론트 PR #102). 상세: 마이그레이션 함정 §4.5.
