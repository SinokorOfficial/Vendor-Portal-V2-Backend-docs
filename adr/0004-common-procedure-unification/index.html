    ADR-0004 · 공통 프로시저 호출 통합 (executeVmsCommonProcedure)¶

    • 상태: 채택
    • 맥락: 공통 프로시저 실행은 selectVmsCommonProcedure(조회)와 saveVmsCommonProcedure(저장) 두 메서드로 나뉘어 있었고, 화면은 조회/저장에 따라 /selectVendorCommonProcedure · /saveVendorCommonProcedure 엔드포인트를 골라 호출했다. 그러나 둘 다 "화면이 보낸 패키지/프로시저 메타로 Oracle 프로시저를 동적 실행"하는 동일 골격이며, 실제 차이는 몇 가지로 좁혀진다.
      • 조회는 CALL PKG.PROC(...), 저장은 DECLARE ... BEGIN ... END; 익명 블록(그리드 다건을 SYS_REFCURSOR IN 커서로 구성) — 익명 블록이 상위집합(IN 커서 0개도 표현 가능).
      • 저장만 @Transactional, 조회는 비트랜잭션.
      • OUT 커서 지원 범위가 달랐다 — 조회 1~20, 저장 1~5.
      • saveVmsCommonProcedure 의 resultCd(N/E) 오류 검사는 실제 호출 이전에 배치돼 있어 동작하지 않는 死코드였다.

    결정¶

    두 경로의 상위집합인 executeVmsCommonProcedure 와 전용 엔드포인트 POST /api/vendor/comm/executeVendorCommonProcedure 를 신설한다(VmsCommonService.java:577, VmsCommonController.java:60, VmsCommonDao.java:57).

    • 단일 통합 매퍼 — 익명 PL/SQL 블록 하나로 조회/저장을 모두 표현한다(VmsCommon-mapper.xml의 executeVmsCommonProcedure). IN 커서가 있을 때만 DECLARE, OUT VARCHAR가 1개면 resultCd·여러 개면 ARR_OUT_PARAM, OUT 커서는 OUT_CURSOR_COUNT 로 1~20을 <if> 동적 결정.
    • @Transactional — 상위집합으로 항상 트랜잭션. 조회는 무해(빈 커밋), 저장은 원자성 보장.
    • IN 커서 항상 처리 — 없으면 생략, 있으면 저장 방식으로 동적 커서 쿼리 구성.
    • OUT 커서 슬롯마다 개별 resultMap(retExec1~retExec20) — 하나를 공유하면 MyBatis auto-mapping 캐시(resultMap id 기준)가 서로 다른 컬럼셋 커서에 잘못 재사용돼 ORA-17006(Invalid column name)이 난다. 레거시 select 매퍼가 커서마다 retMap11/retMap21… 을 따로 둔 이유가 이것.
    • resultCd(N/E) 검사는 호출 후로 이동 — 사유 메시지는 첫 OUT 커서(result1=P_RS)에서 읽는다(VmsCommonService.java:767). OUT 커서 0개는 기존 select/save 와 동일하게 no-op(:732).
    • 기존 select/save 메서드·매퍼는 존치 — 하위호환. 화면 전환만 점진 진행한다.

    프런트엔드는 EIR을 제외한 전 모듈(FDS·CRS·MVS·CFS·TES·CMS·MDM 등)의 select/saveVendorCommonProcedure 호출을 executeVendorCommonProcedure 로 전환했다.

    결과¶

    • ✅ 화면이 조회/저장을 구분하지 않고 단일 엔드포인트로 프로시저를 호출한다.
    • ✅ 저장도 OUT 커서 1~20을 지원(기존 save 는 1~5). 조회·저장 모두 다중 커서·다중 IN 커서를 동일 경로로 처리.
    • ✅ 실벤더/admin 계정 실데이터로 검증(예: CRS SP_GET_EST 30,316행, MVS SP_GET_STOCK 2,849행, CMS SP_GET_API_LOG 1,248행, TES SP_GET_SCHEDULE 다중커서) — ORA-17006 등 오류 0.
    • ⚠️ 저장 경로의 resultCd(N/E) 검사가 이제 실제로 동작한다(기존 save 는 死코드라 삼켰음). 다만 화면들은 결과/오류를 resultCd 가 아니라 P_RS/P_RS_ERR 커서로 처리하는 관례라 정상 흐름에 미치는 영향은 작다. N/E 는 사실상 하드 오류 신호다.
    • ⏭️ EIR은 미전환(의도적 제외). 기존 select/save 및 매퍼는 당분간 병존한다.
