    변경 이력¶

    개발자 문서·백엔드의 주요 변경을 기록한다. 상세 커밋은 git 로그를 참고.

    2026-09¶

    • CRS 견적에 소유 검증을 넣었다 — 24개 프로시저 중 20개에 없었다(Infra #51) — 전수 감사 결과 PKG_CRS_ESTIMATE 에 소유 모델이 사실상 없었다. 실측: 협력사 계정이 봉투를 위조조차 하지 않고 검색 파라미터 APP_YN='Y' 하나만 추가해 111개 회사 18,558건을 받았고, 견적번호만 알면 타사 견적 상세·견적서(업체명·공임단가·책임구분 8종 원가)가 열렸으며 sp_del_Est 는 남의 미승인 견적을 영구 삭제할 수 있었다. 조치: 판정자 3개(fn_is_approver/fn_can_access_cust/fn_can_access_est) 신설 + 12개 프로시저에 게이트. sp_get_Est_Rpt 는 호출자를 식별할 인자가 없어 p_cust_cd/p_user_id 를 추가했다(스펙 동시 변경). ★구조적 원인은 관문에 인가가 없다는 것 — @PreAuthorize 0건, 메뉴 권한 검사 0건이라 "화면에 메뉴가 없다"는 방어가 아니다(같은 관문을 TES/FDS/EIR/CFS 도 쓴다). ★승인자 = 역할 CRS02 이고 CORP_CD <> 'REPAIR'(REPAIR 는 협력사 공통 법인이라 법인만으로는 경계가 안 된다). ★거절은 resultCd='N' + MSG 커서(409, 사유 노출)로 한다 — raise_application_error 는 500 으로 뭉개진다. 상세: 보안·인증 문서 의 "인가가 없다" · "견적 소유 판정" 절.

    • 탭 신원 대조 — 세션과 다른 계정을 주장하는 요청을 409 로 끊는다(PR #174, FE #220) — SINOKORSESSION 은 탭이 아니라 브라우저 단위 쿠키다. 같은 브라우저에서 다른 계정으로 로그인하면 먼저 열려 있던 탭의 세션까지 덮어써지는데, 그 탭의 봉투(USER_ID/CORP_CD/COMP_CD/CUST_CD)는 옛 계정 그대로 남아 남의 데이터에 닿는다. 실측: TSN21 세션에 봉투만 CUST_CD=TSN01 로 바꿔 SP_GET_EST 호출 → 209,141건(전부 TSN01). 조치: 프론트가 매 요청에 X-Client-User(이 탭이 아는 계정)를 싣고 SessionIdentityGuardFilter(AuthorizationFilter 뒤)가 세션 userId 와 대조, 다르면 컨트롤러 진입 전 409 + X-Session-Mismatch. ★요청 검증이지 응답 검증이 아니다 — 응답 시점엔 저장이 이미 커밋된 뒤라 되돌릴 수 없다. ★헤더가 없으면 검사하지 않는다(옛 번들 캐시·파트너 JWT·외부 딥링크 하위호환) — 필수화하면 배포할 때마다 열려 있던 모든 탭이 409 를 맞는다. ★에러로그에 적재하지 않는다(탭 두 개는 장애가 아니다) — WARN [SESSION] 로만 남긴다. 상세: 보안·인증 문서 의 "탭 신원 대조" 절. 이건 신원이 어긋난 요청만 끊는다 — 봉투 값 자체를 세션에서 강제하는 건은 별건.

    • 파일 삭제 2곳의 USER_ID 위조 차단(PR #173, Infra #51) — FileDataController 의 deleteFile·deleteFiles 가 explMap.put("USER_ID", 세션) 뒤에 putAll(param) 을 해서, 클라이언트가 보낸 USER_ID 가 세션 값을 덮어썼다 — 삭제자를 위조할 수 있었다. uploadFile 은 BE #169 에서 같은 이유로 순서를 바꿨는데 삭제 경로 2곳이 빠져 있었다. 순서만 뒤집는다(putAll → put(USER_ID)). ⚠️MNGT_NO 소유 검증은 여전히 없다 — 이 수정은 '누가 지웠는지'를 믿을 수 있게 할 뿐, '남의 첨부를 지우는 것'은 못 막는다(별건).

    • 로그인 실패 로그에 IP 기록(PR #172, Infra #54) — TB_CMS_LOGIN_LOG 가 성공(S01)에만 IP 를 남기고 실패(E01~E05)에는 null 을 넣고 있었다. 보안상 출처가 가장 필요한 쪽이 실패인데 정확히 거기가 비어 있었다. ★실제로 대가를 치렀다 — 2026-06-05~12 운영에서 존재하지 않는 계정 ID 로 5,123건(123개 ID)의 시도가 있었는데 전부 IP 가 없어 출처를 지금도 모른다. 같은 기간 다수 계정 로그인이 성공했고, 성공 로그에만 IP 가 남은 탓에 뚫린 뒤에야 파악됐다. 원인은 loginFailure(Authentication, AuthenticationException) 시그니처에 HttpServletRequest 가 없는 것 — 이 메서드는 AuthenticationProvider(LoginUserDaoAuthenticationProvider:79) 안에서 불려 인자로 받을 수 없다. 인터페이스를 바꾸는 대신 RequestContextHolder 로 현재 요청을 꺼낸다(이 파일이 buildRequestSummary 등에서 이미 쓰는 패턴). ★resolveLoginIp 로 IP 문자열 생성을 성공·실패가 공유한다 — 형식이 같아야 CmsLoginLog 화면이 콤마로 잘라 CLIENT_IP/PROXY_1 을 뽑는 파싱(CmsLoginLog-mapper.xml:12-13)이 동일하게 동작한다. 요청 스레드가 아니면 종전과 같이 IP 없이 기록된다. ℹ️로그아웃(S02)의 null 은 그대로 뒀다(보안 가치 없음, 범위 밖). 동작 변화는 실패 로그의 LOGIN_IP 가 채워지는 것뿐이고 성공 경로는 값이 같다.
    • 파일 정합성 점검 성능 개선(2) — ORPHAN 도 listNames+확장자필터로(PR #166) — PR #165 후속. 양옵션(ORPHAN+PORTAL) 한 달 조회가 여전히 느렸다. ORPHAN 이 listFiles(파일별 stat)로 폴더를 열거해 큰 폴더에서 느린 게 남아 있었다. 조치: ORPHAN 도 listNames(NLST) + "확장자 있는 이름만"(날짜 하위폴더 01·2026 등 제외) 필터로 전환 — stat 없이 파일만 추린다. ★단 PORTAL 은 existsBatch(파일별 SIZE) 유지가 정답: 포탈 미러는 거대 월폴더에 드문드문 박혀 있어 폴더 전체 listNames(수천 이름)보다 타깃 SIZE 가 빠르다(폴더-listNames 로 바꿨다 26s→오히려 악화 확인). V2/ORPHAN 은 폴더당 행이 많아 listNames 유리 — 축별 접근이 다르다. 실측(.100 2026-01, 51,116건·포탈 1,387): 기본 2.25s / +ORPHAN 3.06s / +ORPHAN+PORTAL 9.49s(이전 방식 26s). 운영은 포탈 미러가 수십 건뿐이라 양옵션도 몇 초. list()(listFiles)는 이제 미사용이나 재사용 가능 유틸로 존치.
    • 파일 정합성 점검 성능 개선 — MISSING 은 listNames(NLST)로 빠르게, ORPHAN 은 옵션화(PR #165, FE #218) — 운영에서 한 달 스코프 조회가 60초 axios 타임아웃("인터넷 연결을 확인해주세요")으로 실패했다. 원인: V2 점검이 폴더마다 listFiles(LIST — 파일별 stat)로 조회하는데, 한 달 스코프엔 월(月) 레벨 폴더(KPL/KYL 전송분이 /2026/09/ 같은 월폴더, 파일 수천 개)가 끼어 그 폴더 하나 LS 가 수십 초라 60초를 넘긴다. 조치: MISSING(그 파일이 있나만 확인)은 FtpServiceInq.listNames()(NLST — 이름만, stat 없음 → 월폴더도 순식간)로 전환(하위 디렉터리 이름이 섞여도 SAVE_NM 과 안 겹쳐 무해). ORPHAN 켤 때만 폴더 전체를 훑으니 범위를 좁게. (짝 FE 는 axios 타임아웃도 이 화면만 180s 로 상향)

    • 미사용 파일 백엔드 정리 + 네이밍 정렬(PR #42·#43·후속) — 프론트/외부 호출이 전무한 Cost 첨부기능(VmsCostController·VmsCostService)과 그 전용 진입점(KeyService), 이들만 쓰던 PKG_CM_FILE(SP_GET_FILE_UPLOAD/SP_SET_FILE) 호출 체인, 死메서드 12개(fileUploadGpt·logoImageDownload·base64ImageDownload* 등)와 死엔드포인트(/fileUploadGpt·/fileDownload·/logoImageDownload)를 제거(약 1,320줄↓). 이어 FileDataController/FileDataService 의 메서드명과 엔드포인트 URL 을 verb-first 로 정렬했다 — /api/file/fileUpload→/uploadFile, /fileUploadInv→/uploadInvFile, /fileDelete→/deleteFile, /templateDownload→/downloadTemplate, /templateDownload4TES→/downloadTemplate4TES(메서드명 동일 규칙, uploadFileNasPath→uploadFileNas 포함; TES 템플릿 생성 private 헬퍼 tally/lhdc/lash/lashCon/tug→get*Template). 아울러 死스텁 엔드포인트 POST /api/vendor/comm/invoiceFileUploadIF(빈 응답·호출 0)도 제거. ⚠️ 엔드포인트 개명은 API 경로 변경(breaking) 이라 프론트 호출부(FileService·첨부 그리드·TES 템플릿 다운로드 등)를 같은 릴리스에서 함께 수정해 반영했다 — 백엔드·프론트를 동시 배포해야 한다. 존치 다운로드(/api/file/downloadFileNas)와 파트너 ZIP 다운로드 경로는 그대로다. 아울러 다건 조회 selectFileLists(MNGT_NO IN)를 selectFileList 에 동적 WHERE(<choose>: 단건 = / 리스트 IN / 그 외 1=0)로 흡수하고 유일 호출처(CmsInvoiceFileUploadPopup) 1곳을 이관 — 엔드포인트/매퍼 1쌍 감소(관리포인트 축소).
    • 공통 프로시저 호출 통합(executeVmsCommonProcedure) — select/save 두 경로를 합친 상위집합 메서드와 전용 엔드포인트 POST /api/vendor/comm/executeVendorCommonProcedure 신설. @Transactional·IN 커서 항상 처리·OUT 커서 1~20·커서별 개별 resultMap(ORA-17006 방지). 기존 select/save 는 존치. 프런트는 EIR 제외 전 모듈 전환. 상세: ADR-0004, vps §2-2.
    • 문서 작성 정책 명문화 — 홈에 ① 사내 전용 정보(내부 IP·호스트명·계정·실운영 문서)의 공개 문서 게시 금지 ② 한국어 · MkDocs Material 조직 표준 준수 를 명시. → 홈.
