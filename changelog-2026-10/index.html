    2026-10 변경 이력¶

    보안 수정: 인증 우회 규칙 제거, 팝업 SQL 바인드, 비밀번호 해시 응답 제외, 내부 전용 프로시저 거절 (PR #221, Infra #88)¶

    2026-10-14 리팩토링 전수 조사(Infra #83)에서 나온 보안 항목 중 1, 2, 3(긴급분), 5번을 고쳤다. Infra #88 조사 기준으로 운영 로그에서 악용 흔적은 찾지 못했다(요청 본문은 기록되지 않아 2, 3번은 "흔적 없음"까지만 말할 수 있다).

    정적 확장자 예외 규칙 삭제 (1번)¶

    • WebSecurityConfiguration 의 webSecurityCustomizer 를 지웠다. 정적 확장자로 끝나는 요청을 보안 필터에서 통째로 빼는 규칙이었는데, 쿼리 문자열까지 보고 판정해서 API 요청도 보안 필터를 건너뛸 수 있었다.
    • 백엔드는 운영에서 정적 자원을 서빙하지 않는다(nginx 는 /api/ 만 넘기고, 리소스 핸들러가 가리키는 static/css, js, img, fonts 디렉터리도 없다). 그래서 지워도 바뀌는 정상 동작은 없다. permit-all 목록은 그대로다.
    • 보안 필터 3개(JwtAuthenticationFilter, LoginAuthenticationProcessingFilter, SessionIdentityGuardFilter)는 @Bean 이라 서블릿 필터로도 자동 등록되고 있었다. FilterRegistrationBean#setEnabled(false) 로 끄고 시큐리티 체인 안에서만 돌게 했다.

    컨테이너 타입 팝업 BL_NO 바인드 (2번)¶

    • CmsCommonPopup-mapper.xml 의 selectCntrType 이 BL_NO 를 SQL 문자열에 그대로 넣고 있었다. 바인드(#{BL_NO})로 바꿨다. HCBLNO 는 세 선사 스키마 모두 VARCHAR2(16) 이라 비교 결과는 같다.

    공통 프로시저 관문: 내부 전용 프로시저 거절 (3번 긴급분)¶

    • 외부 진입점 VmsCommonController 가 내부 전용 프로시저(지금은 메일 앱 설정을 돌려주는 PKG_CM.SP_GET_AAD)를 실행 전에 거절한다. 이름은 trim, 대문자로 맞춰 비교하고 목록은 상수 한 곳에 둔다.
    • 메일 발송(비밀번호 찾기 포함), EIR, 파트너 API 는 서비스 메서드를 직접 불러 영향이 없다.
    • 허용 목록 방식으로 바꾸는 것은 후속이다.

    사용자 상세 조회에서 비밀번호 해시 제외 (5번)¶

    • CmsUserMgt-mapper.xml 의 select 에서 USER_PWD 를 뺐다. 화면은 저장 때 MAIN 을 그대로 돌려보내지만 USER_PWD 를 쓰는 곳은 없다(update 는 이 컬럼을 바인드하지 않는다).

    테스트 (DB, Redis, 실 설정 파일 없이)¶

    테스트 고정하는 것
    WebSecurityConfigurationTest API 경로는 쿼리 문자열이 무엇이든 로그인을 요구한다, application.yaml.example 의 permit-all 경로는 열려 있다, 보안 필터는 체인 안에서만 돈다
    CmsCommonPopupMapperTest selectCntrType 의 BL_NO 가 바인드 파라미터로 들어간다
    VmsCommonControllerTest 내부 전용 프로시저는 대소문자, 공백과 무관하게 거절되고 서비스가 불리지 않는다

    세 테스트 모두 수정 전 코드로 되돌리면 실패하는 것을 확인했다.

    • 문서: security.md, architecture.md, api.md 의 정적 리소스 설명을 고치고 WebSecurityConfiguration.java, VmsCommonController.java 줄번호를 맞췄다(modules.md, code-walkthrough/vps.md 포함). security.md, code-walkthrough/vps.md 에 내부 전용 프로시저 거절을 적었다.

    공통 프로시저 관문: EIR Response Log 는 관리자 고정 대상에서 제외 (PR #224, Infra #88)¶

    BE #222 에서 관리자 전용으로 묶은 프로시저 중 PKG_EEIR.SP_GET_RESPONSE_LOG(EIR Response Log 화면)를 뺐다. 지금은 ADMIN 메뉴지만 나중에 다른 역할에 열 수 있어, 관문에서 ADMIN 으로 고정하지 않기로 했다(사용자 결정 2026-10-15). 화면 접근은 메뉴 권한으로 관리한다.

    • VmsCommonController.ADMIN_ONLY_PROCEDURES 에서 1개 제외(12개 → 11개)
    • 테스트: 모듈 관리자 역할(EIR00)로도 관문을 통과하는지 고정

    공통 프로시저 관문: 관리자 전용 프로시저는 ADMIN 만 (PR #222, Infra #88)¶

    Infra #88 3번(공통 프로시저 관문에 인가가 없다)의 후속이다. 관리자 메뉴 화면이 관문으로 부르는 프로시저를 서버가 역할을 보지 않고 실행하고 있었다. 메뉴가 ADMIN 에만 걸려 있어도 그건 좌측 메뉴 노출일 뿐이다.

    관리자 전용 프로시저는 ADMIN 만¶

    • 외부 진입점 VmsCommonController 가 실행 전에 관리자 전용 프로시저 목록(ADMIN_ONLY_PROCEDURES)을 보고, 세션 역할에 ADMIN 이 없으면 거절한다(This function is allowed for administrators only.). 역할은 세션에서만 읽고, 세션 역할이 비어 있어도 거절한다.
    • 이름은 내부 전용 프로시저와 같은 방식(trim, 대문자)으로 맞춰 비교하고, 한 요청에 하나라도 걸리면 아무것도 실행하지 않는다.
    • 대상은 아래 12개다. 화면별로 메뉴 역할(.100)과 프론트 호출처를 하나씩 확인했다.
    화면(메뉴) 메뉴 역할 프로시저

    API 호출 로그 ADMIN PKG_API.SP_GET_API_LOG
    용어 사전 ADMIN PKG_CM.SP_CHK_TERM_DUP

    • 사용자 관리 메뉴는 모듈 관리자 역할에도 걸려 있지만, 삭제 버튼과 비밀번호 초기화 버튼은 ADMIN 에만 보이고 두 프로시저의 PL/SQL 도 ADMIN 만 허용한다. 그래서 두 기능은 ADMIN 전용으로 묶었다(사용자 결정). 모듈 관리자가 쓰는 사용자 조회, 저장은 그대로다.
    • 이 12개를 서버 내부 호출(메일 발송, EIR, 파트너 API)이 부르는 곳은 없다. 내부 호출은 서비스 메서드를 직접 불러 어차피 이 검사를 거치지 않는다.

    사용자, 회사 관리 법인 범위를 서버에서 강제 (PR #223, Infra #88)¶

    사용자 관리와 회사 관리의 모듈 범위(회사의 SYSTEM_DIV 가 편집자 역할 앞 3자 중 하나)는 회사 트리와 사용자 목록 SQL 에만 있었다. 단건 조회와 저장은 받은 ID 로만 처리했고, 사용자 목록은 모듈 관리자(..00)를 범위 밖으로 빼 전 회사 사용자를 보여 줬다. 2026-10-15 사용자 결정(ADMIN 은 전부, 모듈 관리자는 자기 모듈의 회사와 그 소속 사용자만)에 맞춰 기존 조건을 서버가 모든 경로에 강제한다.

    • 목록
      • 사용자 목록(selectList): 모듈 관리자 예외를 없앴다. ADMIN 만 전체, 그 밖은 자기 모듈 회사 소속 사용자.
      • 회사 트리(selectTree): 모듈 조건이 읽는 USER_ID 를 서비스가 세션 값으로 덮어쓴다. 규칙은 그대로다.
    • 단건 조회와 쓰기에 범위 확인을 더했다. 범위 밖이면 409 This company or user is outside your management scope. 와 [SCOPE] 경고 로그(편집자, 대상, 회사).
      • 사용자 상세, 역할 복사 원본: 대상 사용자
      • 사용자 저장: 기존 사용자의 현재 소속과 새 소속, 새 사용자의 소속, 회사 관계 그리드의 CORP_CD_REL
      • 회사 상세, 관계(selectCorpRel), 삭제: 대상 회사
      • 회사 저장: 현재와 저장할 SYSTEM_DIV(새 회사는 입력값), 바뀐 상위 회사, 하위 그리드가 쓰는 다른 회사
      • 쓰기는 퍼사드나 서비스 첫머리에서 쓰기 전에 전부 본다
    • 기존 로직과 다르게 둔 것
      • 관계 그리드는 행의 CORP_CD 가 아니라 CORP_CD_REL 로 본다. CORP_CD 는 선사(SNKO, HALK, HSLI, FDS)다.

    에러로그에 관리번호(MNGT_NO)와 멀티파트 param 기록 (PR #218, Infra #76)¶

    PR #182 로 에러로그에 호출 메뉴(MENU:)가 들어갔지만 관리번호는 빠져 있었다. 구멍은 멀티파트 하나였고, 하필 그게 첨부 업로드(FTP 장애 경로)라 2026-09-30 / 10-01 의 FileSystemException 이 어느 문서였는지 알 수 없었다.

    바뀐 모습¶

    REQUEST: POST /api/file/uploadFile
MENU: crsEstUploadExl
MNGT_NO: SEL011908000123
PAYLOAD: (multipart/form-data, 1,234,567 bytes)
  param: {"MNGT_NO":"SEL011908000123","COMP_CD":"SNKO", ...}
  files: 견적서.pdf (1,233,900 bytes)

    콘솔 한 줄: [ERR] POST /api/file/uploadFile [crsEstUploadExl MNGT_NO=SEL011908000123] : .... 관리번호는 식별자라 "콘솔에 요청 본문을 안 남긴다" 는 방침에 걸리지 않는다.

    원인 두 가지¶

    • 멀티파트 PAYLOAD 줄이 아예 안 찍히고 있었다. Tomcat 은 파트를 파싱할 때 ContentCachingRequestWrapper 를 거치지 않고 밑단 스트림을 직접 읽어 캐시가 빈 채로 남는다. 그 분기가 "캐시가 비어 있지 않으면" 안에 있었다. .100 의 과거 uploadFile 에러 4건 모두 PAYLOAD 줄이 없었다. → 멀티파트는 request.getParts() 로 파트를 직접 읽는다.
    • param 은 파일 파트처럼 온다. 프론트 FormBuilder.appendJson 이 Blob 을 넣는데, 브라우저는 File 아닌 Blob 에도 filename="blob" 을 붙인다. → filename 이 없거나(일반 폼 필드) json 이고 64KB 이하면 텍스트 파트로 보고 내용을 찍는다.

    범위¶

    • 관리번호는 JSON 바디 또는 JSON 파트의 최상위 MNGT_NO 키 하나만 본다. SEARCH.MNGT_NO, FILES[] 처럼 한 겹 안의 값은 찾지 않는다(그 요청들은 JSON 이라 PAYLOAD 에 원문이 남는다).
    • CmsDocumentPopup 은 param: {} 로 올려서 이 조치로도 관리번호가 안 남는다(화면이 업로드 뒤에 행을 만드는 구조라 로그 때문에 바꿀 자리가 아니다).
    • 파트 파싱 자체가 실패한 요청(크기 초과, 깨진 멀티파트)은 크기만 남긴다. 에러 적재는 막지 않는다.

    검증 (로컬 9050, .100)¶

    요청 결과
    업로드, param 을 filename=blob + json 으로 MNGT_NO: 줄, param: 내용(비밀번호 키 *****), 파일은 이름·크기만
    업로드, param 을 filename 없이 같음
    JSON 프로시저 호출(최상위 MNGT_NO) MNGT_NO: 줄
    경계가 깨진 멀티파트 PAYLOAD: (multipart/form-data, 24 bytes) 만, 적재 정상

    • ⚠️ 끊김 자체를 막지는 않는다 — 끊김이 10초보다 길면 재시도도 실패한다. 원인 확인은 Infra #75(2026-10-02 #41 에서 분리, Azure 지원 요청 1순위).
    • 테스트 FtpServiceInqTest 5건: 닫힌 포트로 실제 세션 생성 실패를 일으켜 판정 기준이 Spring 의 예외와 맞는지 확인(라이브러리가 메시지를 바꾸면 깨진다) + 재시도 횟수 4건.

    첨부 소유 검증 — 업로더 축 단일 규칙으로 전 모듈 차단 (Infra #59)¶

    TB_CMS_ATFILE 은 전 모듈 첨부가 모이는 한 테이블인데 클라이언트가 보낸 MNGT_NO 를 그대로 믿어, 로그인만 하면 남의 번호로 목록·다운로드·삭제가 됐다. ★종전 설계(fn_can_access_est + 견적 존재 폴백)는 CRS 만 덮고 CFS/TES/FDS/CSM 은 무방비였다 — 비CRS 는 견적 조회가 항상 0건이라 검증을 아예 안 탔다. ★모듈별로 막으려면 디스패치 리졸버가 필요한데(값 모양으로 못 가른다), 업로더 축이 그걸 통째로 우회한다 — "누가 올렸나" 만 보면 모듈을 알 필요가 없다. REG_USER_ID 는 업로드 시 getSession().getUserId() 라 위조 불가이고 .3 914,822행 충전율 100%. ★①(견적 소유)이 맨 앞이어야 한다 — 한 견적에 여러 협력사가 올린 첨부가 섞인 경우가 1,827건 있어, 업로더 축만 쓰면 견적 소유자가 자기 첨부 일부를 잃는다. ★다운로드는 매퍼가 아니라 서비스에서 판정한다 — 매퍼에서 걸면 거절이 0건이 되어 포탈 폴백으로 흘러 같은 MNGT_NO 의 포탈 행이 대신 내려간다. ★포탈시스템(SKR_DOC_MST) 폴백 행도 같은 규칙으로 막는다 — 거기 업로더는 INS_USR 이고 우리 쪽 USER_ID 다(충전율 99.999%). 업로드는 PKG_CM.FN_CAN_SAVE_FILE 로 막았다 — ①기존 첨부가 있으면 그걸 볼 수 있는가(주인이 아니어도 같은 회사면 통과), ②첨부 0건이면 번호의 주인(수리 견적 / TB_TES_GRP_INV 의 COMP_CD+CORP_CD), ③어디에도 없으면 신규로 보고 허용. ★fn_can_access_file 로 대신하면 안 된다 — 업로더 자리에 자기자신/NULL 을 넣으면 ②/④ 로 떨어져 항상 'Y' 다. ★CORP_CD 는 파라미터가 아니라 함수가 세션 사용자로 조회한다. CSM 은 대상 밖. ★④(완전 신규로 보고 통과)가 남는 노출이다 — 미식별 813 · 포탈 문서 186 · CFS 주문(BK_NO) 9. "첨부가 아직 하나도 없는 남의 번호에 첫 파일을 심는 것" 이고 열람 유출이 아니라 무결성 문제다. ★CFS 는 두 갈래 — 송장(GRP_INV_NO, COST_TP='CFS')은 ③이 잡지만 주문(TB_CFS_ORD.BK_NO)은 TB_TES_GRP_INV 에 없어 ④로 빠진다. 9건뿐이라 막지 않기로 결정(2026-10-02). 막을 땐 소유 축이 CUST_CD 다 — 그룹인보이스의 CORP_CD 와 다르니 통일 금지. 적용 지점 4곳이 전부 닫혔고, 검증 제외 4종은 보안 문서의 "첨부 소유 검증" 절에 적었다.

    • ★배포 직후 핫픽스 3건(2026-10-02) — 게이트 로직은 맞았는데 주체(USER_ID)가 매퍼까지 가지 않아 운영에서 드러났다. ① getSessionUserId() 가 getPrincipal() 을 봐서 null → FN_CAN_ACCESS_FILE(null, …) 이 전부 'N' → 업로드 전건 거절(PR #191). ② 컨트롤러가 param.getMap("SEARCH").put("USER_ID", …) 로 주입했는데 DMap.getMap() 은 copyMap() 으로 사본을 돌려준다 — 쓴 값이 버려져 첨부 목록 0 건. 서비스에서 SEARCH 를 한 번만 꺼내 그 인스턴스를 DAO 로 넘기도록 고쳤다(b15b1d3). ③ getBase64Image 만 USER_ID 주입이 빠져 있었다 — 매뉴얼 이미지가 전부 /FORM/ 이라 템플릿 면제로 살아 있었을 뿐, 아니었으면 null 행에서 NPE(500)였다. 주입 + null 가드 추가(f917015). ⇒ 교훈: 거절을 'N'/빈 결과로 설계하면 전달이 끊겨도 조용히 전부 차단된다. 세션 값을 쓰는 게 게이트면 SQL 단위 검증으로 끝내지 말고 로그인 계정으로 그 엔드포인트를 실제 호출할 것.
