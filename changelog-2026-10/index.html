    2026-10 변경 이력¶

    API 를 화면에서 끌 수 있게 한다 (PR #281)¶

    /api/partner/** 의 각 API 를 TB_CMS_API.USE_YN 으로 켜고 끈다. 'N' 이면 409 (This API is not available.) 로 거절한다. API 관리 화면(CmsApiMgt)에서 바꾸면 재기동 없이 먹는다.

    TOKEN_CHK 와 무엇이 다른가¶

    어제 넣은 TOKEN_CHK(PR #279) 는 인증을 요구할지를 정하고, 이번 USE_YN 은 API 자체를 끈다. 그래서 거르는 자리도 다르다.

    거르는 자리 막는 대상
    TOKEN_CHK Security 층(ApiTokenChkAuthorizationManager) 토큰·세션이 없는 요청 → 302
    USE_YN 컨트롤러(PartnerService.assertApiEnabled) 인증을 통과한 요청도 → 409

    permitAll 목록에 없는 경로는 Security 층을 안 거치므로, 끄는 스위치는 컨트롤러에 둬야 모든 엔드포인트를 덮는다.

    비어 있으면 막지 않는다¶

    USE_YN 은 컬럼을 뒤늦게 더한 터라 기존 행이 전부 NULL 이다. 'Y' 만 통과시키면 값을 채우기 전에 모든 호출이 멎으므로, 'N' 일 때만 거절한다.

    단 발급 화면의 API 목록(selectApiList)은 USE_YN = 'Y' AND TOKEN_CHK = 'Y' 로 거른다. 이쪽은 NULL 이 빠지므로, 값을 안 채우면 목록이 빈다(호출 자체는 멀쩡하다).

    가드를 건 자리¶

    cancelEir(EIR002) · download(API001) · getEstAttachFile(API003) · downloadAll(API002) 네 곳. getCancelEir 만 TB_CMS_API 에 행이 없어 제외했고, 그 이유를 코드에 남겼다 — 행을 추가하면 그 순간부터 관리 대상이 되므로 그때 가드를 함께 넣어야 한다.

    Authorization: Bearer 가 401 이던 것¶

    JwtAuthenticationFilter 가 접두어를 "bearer " 리터럴로 떼어내고 있었다(replaceFirst 는 정규식이라 대소문자를 가린다). 표준 표기인 대문자 Bearer 로 보내면 접두어가 남은 채 "Bearer eyJ…" 가 JWT 파싱에 들어가 401 이었다. 거의 모든 HTTP 클라이언트가 대문자를 보낸다.

    (?i)^bearer\s+ 로 바꿔 대소문자를 가리지 않고 맨 앞에서만 떼어낸다.

    토큰 발급 메일에 사용 방법을 넣는다¶

    종전 메일에는 호출 경로도 선사 코드도 없어 받는 쪽이 무엇을 부를지 알 수 없었다. 표에 두 줄(호출 경로, 선사)을 더하고, 그 아래에 요청 예시와 주의사항을 붙였다(국문·영문).

    • 헤더 예시는 표준 표기 Authorization: Bearer <토큰>
    • 헤더를 못 쓰면 &token= 도 되지만 URL 에 남아 접근 로그에 기록되므로 헤더를 권한다
    • 응답 코드의 뜻(401 토큰 문제 / 302 토큰 없음 / 409 API 중지)

    메일에 쓸 경로가 조회에 없어 selectOne 에 b.API_URL 을 더했다.

    ⚠ 배포 순서 — DB 가 먼저다¶

    컬럼 없이 이미지가 올라가면 /api/partner/* 가 전부 500(ORA-00904) 이다.

    ALTER TABLE TB_CMS_API  ADD (USE_YN VARCHAR2(1));
ALTER TABLE TMP_CMS_API ADD (USE_YN VARCHAR2(1));   -- IN 커서 컬럼 정의를 TMP 가 겸한다
UPDATE TB_CMS_API SET USE_YN = 'Y';                 -- ★빠지면 발급 화면 API 목록이 빈다
COMMIT;

    이어서 PKG_API 바디 네 곳에 use_yn 을 더한다(조회 1곳, TMP 적재 1곳, merge update·insert 2곳). 기본값은 nvl(…, 'Y') 로, token_chk 의 'N' 과 반대다.

    검증¶

    로컬 9040, .100, API003(/getEstAttachFile) 토큰으로 8종 실측.

    경우 결과
    Authorization: bearer 200 (zip 6개 파일 379KB)
    Authorization: Bearer 200 ← 이번 수정
    ?token= 200
    토큰 없음 302
    다른 선사(COMP_CD=HALK) 401
    다른 경로(/download) 401
    폐기된 토큰 401
    USE_YN='N' 409 (화면에서 끈 즉시, 재기동 없이)

    JWT 토큰 관리 화면 오류 정리 (PR #277)¶

    BE #275 / FE #335 로 올린 화면을 실제로 띄워 보고 고친 것들이다. 전부 빌드와 린트를 통과하는 종류라 실행해 봐야만 드러났다.

    만료일이 하루 밀렸다¶

    2099-12-31 로 발급하면 END_DT 가 2100-01-01 00:00:00 으로 저장됐다. LocalTime.MAX(23:59:59.999999999)가 Oracle TIMESTAMP(6) 에 들어갈 때 반올림된 것이다. LocalTime.of(23,59,59) 로 바꿔 JWT 의 exp 와도 초까지 맞췄다.

    메시지 코드가 뜻과 달랐다¶

    코드 주석만 보고 썼다가 실제 문구가 전혀 다른 것을 세 번 썼다.

    쓰던 곳 실제 문구였던 것 바꾼 것
    필수항목 누락 MSG000002 삭제하시겠습니까? MSG000012 {0} 은/는 필수 입력 항목입니다
    행 미선택 MSG000019 이미 사용중 인 {0} 입니다 MSG000009 선택된 행이 없습니다
    메일 발송 실패 MSG000013 복사하시겠습니까? MSG000453 (신규)

    새로 만들었다가 기존 문구로 되돌린 것도 넷이다 — MSG000015(존재하지 않는 {0}), MSG000022(종료일자 역전), MSG000399(이메일 발송 완료), MSG000419(유효하지 않은 이메일).

    그 밖¶

    • TB_CMS_JWT INSERT 가 새 JWT_SN 을 돌려준다(selectKey) — 발급 직후 메일 발송이 이 값을 쓴다.

    검증¶

    ./gradlew compileJava 통과. 짝 PR: Frontend #336

    API 경로마다 인증 요구 여부를 화면에서 켠다 (PR #279)¶

    /api/partner/** 가 토큰을 요구할지 말지를 TB_CMS_API.TOKEN_CHK 이 정한다. API 관리 화면(CmsApiMgt)에서 바꾸면 재기동 없이 바로 먹는다.

    왜 yaml 이 아니라 DB 인가¶

    종전엔 공개 여부가 application.yaml 의 request-permit-all-mappings 에 박혀 있어, 한 경로를 닫으려면 배포를 해야 했다. 외부(eBiz) 연동을 토큰 방식으로 옮기는 일은 상대가 먼저 바뀌고 우리가 뒤따라 닫는 순서라, 그 사이를 배포로 맞추기 어렵다.

    토큰 검증 자체는 이미 돌고 있었다¶

    permitAll() 은 인가 판정만 건너뛴다. 필터 체인은 원래도 다 돈다. 그래서 공개 경로라도 토큰을 달고 오면 검증을 받는다. 실측(로컬 9040, 이번 변경 전):

    경로 토큰 없음 가짜 토큰
    /download 200 401
    /downloadAll 500 (HBLNO 복호화 실패 = 컨트롤러 도달) 401
    /getEstAttachFile 302 401

    곧 무중단 전환이 된다 — 상대 시스템에 올바른 토큰을 먼저 심으면 공개 상태에서도 그대로 돌고, 확인한 뒤 화면에서 끄면 된다. 반대로 틀린 토큰은 공개 경로에서도 즉시 401 이라, 상대 쪽 검증이 우리 쪽 변경보다 먼저다.

    구현¶

    permitAll() 을 ApiTokenChkAuthorizationManager 로 바꿨다.

    • /api/partner/ 로 시작하지 않는 공개 경로(로그인·health·jsp)는 DB 를 보지 않고 그대로 통과
    • TB_CMS_API.TOKEN_CHK='Y' → AuthenticatedAuthorizationManager 에 위임
    • 등록되지 않은 경로(조회 결과 null)는 yaml 의 공개 선언을 그대로 따른다 — 지금까지의 동작

    거부는 AuthorizationFilter 가 받아 넘기므로 응답이 종전 미인증 요청과 같다(익명이면 /login 302).

    캐시는 두지 않았다. 화면에서 끈 값이 바로 먹어야 하고, 이 경로의 호출량이 30일 1,800건 수준이다.

    yaml 의 역할이 바뀌었다¶

    목록에 남아 있는 것이 "공개"가 아니라 "화면이 열어둘 수 있는 후보" 다. 목록에 없으면 무조건 인증이라, PartnerController 에 엔드포인트를 새로 붙여도 저절로 열리지 않는다(와일드카드를 쓰지 않는 이유는 그대로다). /api/partner/getEstAttachFile 을 목록에 넣고 TOKEN_CHK='Y' 로 두었다 — 동작은 전과 같고, 이제 화면에 상태가 보인다.

    /api/partner/getCancelEir 은 TB_CMS_API 에 행이 없어 화면에서 끌 수 없다(공개 고정).

    토큰의 선사를 대조한다¶

    verifyApiToken 에 세 번째 검사를 넣었다. 경로만 맞으면 ?COMP_CD= 를 바꿔 다른 선사 데이터를 받아갈 수 있었다 — 발급 단위가 (사번, 선사, API) 인데 선사만 검사에서 빠져 있었다.

    request.getParameter 는 JSON 본문을 읽지 않으므로, 본문으로 COMP_CD 를 보내는 POST /api/partner/cancelEir 은 대조를 건너뛴다. 본문을 읽으면 스트림이 소진돼 컨트롤러의 @RequestBody 가 깨진다.

    ⚠ 배포 순서 — 운영 DB 가 먼저다¶

    .3 에 컬럼이 없는 채로 이미지가 올라가면 /api/partner/* 가 전부 500 이다(실측: ORA-00904: "TOKEN_CHK": 부적합한 식별자). eBiz 다운로드가 통째로 멎는다.

    ALTER TABLE TB_CMS_API  ADD (TOKEN_CHK VARCHAR2(1) DEFAULT 'N' NOT NULL);
ALTER TABLE TMP_CMS_API ADD (TOKEN_CHK VARCHAR2(1));
UPDATE TB_CMS_API SET TOKEN_CHK = 'Y' WHERE API_ID = 'API003';

    TMP_CMS_API 쪽을 빠뜨리면 안 된다 — IN 커서(P_IC)의 컬럼 정의를 그 테이블이 겸한다 (CM_CD 000050 → USER_TAB_COLS). 그래서 CM_CD 는 손댈 필요가 없다.

    PKG_API 바디는 세 곳(조회 select, tmp 적재, merge)에 auth_yn 을 더한다. 이쪽은 덜 급하다 — 빠지면 화면에 값이 비어 보일 뿐 인가 판정은 테이블을 직접 읽는다.

    검증¶

    로컬 9040, .100.

    • 컬럼 없는 상태: /api/partner/* 500, /application/health 200 (DB 를 보지 않는 경로는 무영향)
    • compileJava 통과

    관문 허용 목록 상태 조회에 개수 추가 (PR #280, Infra #92)¶

    POST /api/vendor/comm/getProcedureAllowlistStatus 응답에 COUNT(응답한 서버가 들고 있는 목록 개수)를 더했다. 패키지 관리 화면 버튼 왼쪽 표시가 최근 갱신 : 2026-10-29 14:58 (111개) 가 된다(FE 별도 PR). 새 프로시저를 쓰는 화면을 배포하고 갱신 버튼을 누른 뒤 개수가 늘었는지로 새 이름을 받았는지 본다.

    관문 허용 목록 — 차단 전환, 최근 갱신 시각 조회 (PR #278, Infra #92)¶

    허용 목록(BE #233)을 기록만 하던 단계(2026-10-20~29 관찰, 업무 화면 MISS 0건)에서 거절로 바꿨다.

    차단¶

    • 목록에 없는 프로시저는 ProcedureNotAllowedException → 403, ERR_DIV 01, unknown(화면 .catch 가 삼키는 곳에서도 오류 창), 문구 MSG000454 (en: This function is not available. Please refresh the page (F5). If the problem persists, contact the administrator.)
    • 403 인 이유: 5xx 면 옛 탭 하나로 5xx 경보가 울리고, 401 이면 프론트가 로그인 화면으로 보낸다
    • 거절은 전역 예외 리졸버 경로라 에러 로그에 TRACE, MENU, PAYLOAD 와 함께 남는다. 콘솔은 WARN [VMS-ALLOW] DENY <PKG.PROC> USER_ID=… REFERER=…

    다시 받는 때 정리¶

    왜 Azure 메트릭이 아니라 컨테이너 안에서 읽나¶

    MemoryPercentage·CpuPercentage 는 정수로 반올림돼 나온다. 사용량 ÷ 퍼센트로 한도를 역산하면 실측에서 이렇게 나왔다.

    실제 3 GiB  / 1.5 core
역산 3.36 GiB / 2.0~2.3 core

    CPU 는 사용률이 1~3% 라 나눗셈이 오차를 증폭시켜 더 심하다. cgroup(memory.max·cpu.max)과 Runtime.maxMemory() 는 설정값 그대로라 정확하다.

    • cgroup v2 경로를 먼저 보고 없으면 v1. 못 읽거나 max(무제한)면 null → 화면은 - 로 비운다. 로컬(WSL)은 무제한이라 실제로 이 경로를 탄다
    • 레플리카 수만 Azure 메트릭(Replicas)에서 읽는다 — 컨테이너 안에서는 알 수 없다. 실패해도 그 칸만 비고 나머지는 나온다
    • 응답의 HOST 가 어느 레플리카가 답했는지 알려준다

    공통 프로시저 로그에 조회 범위(기간·업체 지정 여부)를 남김 (PR #268, Infra #94)¶

    [VMSPROC] 느린 호출 로그 꼬리에 fm=20261001 to=20261031 days=31 company=Y 를 덧붙인다.

    [VMSPROC] PKG_CRS_ESTIMATE.SP_GET_EST rows=0 sqlLen=0 elapsedMs=31708 fm=20261001 to=20261031 days=31 company=N

    20초를 넘긴 관문 호출 196건(30일) 중 sp_get_Est 가 98건으로 절반인데, 이 프로시저는 결과 견적 1건마다 스칼라 서브쿼리 5~6개와 PL/SQL 함수 2종을 돌려 걸리는 건수가 그대로 시간이 된다. 즉 "얼마나 긴 기간을, 업체를 지정하고 조회했는가" 가 비용을 정한다.

    그런데 로그에 그 정보가 없어서 기간 상한을 몇 개월로 둘지 정할 근거가 없다. 그냥 3개월로 막으면 업무를 끊을 수 있다. 1~2주 모아 분포를 보고 정하려고 남긴다.

    • 로그량은 안 늘어난다 — 기존 임계(1초 또는 50행)를 그대로 쓴다. sp_get_Est 는 운영 15,433건 중 1초 미만이 0건이라 어차피 전건이 남는다.
    • 키 이름은 화면이 정하므로 있는 것만 붙인다. FM_DT/TO_DT 가 8자리가 아니면(미입력·입력 중) 통째로 뺀다. COMPANY_CD 키가 없는 화면엔 company= 를 안 붙인다.
    • days 는 양끝 포함이다(20261001~20261031 → 31).

    분포를 보는 쿼리는 이렇다.

    ContainerAppConsoleLogs_CL
| where TimeGenerated > ago(14d) and ContainerAppName_s == 'vp-prod-be' and Log_s has '[VMSPROC]'
| where Log_s has 'PKG_CRS_ESTIMATE.SP_GET_EST'
| extend days = toint(extract(@'days=(\d+)', 1, Log_s)),
         company = extract(@'company=(\w)', 1, Log_s),
         ms = tolong(extract(@'elapsedMs=(\d+)', 1, Log_s))
| summarize n = count(), p50 = percentile(ms,50)/1000.0, mx = max(ms)/1000.0
    by company, band = case(days<=31,'1개월 이하', days<=93,'3개월', days<=186,'6개월', days<=366,'1년','1년 초과')
| order by n desc

    왜 실패했나 — 게이트가 이 경로에 맞지 않는다¶

    SP_SET_FILE4PORTAL 은 화면에서 협력사가 자기 견적에 올릴 때 쓰라고 만든 것이라 fn_can_access_est(p_user_id, …) 소유검증을 건다. 관리자 보정은 성격이 다르다 — 이미 커밋된 정본 행을 포탈로 복사할 뿐 행위자가 없다. 그래서 어느 ID 를 넣어도 맞지 않는다.

    넣는 ID 결과
    업로더 그 사람이 그 거래처에 연결돼 있지 않으면 '남의 견적'으로 거절
    관리자 프로시저 필터가 reg_user_id/ins_usr = p_user_id 라 0건 → 무동작인데 성공

    조치 — 보정만 프로시저를 쓰지 않는다¶

    VENDOR 가 세 포탈 스키마에 SELECT/INSERT/DELETE 직접 권한을 갖고 있어 매퍼에서 바로 쓴다. DB 변경은 없다(프로시저를 고치지도, 만들지도 않았다). 업로드 화면 (CrsEstimate·CrsFileUploadPopup)은 프로시저를 그대로 쓰고 게이트도 그대로다.

    소유검증을 없앤 게 아니라 옮긴 것 — 이 쓰기를 가두는 장치 다섯¶

    1. 엔드포인트가 관리자 전용(requireAnyRole(ROLES_ADMIN))
    2. 대상이 클라이언트 입력이 아니다 — selectPortalGaps(기간·관리번호 스코프, 전부 비면 1=0)
    3. 쓰는 내용이 전부 정본에서 나온다 — INSERT 원천이 TB_CMS_ATFILE 뿐이라 없던 첨부가 생기지 않고, 아무에게도 권한을 주지 않는다
    4. 지우는 범위가 우리가 만든 행뿐 — FILE_PATH LIKE '/VENDOR%'
    5. 정본이 없으면 아무것도 지우지 않는다 — DELETE 에 EXISTS 가드 → 재동기화만 가능하고 고아를 만들 수 없다

    로컬 default 프로파일 포트를 9040 으로 (PR #270, Infra #98)¶

    application-default.yaml.example 의 server.port 를 9041 → 9040 으로 바꿨다. 이제 아무 설정 없이 ./gradlew bootRun 하면 9040 으로 뜬다. 팀 로컬 규칙도 프론트 4040, 백엔드 9040 으로 돌아간다.

    왜¶

    9041 은 이관 동안 레거시(V1, 9040)와 함께 띄우려고 나눈 값이었고, 팀 로컬 규칙(9050)은 SERVER_PORT 환경변수로 덮어썼다. 레거시를 닫았으니 둘 다 필요 없어 원래 포트로 되돌린다.

    운영 영향 없음¶

    운영(ACA)은 SPRING_PROFILES_ACTIVE=prod,azure 로 뜨고 포트는 application-azure.yaml 의 9041 이다. default 프로파일은 운영에서 쓰지 않는다. 그래서 azure 설정, Dockerfile 의 EXPOSE 9041, bicep, nginx, 배포 워크플로의 9041 은 그대로 둔다.

    각자 할 일¶

    실설정 application-default.yaml 은 gitignore 라 이 변경이 자동으로 들어가지 않는다. 각자 로컬 src/main/resources/application-default.yaml 의 server.port 를 9040 으로 바꾼다. SERVER_PORT=9050 을 붙여 띄우던 스크립트나 실행 설정이 있으면 그것도 뺀다.

    파일 정합성에 "포탈 미등록" 점검과 재등록 추가 (PR #269)¶

    정본(TB_CMS_ATFILE)에 'RP' 첨부가 있는데 포탈시스템(SKR_DOC_MST)에는 그 견적 행이 한 줄도 없는 경우를 찾아, 그 자리에서 다시 등록한다.

    업로드가 끝나면 화면이 SP_SET_FILE4PORTAL 을 불러 포탈시스템에 사본을 쓴다. 그 호출이 끝내 돌지 못하면 파일은 멀쩡한데 선사 쪽 화면에서만 안 보인다. 지금까지는 이게 생겨도 아무도 몰랐다 — 정합성 화면은 DB↔NAS 만 대조해 이 방향을 보지 않았다.

    탐지 — selectPortalGaps¶

    selectFallbackExposedMirrors 와 방향이 반대다(저쪽은 "미러만 남은 것").

    • NOT EXISTS 를 MNGT_NO 로 건다. SAVE_NM↔UNIQ_NM 대조는 인덱스가 없어 .100 에서 25분이 지나도 안 끝났다. 그래서 판정 단위가 견적이고, 일부 파일만 빠진 견적은 안 잡힌다.
    • 스코프는 기존 조회와 같다(기간 + 관리번호, 전부 비면 1 = 0). 3선사 UNION 으로 1개월 2.7초.
    • 최근 10분 내 업로드분은 제외한다 — 지금 올라가는 중인 견적에 재등록이 겹치면 프로시저의 DELETE → COMMIT → INSERT 사이에 끼어 오히려 어긋나게 만든다.
    • 묶음 단위는 (견적, 업로더, 선사) 다. 프로시저 INSERT 가 reg_user_id = p_user_id 로 한정돼 업로더별로 따로 불러야 그 사람 몫이 실린다.

    재등록 — POST /repairPortal¶

    DRY_RUN='Y' 면 대상만 돌려주고 아무것도 하지 않는다 — 화면이 실행 전에 보여주는 용도다. 미리보기와 실행이 같은 쿼리를 타야 "본 것"과 "건드리는 것"이 어긋나지 않는다.

    ★관문(executeVendorCommonProcedure)으로 부르면 안 된다. 관문은 P_USER_ID/P_COMP_CD 를 호출자(관리자) 세션에서 채우는데, 프로시저의 DELETE 는 ins_usr = p_user_id, INSERT 는 reg_user_id = p_user_id 로 한정된다 — 관리자 ID 로 부르면 양쪽 다 0건이라 성공처럼 보이는 무동작이 된다. 그래서 업로더 ID 로 직접 호출한다(statementType="CALLABLE").

    프로시저 안에 소유검증(fn_can_access_est)이 있어 업로더가 그 견적에 더는 접근할 수 없으면 'No permission' 커서를 돌려주고 아무것도 하지 않는다. 실패로 집계해 사유를 그대로 올린다.

    ★NAS 에 실물이 있는 것만 재등록한다¶

    탐지는 테이블 둘만 대조하는 순수 SQL 이라 실물이 이미 없는 파일도 걸린다(이 화면의 MISSING 과 같은 행). 그대로 재등록하면 열리지 않는 첨부를 포탈에 새로 만드는 꼴이다 — 선사 포탈은 SKR_DOC_MST 를 직접 읽으므로 BE #167 의 /VENDOR% 제외가 걸리지 않아 그대로 노출되고 FTP 550 이 난다.

    그래서 selectPortalGapFiles 로 같은 대상의 파일을 뽑아 NAS 존재를 확인하고, 각 행에 NAS_STATUS 를 붙인다. 프로시저는 그 견적·그 업로더의 파일을 전량 다시 넣으므로 일부만 골라 넣을 수 없다 — 한 개라도 없으면 그 견적을 통째로 제외한다. 폴더 조회 자체가 실패해도 판정이 불가능하므로 제외한다(모르면 건드리지 않는다).

    확인은 기존 resolveNas()(listNames + 폴더 캐시)를 그대로 쓴다. 대상 폴더만 훑으므로 전량 스캔이 아니다.

    정렬¶

    포함(재등록 대상) 먼저, 그 안에서 최종등록 오름차순. NAS_STATUS 는 SQL 이 아니라 NAS 확인 단계에서 정해지므로 매퍼의 ORDER BY 로는 걸 수 없다 — 서비스에서 한 번만 정렬한다. 매퍼의 ORDER BY COMP_CD, MNGT_NO 는 같은 시각끼리의 순서를 고정하는 기준선으로 남는다(Java sort 는 안정 정렬). LAST_REG 는 'YYYY-MM-DD HH24:MI' 라 문자열 비교가 곧 시간순이다.

    왜 이 화면의 읽기전용 원칙에 예외를 두나¶

    MISSING 정리가 스크립트 생성에 머문 것은 되돌릴 수 없는 DELETE 였기 때문이다(그 결정은 그대로 둔다). 이쪽은 멱등한 재동기화다 — 그 견적·그 업로더 몫의 미러만 지우고 정본에서 다시 넣으므로 맞는 견적에 한 번 더 돌아도 결과가 같고 되돌릴 것이 없다. 관리자 전용 게이트도 그대로 적용된다.

    역할 메뉴 저장에서 없는 상위 메뉴나 순환을 만나면 거절 (PR #263, Infra #95)¶

    역할별 권한 관리 화면(CmsRoleMenuMgt)에서 저장하면 서버가 화면 메뉴의 상위 메뉴를 끝까지 거슬러 올라가 함께 넣는다(CmsRoleMenuMgtService.findRecursiveUpperMenuList). 지금 메뉴 데이터로는 문제가 없었지만 두 경우에 저장이 깨졌다.

    • 없는 상위 메뉴: UPPER_MENU_ID 가 메뉴 테이블에 없는 ID 를 가리키면 조회가 null 을 돌려주고, 다음 단계에서 NullPointerException(500)이 났다.
    • 순환: 상위 관계가 돌면(A 의 상위가 B, B 의 상위가 A) 재귀가 끝나지 않아 StackOverflowError 가 났다.

    조치¶

    두 경우 모두 저장을 거절한다(업무 예외, 409). 문구에 문제 메뉴 ID 를 넣어 메뉴 관리에서 찾을 수 있게 했다.

    경우 문구(예)
    없는 상위 M1 메뉴의 상위 메뉴(X9)를 찾을 수 없습니다. 메뉴 관리에서 상위 메뉴를 바로잡은 뒤 다시 저장하세요.
    순환 상위 메뉴가 순환합니다(L1 → A → B → A). 메뉴 관리에서 상위 메뉴를 바로잡은 뒤 다시 저장하세요.
    • 있는 메뉴까지만 저장하면, 관리자가 메뉴 관리에서 상위를 고친 뒤 권한 관리에서 다시 저장해야 하는데 그 사실을 알 길이 없다. 그래서 거절한다(사용자 결정).
    • 순환은 화면 메뉴에서 거슬러 오르는 경로에 같은 메뉴가 다시 나올 때만이다. 여러 메뉴가 같은 상위를 갖는 것(공유 상위)은 순환이 아니라 그대로 저장된다.
    • 거절은 역할 메뉴를 지우고 넣기 전에 난다. 앞서 처리한 역할 그리드 변경도 save 의 트랜잭션과 함께 롤백된다.
    • 같은 상위는 한 번만 조회한다. 종전에는 공유 상위를 단계마다 다시 조회했다. 넣는 메뉴와 순서는 같다.
    • 문구는 새 MSG 코드 없이 같은 서비스의 다른 거절처럼 문장을 그대로 쓴다. 문장은 MessageFormat 을 한 번 거치므로 작은따옴표와 중괄호를 쓰지 않았다.

    확인¶

    RoleMenuSaveUpperMenuTest: DAO 는 목이고, 없는 ID 에는 운영처럼 null 을 돌려준다. 메시지 소스는 운영과 같은 LocaleMessageSource 를 쓴다.

    순환 상위(L1→A→B→A) StackOverflowError 거절, 지우거나 넣는 호출 0

    첨부 다운로드 zip 에서 같은 이름 첨부가 빠지거나 전체가 실패하던 것 (PR #264, Infra #95)¶

    외부(eBiz, API)가 부르는 무인증 첨부 다운로드 두 경로가 zip 안 이름이 겹칠 때 망가졌다. 원인은 같다 — 같은 이름을 두 번 넣으면 ZipOutputStream.putNextEntry 가 ZipException: duplicate entry 를 던진다. 증상은 경로마다 달랐다.

    • 일괄 GET /api/partner/downloadAll(B/L 단위, Infra #95 2-6): zip 안 이름을 첨부마다 CNTR_NO + ".zip" 으로 고정해, 한 관리번호에 첨부가 2건 이상이면 두 번째에서 예외가 났다. 항목별 catch 가 없어 다운로드 전체가 실패한다. 응답이 500 과 Tomcat 오류 HTML(455바이트)로 바뀌는데 Content-Disposition: attachment; filename="<B/L>.zip" 은 이미 붙어 있어, 브라우저는 열리지 않는 <B/L>.zip 을 저장한다. 첫 번째 첨부도 받지 못한다.
    • 단건 GET /api/partner/download(관리번호 단위, Infra #95 2-19): 이름은 원래 파일명이었지만 같은 이름 첨부가 있으면 항목별 catch 가 그 예외를 로그로만 남기고 넘어가, 200 인데 두 번째 첨부가 조용히 빠졌다.

    바꾼 것¶

    • 두 경로가 이름 짓기 규칙 하나(zipEntryName)를 같이 쓴다. 루프는 각자 그대로다.
    • zip 안 이름은 첨부의 원래 파일명(FILE_NM)이다. 응답 안에서 이미 쓴 이름이면 확장자 앞에 번호를 붙인다(SZLU2020267.zip, SZLU2020267 (2).zip, SZLU2020267 (3).zip). 대소문자만 다른 이름도 겹친 것으로 본다(Windows 에서 풀면 겹친다).
    • 경로로 해석될 문자는 남기지 않는다(zip slip). 마지막 /, \ 뒤만 쓰고 연속된 점은 하나로 줄인다(../../evil.zip → evil.zip, UETU2386091..zip → UETU2386091.zip). 남는 이름이 없으면 NAS 저장명(SAVE_NM)을 쓴다. 단건 경로는 종전에 FILE_NM 을 그대로 써서 경로 문자도 그대로 들어갔다.
    • 응답 파일명(Content-Disposition), 무인증, 호출 로그는 그대로다. 단건은 eBiz 호출이면 [<B/L>] <CNTR_NO>.zip, HBLNO 없는 호출이면 <MNGT_NO>.zip, 일괄은 <B/L>.zip.

    사용자에게 보이는 변화¶

    NAS 로그인이 거절되면 FtpServiceInq 가 예외를 던짐 (PR #265, Infra #95)¶

    FtpServiceInq 의 raw FTPClient 접속 공통부(open())가 login() 결과를 보지 않았다. NAS 비밀번호가 틀리거나 계정이 잠기면 예외 없이 이렇게 됐다.

    • listNames: NLST 가 거절돼 빈 목록
    • existsBatch: SIZE 가 전부 거절돼 모든 파일이 '없음'
    • 삭제(delete)는 뒤이은 TYPE I 응답(530)이 연결 확인에 걸려 예외가 났으므로 문제없었다.

    그래서 파일 정합성 점검(관리자 화면)이 NAS 로그인 장애를 "점검한 파일이 전부 실제 파일 없음(MISSING)" 으로 보고할 수 있었다. 이 화면의 "MISSING 삭제문 생성" 은 그 행들로 TB_CMS_ATFILE DELETE 스크립트를 만든다.

    바꾼 것¶

    open() 에서 login() 이 false 면 FileSystemException("[FileSystem Error] FTP 로그인 실패 (replyCode=530): <서버 응답>") 을 던진다. 세 메서드(listNames, existsBatch, delete)에 모두 적용되고, 로그인 뒤 명령(TYPE, NLST, SIZE, CWD, DELE)은 보내지 않는다. 계정 정보는 문구에 넣지 않는다.

    • 포탈시스템 축: existsBatch 가 던지면 전 행이 SCAN_ERROR("포탈 NAS 확인 실패")다.
    • SCAN_ERROR 는 "MISSING 삭제문 생성" 대상이 아니다.
    • 응답 자체는 200 이다(서비스가 폴더 단위로 잡아 결과 행으로 바꾼다). 삭제 경로는 종전처럼 실패로 처리된다(문구만 바뀜).

    스트리밍 파싱 NPE — 셀 주소(r) 없는 엑셀 (PR #257)¶

    어제 배포한 스트리밍 파싱(PR #252)에서 업로드가 거절되는 회귀가 났다. 운영 에러 로그:

    POST /api/vms/comm/uploadExcel   file: SKLU1590876.xlsx (2,832 bytes)
WebServiceException: Failed to read the Excel file. [row 2]
  Cause: NullPointerException: Cannot invoke "String.length()" because "cellRef" is null

    원인 — <c> 의 r 속성은 선택이다¶

    스트리밍 핸들러는 몇 번째 열인지를 셀 주소("C12")에서 직접 계산한다. SAX 가 빈 칸을 건너뛰기 때문에 순서만 믿으면 열이 밀려서다.

    그런데 그 주소가 없을 수 있다. OOXML 에서 <c> 의 r 속성은 선택이고, POI 는 없으면 그대로 null 을 넘긴다.

    // XSSFSheetXMLHandler.java:269
cellRef = attributes.getValue("r");   // 없으면 null → output.cell(cellRef, …)

    엑셀로 저장한 파일엔 보통 들어 있다. 다른 도구가 만든 파일엔 없다. 전환 전 DOM 경로는 row.getCell(i) 인덱스 접근이라 이 속성과 무관했고, 내가 쓴 테스트 파일(SheetJS)은 항상 r 을 넣어서 검증에서 안 걸렸다.

    조치¶

    주소가 없으면 행 안에서 순서대로 센다. 있으면 종전대로 주소를 쓴다(빈 칸이 있어도 안 밀린다).

    int ci = (ref == null) ? nextCol : columnIndexOf(ref);
if (ci < 0) return;
nextCol = ci + 1;

    검증¶

    crs5000.xlsx 의 시트 XML 에서 <c> 의 r 속성 75,030개를 지운 재현 파일(noref.xlsx)을 만들어 대조했다.

    파일 수정 전 수정 후
    r 속성 없음 ❌ NPE(운영과 같은 메시지) ✅ 5,000행
    r 속성 있음 ✅ 5,000행 ✅ 5,000행 (결과 동일)

    실제 엔드포인트 E2E 도 통과했다 — noref.xlsx 5,000행 0.8초, 응답 크기가 정상 파일과 같다.

    영향¶

    배포(10-21 18:45 KST) 후 실패 4건, 성공 32건. 실패는 10-22 09:33~09:34 한 사용자에 몰려 있다. 대부분의 파일은 엑셀이 만들어 r 이 있으므로 전면 장애는 아니었지만, 그 도구로 파일을 만드는 사용자는 계속 막힌다.

    힙 여유가 없으면 업로드를 받지 않는다 (PR #259)¶

    2026-10-19 OOM(Infra #94)의 마지막 안전장치. 이미 찬 힙은 비울 방법이 없으므로(GC 는 이미 최선을 다한다), 제어 가능한 변수는 "더 넣지 않는 것" 하나뿐이다.

    왜 이메일 알림으로는 안 되나¶

    먼저 알림을 검토했다가 접었다. 실측이 분명했다.

    ① 사람이 반응할 시간이 없다 — 10-19 에 힙이 1분 만에 374MB → 511MB 로 올라 터졌다. Azure 평가 주기 1분 + 메일 지연을 더하면 도착 시점엔 이미 끝나 있다.

    ② 예보가 되는 임계값이 없다 — 사고 직전 20분(5분 창 최대값)이 평상시와 구별되지 않는다.

    10:20  412MB     10:30  398MB
10:25  438MB     10:35  406MB
10:40  511MB  ← OOM 이 일어난 바로 그 창
    임계(5분 최대) 발동 빈도(14일 실측)
    420MB 10.1회/일
    450MB 5.3회/일
    470MB 3.0회/일
    490MB 1.0회/일

    구별 가능한 값(490MB)은 OOM 과 같은 창에서만 나온다. 일찍 알려고 420 에 걸면 멀쩡한 날에도 하루 10통이다.

    조치 — 앱이 스스로 거절한다¶

    파싱을 시작하기 직전에 힙 여유를 보고, 100MB 미만이면 받지 않는다.

    if (freeHeapBytes() < MIN_FREE_HEAP_BYTES) {
    throw this.errorMessage(RETRY_LATER_MESSAGE).build();
}
    • 게이트를 잡은 뒤에 본다 — 줄 서기 전 값은 파싱 시점엔 낡은 값이다
    • 100MB 인 근거: 상한(2만 행) 업로드 1건의 최대 힙 증가가 40~62MB(실측). 운영 힙 상한 512MB 이므로 사용량 412MB 초과 시에만 걸리고, 최근 7일 기준 그런 순간은 전체의 0.59% 다

    문구를 바꿨다¶

    Uploads are processed a few at a time. Please try again in about a minute.

    종전 게이트 문구("The server is busy…")의 "busy(혼잡)" 를 걷어냈다. 서버 사정을 드러내지 않고 "원래 정해진 제한" 으로 읽히게 쓴다 — 실제로 동시 2건 제한이 있으니 사실과도 맞고, 사용자가 장애로 오인하지 않는다. "약 1분" 을 붙여 연타 재시도를 줄인다.

    게이트 대기 초과와 힙 부족 두 거절이 같은 문구를 쓴다. 사용자 입장에선 구분할 이유가 없다.

    검증¶

    임계를 일부러 높여 강제 발동시켜 응답을 확인했다.

    HTTP 409  errDiv "01"  unknown false
message: "Uploads are processed a few at a time. Please try again in about a minute."

    unknown:false 라 프론트가 문구를 그대로 표시하고, errDiv 01 로 에러 로그에도 남는다(모니터링 가능). 임계 원복 후 5천/2만행/r 속성 없는 파일 모두 정상 업로드를 재확인했다.

    서버 로그는 둘을 구분한다¶

    사용자 문구는 같지만 대응이 다르므로(대기 초과 = 동시 업로드 지속 / 힙 부족 = 메모리 압박) 로그는 갈라서 남긴다.

    [EXCEL GUARD] gate-timeout waited=60s file=...
[EXCEL GUARD] heap-low free=87MB min=100MB max=512MB file=...

    [EXCEL GUARD] 를 Azure 알림이 잡는다(Infra alerts.bicep). 힙 수치 임계와 달리 이건 오탐이 거의 없는 신호다 — 울렸다는 건 실제로 일을 거절했다는 뜻이다.

    남는 것¶

    이 가드는 마지막 안전장치지 근본 해결이 아니다. 평상시 힙 여유가 100MB 안팎인 구조는 그대로이고, Infra #94 1순위로 남아 있다. 가드가 실제로 발동하기 시작하면 그 신호를 받아 상한 하향·게이트 1건·증설을 검토한다.

    commons-lang3 3.17.0 → 3.18.0 (PR #258, Infra #89)¶

    Spring Boot BOM 이 commons-lang3 를 3.17.0 으로 고정해, poi 의 commons-compress 1.28.0 이 요구하는 3.18.0 이 3.17.0 으로 내려가 있었다(3.5.14 때부터 같음). 3.17.0 에는 CVE-2025-48924(ClassUtils.getClass 에 아주 긴 입력을 주면 재귀가 깊어져 StackOverflowError, 서비스 거부)가 있고 3.18.0 에서 고쳐졌다. build.gradle 에 3.18.0 을 직접 적어 BOM 보다 높게 잡았다(commons-io, commons-net 과 같은 방식).

    • 우리 코드는 StringUtils 만 쓰고 lang3 의 ClassUtils 는 쓰지 않아 실제 노출은 거의 없었다. 보안 스캐너(Trivy, Dependabot)에 계속 걸려 정리했다.
    • 런타임 클래스패스에서 바뀐 것은 commons-lang3 하나다.
    • 빌드와 테스트, 9050 기동 비교(엔드포인트 매핑, 인증 없는 응답, 공개 API 응답, 기동 경고)가 전후 같다.

    자동번호 카운트 저장을 한 트랜잭션으로 묶음 (PR #261, Infra #95)¶

    자동번호 카운트 관리 화면(CmsAutonoCount)의 저장 POST /api/cms/setting/cmsAutonoCount/saveCount 에 트랜잭션이 없었다. MyBatis 는 트랜잭션 밖에서 문장마다 커밋하므로, 여러 행을 저장하다 중간 행이 실패하면 앞 행은 이미 커밋된 채로 화면에는 실패가 떴다.

    첨부 이미지 목록에서 초대형 PDF 는 그 첨부만 건너뜀 (PR #266, Infra #95)¶

    POST /api/file/getBase64ImageList(수리 이미지 뷰어, 무인증)는 첨부 중 초대형 PDF 가 하나라도 있으면 목록 전체가 500 이었다. 나머지 사진도 볼 수 없었다. 이제 그 PDF 만 빠지고 나머지는 그대로 보인다.

    왜 그랬나¶

    • PDFUtil.convertToImage 는 하한 DPI(72)로도 픽셀 상한(40MP)을 넘으면 렌더를 포기하고 RenderTooLargeException 을 던진다(2026-09 PDF OOM 가드, PR #147).
    • getBase64ImageList 에는 이 예외를 잡아 그 첨부만 건너뛰는 catch 가 있었다. 그런데 downloadFile 이 모든 예외를 RuntimeException("[SAVE_NM] Failed to download and resize image.") 으로 감싸 던져서, 타입으로 잡는 그 catch 는 넣은 커밋 때부터 한 번도 타지 않았다.
    • ZIP 첨부 안의 PDF 도 같았다. 여기는 processSingleFile 이 직접 렌더해 감싸지 않은 채로 오지만, ZIP 분기의 catch 는 550(NAS 에 파일 없음)이 아니면 그대로 던졌다.

    바꾼 것¶

    • PDF 첨부: 마지막 catch 에서 원인 사슬에 RenderTooLargeException 이 있으면 그 첨부만 건너뛴다(550 판정 isNasFileMissing 과 같은 방식). 타지 않던 타입 catch 는 지웠다.
    • ZIP 안의 PDF: processSingleFile 에서 그 항목만 뺀다. ZIP 의 나머지 항목과 다른 첨부는 그대로다. ZIP 을 통째로 버리지 않는다.
    • 건너뛸 때 FILE_SN, SAVE_NM(ZIP 이면 항목 이름)을 경고 로그로 남긴다.

    2026-09 PDF OOM 조각의 "해당 첨부만 스킵" 설명은 이제 사실과 맞다.

    그대로 둔 것¶

    • 단건 POST /api/file/getBase64Image 는 종전대로 던진다(한 장만 보는 화면이라 건너뛸 대상이 없다).
    • 깨진 PDF, NAS 통신 오류 같은 다른 예외는 종전대로 목록 전체 실패다. 550 은 종전대로 건너뛴다.
    • 응답 형식, 이미지, 순서.

    운영¶

    • 최근 90일 이 500 은 0건이다(잠복 결함). PDF 다운스케일 로그([PDFIMG])는 42건, 가장 큰 문서가 150 DPI 기준 80MP(37쪽)였다. 하드 상한은 150 DPI 로 환산하면 약 174MP(A4 약 80쪽)라 운영 조회에서는 아직 닿은 적이 없다.
    • 다만 그런 첨부는 실제로 있다. .100 의 월 정산 PDF 두 건(169쪽 28MB, 191쪽 58MB)이 하한 72 DPI 로도 85MP, 96MP 라 상한을 넘는다.

    Pebble 엔진과 뷰리졸버를 한 벌로 합침 (PR #251, Infra #86)¶

    Pebble 엔진과 뷰리졸버가 두 벌씩 떠 있었다. 하나로 합치면서, 브라우저 요청의 에러 화면(error 뷰)이 템플릿을 못 찾아 렌더되지 않던 문제도 같이 풀렸다. 메일 본문과 인증 실패 HTML 은 그대로다.

    두 벌이었던 이유¶

    • 커스텀 빈은 createPebbleEngine(PebbleTemplateEngineConfiguration)과 createPebbleViewResolver(ViewConfiguration)다.
    • pebble-spring-boot-starter 자동구성은 같은 종류의 빈이 있는지를 타입이 아니라 이름(pebbleEngine, pebbleViewResolver)으로 본다. 이름이 달라 스타터도 엔진, 로더, 뷰리졸버를 따로 만들었다.
    • 테스트 컨텍스트로 세면 엔진 2개, 뷰리졸버 2개였다.

    실제로 어느 쪽이 쓰였나¶

    • 메일(AdminService 의 mail/find-my-password, mail/confirm-code)과 인증 실패 HTML 은 커스텀 엔진을 썼다. 로더 prefix 가 template/ 이라 잘 렌더됐다.
    • ViewConfiguration 의 @Autowired PebbleEngine pebbleEngine 과 WebMvcConfiguration 의 @Autowired PebbleViewResolver pebbleViewResolver 는 후보가 둘이라 필드 이름으로 골라졌고, 둘 다 스타터 빈이 들어갔다.
    • PebbleViewResolver 는 초기화 때 자기 prefix 를 엔진 로더에 덮어쓴다. 두 리졸버가 스타터 엔진 하나를 같이 써서, 로더 prefix 는 나중에 초기화된 쪽 값(static/ 또는 classpath:template/)이 됐다. 어느 쪽이든 ClassLoader 로는 error.html 을 찾지 못한다.
    • 그래서 Accept 에 text/html 이 있는 요청에서 예외가 나거나 GET /error 를 열면 Could not find template 으로 렌더가 실패했다.

    바꾼 것¶

    • VpApplication 의 exclude 에 PebbleAutoConfiguration 을 더했다. 엔진과 뷰리졸버는 커스텀 한 벌만 남는다. 스타터 의존성은 남겨 두었다.
    • createPebbleViewResolver 는 엔진과 같은 pebble.prefix, pebble.suffix 를 쓴다. 이제 메일과 엔진을 같이 쓰므로, 다른 값을 넣으면 초기화 때 메일 쪽 로더 prefix 까지 바뀐다.
    • 쓰는 곳이 없어진 pebble.resolver 설정(PebbleProperty.Resolver)을 지웠다. application.yaml.example 에서도 뺐다. 배포 설정에 남아 있어도 읽지 않으므로 무해하다.

    동작이 바뀌는 것¶

    • error 뷰가 이제 렌더된다. 브라우저로 연 요청이 실패하면 500 렌더 실패 대신 예외에 맞는 상태코드와 template/error.html(메시지 포함)이 나간다.
    • 뷰 렌더 엔진에 스타터가 넣던 SpringExtension 이 빠진다. 템플릿 중 이 확장의 함수(message, href 등)를 쓰는 곳은 없다.

    그대로 둔 것¶

    • pebble.cache 는 PebbleProperty.cacheActive 에 묶이지 않는다(묶이는 키는 pebble.cache-active). 지금 값이 둘 다 false 라 결과는 같다.
    • template/mail/ 아래 10종 중 코드가 쓰는 것은 2종뿐이다(shipping/ 7종과 order/update-order 는 참조 없음).

    확인¶

    • PebbleEngineConfigurationTest(3건). Pebble 설정 클래스만 올리고, 스타터 자동구성은 VpApplication 의 exclude 를 그대로 따른다.
      • 엔진과 뷰리졸버가 1개씩이고 메일 컴파일러와 뷰리졸버가 같은 엔진을 쓴다.
      • 메일 2종과 인증 실패 HTML(error)의 렌더 문자열이 그대로다. 메시지의 HTML 이스케이프도 고정했다.

    첨부 이미지 조회가 PDF 를 한 번만 받아 한 번만 렌더함 (PR #250, Infra #86)¶

    POST /api/file/getBase64ImageList(수리 이미지 뷰어, 무인증)와 POST /api/file/getBase64Image 가 PDF 첨부 1건마다 NAS 에서 2번 받고 2번 렌더하던 것을 1번씩으로 줄였다. 응답은 바뀌지 않는다.

    왜 두 번이었나¶

    • downloadFile 이 PDF 를 받아 PDFUtil.convertToImage 로 렌더(PNG)한 뒤, 그 PNG 를 다시 디코드해 JPEG 로 써서 돌려줬다.
    • 호출부 두 곳은 그 JPEG 를 받아 놓고, PDF 면 retrieveFileFromFtp 로 다시 받아 다시 렌더한 PNG 로 덮어썼다. 첫 번째 결과는 버려졌다.
    • 그래서 응답은 처음부터 두 번째 렌더의 PNG 였다.

    바꾼 것¶

    • downloadFile 의 PDF 분기는 렌더한 PNG 를 그대로 돌려준다(JPEG 로 다시 쓰지 않는다). 이미지 파일 분기는 그대로다.
    • getBase64ImageList, getBase64Image 에서 PDF 를 다시 받고 다시 렌더하던 줄을 지웠다.
    • PDF 1건당 줄어드는 것: NAS 다운로드 1번, 렌더 1번, 그리고 버려지던 PNG 디코드와 JPEG 인코딩(병합 이미지 크기의 이미지를 두 장 더 만들던 단계).

    그대로 둔 것¶

    • 응답: 이미지 개수, 순서, base64 문자열, FILE_SN, FILE_NM, 단건의 fileExt.
    • 예외 처리: 실패는 종전처럼 downloadFile 안에서 RuntimeException("[SAVE_NM] Failed to download and resize image.") 으로 감싸 던진다. NAS 에 없는 파일(550)은 목록에서는 건너뛰고, 단건에서는 던진다.
    • PDF 는 FILE_MODE 가 ETC(포탈시스템 폴백 행)여도 종전처럼 uploadPath 에서 받는다.
    • 무인증(permit-all)과 소유 검증.
    • 초대형 PDF(RenderTooLargeException)는 종전대로 목록 요청 전체가 실패한다. getBase64ImageList 에 이 예외를 잡아 그 첨부만 건너뛰는 catch 가 있지만, downloadFile 이 예외를 감싸 던지기 때문에 그 catch 를 넣었을 때부터 타지 않았다. 동작을 바꾸는 것은 별건으로 남긴다.

    확인¶

    • FileDataServiceBase64ImageTest 14개를 새로 만들어 바꾸기 전 코드에서 먼저 통과시켰다(그때 PDF 횟수 단언은 2). 바꾼 뒤에는 횟수 단언만 1 로 고쳐 다시 통과시켰다. 이미지와 예외 단언은 고치지 않았다.
      • NAS 는 FTPClient 가짜로 바꿔 경로별 다운로드 횟수를 세고, 렌더는 실제로 돌리면서 PDFUtil.convertToImage 호출 횟수를 센다.
      • 목록: PDF 1건, 여러 쪽 PDF(세로로 이어붙인 한 장), 이미지 파일(JPEG 로 다시 씀), 일반 파일(받지 않고 건너뜀), 섞인 목록의 순서, 포탈 폴백 PDF 의 경로, NAS 에 없는 PDF(건너뜀), 초대형 PDF(전체 실패), 깨진 PDF(전체 실패)
      • 단건: PDF, 이미지 파일, 일반 파일(디코드 실패), 초대형 PDF, 소유 검증 거절(빈 응답)
    • 횟수 단언을 2 로 둔 채 바꾼 코드로 돌리면 PDF 정상 경로 5개만 "2번 기대, 1번 호출" 로 실패했다.

    open() 에 넣지 않은 것¶

    • 파일 형식(TYPE I): 호출부에 남겼다. deleteInternal 은 그 앞에 CWD 를 보내는데, 파일 경로로 가는 CWD 는 550 이 나고 바로 뒤 TYPE I 응답(200)이 연결 확인(getReplyCode)에 읽혀 통과한다. TYPE I 를 open() 에 넣으면 CWD 가 뒤로 밀려 모든 삭제가 "FTP 서버 연결 실패 (replyCode=550)" 로 실패한다.
    • FTPClient 생성: 호출부가 만들어 넘긴다. 로그인 중 예외가 나도 호출부 finally 가 disconnect 할 수 있어야 해서다.
    • 로그인 결과 확인과 재시도는 종전대로 없다(재시도는 send 만).

    테스트¶

    FtpServiceInqTest 5개에서 18개로. 새 13개는 가짜 FTP 서버(MockFtpServer 의 FakeFtpServer)에 실제로 붙어 서버가 받은 명령을 순서대로 기록한다. 바꾸기 전 코드에서 먼저 통과시킨 뒤 옮겼다.

    • listNames: 정상(명령 순서 USER, PASS, TYPE I, PASV, NLST, QUIT), 없는 폴더는 빈 목록, 로그인 실패는 빈 목록(현행), 접속 실패는 FileSystemException
    • existsBatch: 같은 경로는 SIZE 한 번, 빈 입력은 접속 안 함, 로그인 실패는 전부 '없음'(현행), 접속 실패는 FileSystemException
    • delete: 정상(한글 파일명으로 UTF-8 확인, CWD 다음 TYPE I 순서), 550 은 성공 처리, 그 밖의 거부는 예외, 로그인 실패는 replyCode=530 예외, 접속 실패는 예외

    엑셀 업로드 스트리밍 파싱 + 동시 2건 게이트, 상한 2만 행 (PR #252)¶

    2026-10-19 엑셀 업로드 한 건이 백엔드 레플리카 2개를 모두 OOM 으로 죽인 건(Infra #94)의 근본 조치다. 파싱을 스트리밍으로 바꾸고, 그 덕에 생긴 여유로 상한을 5,000 → 20,000행으로 올리되, 동시 업로드가 그 여유를 다 먹지 않도록 동시 2건 게이트를 함께 넣는다. 셋은 같이 가야 한다 — 게이트 없이 상한만 올리면 실측대로 터진다.

    무엇이 문제였나¶

    WorkbookFactory.create() 는 워크북 전체를 힙에 올린다. 운영 힙은 2Gi 컨테이너의 25%인 512MB 뿐이고 평상시에도 390~440MB 가 차 있어 여유가 100MB 안팎이다.

    실측 (POI 5.5.1, -Xmx512m, CRS 견적 14컬럼)¶

    행수 파일 현재(DOM) 힙 현재 시간 스트리밍 힙 스트리밍 시간
    5,000 561 KB 63 MB 2.8초 10 MB 1.1초
    20,000 2.2 MB 236 MB 17.2초 29 MB 1.4초
    50,000 5.4 MB OOM — 68 MB 2.2초
    100,000 11 MB — — 131 MB 3.2초

    파서 자체는 행수와 무관하게 4MB 고정이다. 남는 비용은 결과 List<DMap>(행당 약 1.37KB)뿐이라, 같은 여유 100MB 로 3~5만 행까지 받을 수 있다. 무제한은 아니다.

    ★덤으로 잡은 데이터 유실 버그¶

    루프 상한이 getTotalRowCountIncludingHidden(sheet) — 물리 행 개수였다. 빈 행이 있으면 개수가 마지막 행 번호보다 작아져 맨 뒤 행이 조용히 잘렸다.

    빈 행이 섞인 파일   종전 DOM 4행  /  스트리밍 5행   ← 마지막 행이 사라져 있었다

    빈 행 1개당 1행 유실이다. 형제 루프(uploadExcelMvsCntrMove, uploadExcelFdsCntrMove)는 처음부터 <= getLastRowNum() 을 쓰고 있었고, 이 메서드만 달랐다. .xls 경로도 같이 고쳐 둘을 맞췄고, 이제 아무도 안 쓰는 getTotalRowCountIncludingHidden 은 지웠다. 조건식 안에서 매 반복 시트를 통째로 세던 O(n²) 도 함께 사라진다(2만 행 17.2초 → DOM 에서도 크게 줄어든다).

    동등성 검증¶

    운영 코드의 두 경로를 그대로 흉내낸 하네스로 결과를 행 단위 대조했다. 정상 파일, 빈 칸이 섞인 파일, 빈 행이 있는 파일, 2만 행 파일 전부 완전 일치한다(헤더 키와 null 자리까지).

    이식하면서 밟은 함정¶

    • ★XMLHelper.newXMLReader() 를 써야 한다. SAXParserFactory.newInstance() 는 기본이 namespace-unaware 라 localName 이 비고 핸들러가 한 번도 안 불린다 — 에러도 없이 0행이 나온다. 실제로 여기 걸렸다
    • ★SAX 는 빈 칸을 건너뛴다. 순서대로 들어온다고 가정하면 빈 칸이 있는 행에서 열이 통째로 밀린다. 셀 주소("C12")에서 열 인덱스를 직접 계산한다
    • 값 없는 칸도 키는 넣는다 — DOM 경로의 data.put(headerName, null) 과 같은 계약을 맞춰야 프론트 검증이 그대로 동작한다
    • OPCPackage 는 파일 판을 쓴다. InputStream 판은 전체를 메모리에 올려 스트리밍 이득이 사라진다. 임시 파일로 복사 후 열고 finally 에서 지운다

    남는 것¶

    • .xls 는 스트리밍이 안 된다 — XSSFReader 는 OOXML 전용이라 종전 DOM 경로를 유지한다(컨트롤러 크기 상한이 막아준다). HSSF 이벤트 API 는 별건
    • 수식은 캐시 결과값을 읽는다 — 종전 evaluateInCell 은 재계산이었다. 엑셀이 저장할 때 넣어둔 값을 쓰므로 보통 같지만 동작 차이는 맞다
    • uploadExcelMvsCntrMove / uploadExcelFdsCntrMove 는 고정 컬럼 자체 루프라 이번 전환 대상이 아니다. 둘은 행수 상한도 없다 — 크기 상한만으로 막히고 있다(Infra #94)

    상한을 2만 행으로 올린다 — 단, 동시성 게이트와 함께¶

    전환 뒤 2만 행 1건은 힙 약 40MB 다. 2026-10-19 장애를 낸 파일이 약 2만 행이라 그 업무가 통과한다.

    문제는 동시 업로드다. 행수 상한은 "한 번에 몇 행" 만 막지 "동시에 몇 건" 은 못 막는다.

    2만 행 파일 최대 힙 증가
    1건 +40 MB
    10건 동시, 게이트 없음 +387 MB
    10건 동시, 게이트 2 +166 MB
    12건 동시, 게이트 2 +199 MB

    운영 실측으로 최근 30일 6,793건, 같은 분에 최대 12건(p95 5건, p50 2건)이라 동시 업로드는 가정이 아니라 현실이다.

    동시 상한을 행수로 떠안기면 한 사람 몫이 10명 몫으로 깎인다. 그래서 "한 번에 몇 행"(2만)과 "동시에 몇 건"(2)을 분리했다. 넘치는 요청은 거절이 아니라 대기한다(12명이 몰려도 전체 3.1초, 대기 상한 60초).

    ⚠️게이트는 파싱만 묶는다¶

    컨트롤러가 return 한 뒤 finally 에서 세마포어를 놓고, 그 다음에 Spring 이 응답 JSON 을 직렬화한다(2만 행이면 6.7MB). 그 몫은 게이트 밖이라 2 × 40MB = 80MB 로는 안 떨어지고 위 표의 166~199MB 에 머문다.

    운영 힙 여유가 100MB 안팎이므로 이 수치는 여유를 넘는다. 즉 12명이 동시에 2만 행짜리를 올리면 여전히 위험하다. 다만 지금까지 관측된 분당 12건 버스트는 평균 158행짜리 일반 파일이고, 2만 행은 이상치다. 더 줄이려면 응답을 스트리밍해야 하고, 그건 Infra #94 에 남긴다.

    동시성 실측 (참고, 게이트 2 / 12건 동시)¶

    파일당 행수 최대 힙 증가
    5,000 +84 MB
    10,000 +149 MB
    20,000 +199 MB

    상한을 내려야 할 일이 생기면 이 표를 근거로 삼는다.

    자리수보다 짧은 날짜 값이 500 이었다 (Infra #87 1-10)¶

    이름이 _DT(8자리), _DI(12), _DY(4), _DM(6)로 끝나는 컬럼과 파라미터는 -, T, : 를 지운 뒤 그 자리수만큼 자른다. 값이 자리수보다 짧으면 substring 이 StringIndexOutOfBoundsException 을 내 화면에는 어느 칸이 문제인지 없이 500 이 떴다(.100 에러로그 18건, 레거시 시절).

    이제 자리수보다 짧으면 컬럼명을 담은 업무 에러(409)로 돌려준다.

    Invalid date value for ETD_DT: '2026101' (needs 8 digits).

    길거나 같은 값, 빈 값, 날짜가 아닌 컬럼, VSL_DT 는 종전 그대로다. 짧은 값은 종전에도 저장이 막혔으므로 새로 막히는 경우는 없다.

    리터럴 폴백 경로의 자르기와 이스케이프 순서 (Infra #91 7번)¶

    • 기동 시
    • 목록에 없는 이름이 왔을 때 — 새 화면 배포 직후용. 1분에 한 번으로 묶는다
    • 매일 03:00(KST) — 지운 프로시저가 옛 목록에 남는 기간을 하루로. 백엔드의 첫 @Scheduled 작업이라 SchedulingConfiguration 을 추가했다
    • 받기에 실패하거나 내용이 이상하면(빈 목록, 형식 위반) 이전 목록을 쓴다. 한 번도 못 받았으면 판정하지 않는다.

    첨부 업로드 — NAS 전송을 트랜잭션 밖으로, 파트 개수 상한 상향¶

    운영에서 같은 업로드 경로가 두 가지로 깨지고 있었다. 원인이 다르지만 고칠 자리가 겹쳐 함께 묶는다.

    ① 한 장이 실패하면 앞서 올라간 파일이 고아가 됐다¶

    uploadFile 은 한 트랜잭션 안에서 파일마다 INSERT → NAS 전송 을 돌렸다. N 장 중 한 장이라도 전송에 실패하면 DB 행은 전부 롤백되는데 NAS 에 올라간 파일은 그대로 남는다.

    2026-10-18 17:09  CrsEstimate, 8장 업로드
  962621~962626   전송 성공 (343~511ms)
  962627          전송 실패 (10,264ms — passive 데이터 채널 connect 타임아웃)
  → 7장치 INSERT 전부 롤백, NAS 에 고아 6개
  → 사용자는 3분 뒤 8장을 통째로 재업로드

    NAS 는 롤백 대상이 아니므로 "DB 를 되돌린다" 가 정합성을 지켜주지 못한다. 되돌리지 못하는 쪽을 뒤에 둔다 — 파일마다 전송을 먼저 하고, 성공한 건만 짧은 트랜잭션으로 INSERT 한다.

    • 전송 실패 → DB 에 아무것도 안 씀 → 고아 0
    • 성공분은 그대로 등록되고, 전부 실패했을 때만 첫 예외를 그대로 던진다(한 장만 보내는 화면은 동작 불변)
    • ★반대 방향("DB 엔 있는데 실물이 없음")은 만들지 않는다 — 목록에 떠 있는데 다운로드가 깨지는 쪽이 더 나쁘다

    부수 효과로 DB 커넥션 점유가 사라진다. 종전엔 FTP 왕복 내내 커넥션을 쥐고 있었다(실측 p50 602ms / p95 9.7초 / 최대 66초). 업로드가 몰리면 풀(10)이 마르고 대기가 쌓여(active=10 / waiting=49) 같은 레플리카의 다른 요청까지 느려졌다(업로드 제외 p95 683ms → 20.6초, 2026-10-14 실측).

    템플릿(FORM) 교체 경로는 손대지 않았다 — 기존 행 삭제(DB)와 기존 파일 삭제(NAS)가 묶여 있어 쪼개면 "행은 지웠는데 파일이 남는" 상태가 생긴다. 관리자가 한 장씩 올리는 경로라 부분 실패 개념도 없다.

    ⚠️ 같은 빈 안에서 부르는 메서드라 @Transactional 은 프록시를 타지 못해 조용히 무시된다. 두 경로 모두 TransactionTemplate 으로 경계를 직접 잡는다. 트랜잭션 콜백은 checked 예외를 못 던지므로 운반용 래퍼로 싸 두었다가 밖에서 원형 그대로 되던진다 — 예외 타입이 바뀌면 에러 분류(ERR_DIV)와 사용자 문구가 달라진다.

    ② 파일 50장부터 "용량 초과" 로 거절됐다¶

    FdsInvoice 가 7MB 업로드에서 MaxUploadSizeExceededException 으로 막혔다(2026-10-16, 7건). 용량 문제가 아니다 — 같은 기간 단일 파일 49.7MB 가 정상 전송됐고, spring.servlet.multipart 는 1000MB 다.

    Tomcat 10.1.42 가 DoS 방어로 신설한 maxPartCount(기본 50) 였다. 업로드 본문은 파일 N개 + param 1개 라 파일 49장이 상한이었다.

    이름이 사실과 다르게 나오는 경로:

    Tomcat   FileCountLimitExceededException
   ↓     Request.parseParts → new IllegalStateException(e)   (메시지 = cause.toString())
Spring   handleParseFailure 가 size·exceed·limit·count 를 보고
   ↓     → MaxUploadSizeExceededException("Maximum upload size exceeded")

    server.tomcat.max-part-count: 210 으로 올린다. 프론트 사용자 안내 상한 200장 + param 1개 + 여유다 — 서버가 먼저 걸리면 사유를 알 수 없는 에러가 되므로 프론트 상한이 항상 더 낮아야 한다.

    다음 벽은 nginx client_max_body_size 50m 이다. 장당 140KB 스캔 기준 200장이면 약 28MB 라 서로 맞물린다.

    NAS 전송 재시도를 전송 단계까지 넓힌다¶

    BE #184 로 넣은 1회 재시도는 접속·로그인 단계(failed to create FTPClient)만 덮었다. 그때 판단은 "이미 바이트를 보낸 뒤면 재전송이 안전하지 않다" 였다.

    그 전제가 틀렸다. Spring Integration 의 RemoteFileTemplate 은 useTemporaryFileName 기본값이 true 이고 접미사가 .writing 이다(실측).

    <파일명>.writing 으로 전송 → 완료된 뒤에야 최종 이름으로 rename

    전송 중 끊기면 최종 파일은 아예 생기지 않는다. 다시 보내도 깨진 파일이나 중복이 남지 않는다(재시도가 .writing 을 덮어쓰고 다시 rename 한다). 업로드가 쓰는 어댑터(FtpConfiguration)는 이 값을 건드리지 않으므로 기본값 그대로다.

    왜 한 건으로 전체가 죽나¶

    운영 컨테이너는 2Gi 인데 -Xmx 가 없어 JVM 기본값 MaxRAMPercentage=25% 가 걸린다 → 힙 512MB(실측 510.6MB @ 99.73%). POI 는 워크북 전체를 힙에 올리므로 큰 파일 하나가 힙을 통째로 먹는다. minReplicas=2 / maxReplicas=2 라 예비가 없어 두 레플리카가 차례로 넘어가면 포털이 멈춘다.

    VmsExcelFacade.excelHeaderByData 5,000 행 크기는 작은데 열 전체 서식으로 물리적 행이 수십만인 파일. getLastRowNum() 은 O(1)

    • 근본 조치(파서 O(n²) 제거, WorkbookFactory.create(File), 스트리밍 파싱, 힙·메모리 판단)는 Infra #94 에 남아 있다

    ★정정 — 2만 행은 단독으로 OOM 을 못 낸다¶

    229 와 Infra #94 는 "2.28MB(약 2만 행)이라 힙이 터졌다" 고 적었다. 그렇지 않다. 2만 행 파일은 236MB 로, 빈 512MB 힙에서는 여유 있게 통과한다.¶

    진짜 이유는 평상시 힙에 여유가 없다는 것이다. 장애 직전 1시간(10-19 09:40~10:41)의 레플리카별 힙 최대치를 보면 톱니파로 390~440MB 까지 올라간다. 상한이 512MB 니 여유가 100MB 안팎뿐이고, 여기에 큰 업로드가 올라타면 넘친다.

    10:20  412MB    10:30  398MB    10:35  406MB    10:37  401MB
10:26  438MB(다른 레플리카)      10:25  418MB
10:42  511MB  → OOM

    ⇒ 업로드는 방아쇠지 적재량의 전부가 아니었다. 같은 일을 낼 수 있는 다른 무거운 요청이 남아 있다는 뜻이다.

    남는 일¶

    이 조각은 방아쇠를 더 좁힌 것이고 근본 조치가 아니다. Infra #94 에 남아 있다.

    • 평상시 힙 여유 100MB — 이게 본체다. 컨테이너 2Gi 중 힙은 512MB 뿐이고 나머지 약 1GB 가 비힙이다. 비힙을 줄일 수 있으면 같은 2Gi 안에서 힙을 키울 수 있다
    • getTotalRowCountIncludingHidden 의 O(n²) — 실측상 1만 행에서 3.1초→6.4초, 2만 행에서 17.2초. 크지만 OOM 의 원인은 아니다
    • WorkbookFactory.create(File) 전환, 스트리밍(XSSFReader + SAX) 전환

    • 대상은 아래 12개다. 화면별로 메뉴 역할(.100)과 프론트 호출처를 하나씩 확인했다.

    API 호출 로그 ADMIN PKG_API.SP_GET_API_LOG
    용어 사전 ADMIN PKG_CM.SP_CHK_TERM_DUP

    • 사용자 관리 메뉴는 모듈 관리자 역할에도 걸려 있지만, 삭제 버튼과 비밀번호 초기화 버튼은 ADMIN 에만 보이고 두 프로시저의 PL/SQL 도 ADMIN 만 허용한다. 그래서 두 기능은 ADMIN 전용으로 묶었다(사용자 결정). 모듈 관리자가 쓰는 사용자 조회, 저장은 그대로다.

    에러로그에 관리번호(MNGT_NO)와 멀티파트 param 기록 (PR #218, Infra #76)¶

    PR #182 로 에러로그에 호출 메뉴(MENU:)가 들어갔지만 관리번호는 빠져 있었다. 구멍은 멀티파트 하나였고, 하필 그게 첨부 업로드(FTP 장애 경로)라 2026-09-30 / 10-01 의 FileSystemException 이 어느 문서였는지 알 수 없었다.

    바뀐 모습¶

    REQUEST: POST /api/file/uploadFile
MENU: crsEstUploadExl
MNGT_NO: SEL011908000123
PAYLOAD: (multipart/form-data, 1,234,567 bytes)
  param: {"MNGT_NO":"SEL011908000123","COMP_CD":"SNKO", ...}
  files: 견적서.pdf (1,233,900 bytes)

    콘솔 한 줄: [ERR] POST /api/file/uploadFile [crsEstUploadExl MNGT_NO=SEL011908000123] : .... 관리번호는 식별자라 "콘솔에 요청 본문을 안 남긴다" 는 방침에 걸리지 않는다.

    원인 두 가지¶

    • 멀티파트 PAYLOAD 줄이 아예 안 찍히고 있었다. Tomcat 은 파트를 파싱할 때 ContentCachingRequestWrapper 를 거치지 않고 밑단 스트림을 직접 읽어 캐시가 빈 채로 남는다. 그 분기가 "캐시가 비어 있지 않으면" 안에 있었다. .100 의 과거 uploadFile 에러 4건 모두 PAYLOAD 줄이 없었다. → 멀티파트는 request.getParts() 로 파트를 직접 읽는다.
    • param 은 파일 파트처럼 온다. 프론트 FormBuilder.appendJson 이 Blob 을 넣는데, 브라우저는 File 아닌 Blob 에도 filename="blob" 을 붙인다. → filename 이 없거나(일반 폼 필드) json 이고 64KB 이하면 텍스트 파트로 보고 내용을 찍는다.

    범위¶

    • 관리번호는 JSON 바디 또는 JSON 파트의 최상위 MNGT_NO 키 하나만 본다. SEARCH.MNGT_NO, FILES[] 처럼 한 겹 안의 값은 찾지 않는다(그 요청들은 JSON 이라 PAYLOAD 에 원문이 남는다).
    • CmsDocumentPopup 은 param: {} 로 올려서 이 조치로도 관리번호가 안 남는다(화면이 업로드 뒤에 행을 만드는 구조라 로그 때문에 바꿀 자리가 아니다).
    • 파트 파싱 자체가 실패한 요청(크기 초과, 깨진 멀티파트)은 크기만 남긴다. 에러 적재는 막지 않는다.

    검증 (로컬 9050, .100)¶

    요청 결과
    업로드, param 을 filename=blob + json 으로 MNGT_NO: 줄, param: 내용(비밀번호 키 *****), 파일은 이름·크기만
    업로드, param 을 filename 없이 같음
    JSON 프로시저 호출(최상위 MNGT_NO) MNGT_NO: 줄
    경계가 깨진 멀티파트 PAYLOAD: (multipart/form-data, 24 bytes) 만, 적재 정상

REG_USER_ID 는 업로드 시 getSession().getUserId() 라 위조 불가이고 .3 914,822행 충전율 100%. ★①(견적 소유)이 맨 앞이어야 한다 — 한 견적에 여러 협력사가 올린 첨부가 섞인 경우가 1,827건 있어, 업로더 축만 쓰면 견적 소유자가 자기 첨부 일부를 잃는다. ★다운로드는 매퍼가 아니라 서비스에서 판정한다 — 매퍼에서 걸면 거절이 0건이 되어 포탈 폴백으로 흘러 같은 MNGT_NO 의 포탈 행이 대신 내려간다. ★포탈시스템(SKR_DOC_MST) 폴백 행도 같은 규칙으로 막는다 — 거기 업로더는 INS_USR 이고 우리 쪽 USER_ID 다(충전율 99.999%). 업로드는 PKG_CM.FN_CAN_SAVE_FILE 로 막았다 — ①기존 첨부가 있으면 그걸 볼 수 있는가(주인이 아니어도 같은 회사면 통과), ②첨부 0건이면 번호의 주인(수리 견적 / TB_TES_GRP_INV 의 COMP_CD+CORP_CD), ③어디에도 없으면 신규로 보고 허용. ★fn_can_access_file 로 대신하면 안 된다 — 업로더 자리에 자기자신/NULL 을 넣으면 ②/④ 로 떨어져 항상 'Y' 다. ★CORP_CD 는 파라미터가 아니라 함수가 세션 사용자로 조회한다. CSM 은 대상 밖. ★④(완전 신규로 보고 통과)가 남는 노출이다 — 미식별 813 · 포탈 문서 186 · CFS 주문(BK_NO) 9. "첨부가 아직 하나도 없는 남의 번호에 첫 파일을 심는 것" 이고 열람 유출이 아니라 무결성 문제다. ★CFS 는 두 갈래 — 송장(GRP_INV_NO, COST_TP='CFS')은 ③이 잡지만 주문(TB_CFS_ORD.BK_NO)은 TB_TES_GRP_INV 에 없어 ④로 빠진다. 9건뿐이라 막지 않기로 결정(2026-10-02). 막을 땐 소유 축이 CUST_CD 다 — 그룹인보이스의 CORP_CD 와 다르니 통일 금지. 적용 지점 4곳이 전부 닫혔고, 검증 제외 4종은 보안 문서의 "첨부 소유 검증" 절에 적었다.

    • ★배포 직후 핫픽스 3건(2026-10-02) — 게이트 로직은 맞았는데 주체(USER_ID)가 매퍼까지 가지 않아 운영에서 드러났다. ① getSessionUserId() 가 getPrincipal() 을 봐서 null → FN_CAN_ACCESS_FILE(null, …) 이 전부 'N' → 업로드 전건 거절(PR #191). ② 컨트롤러가 param.getMap("SEARCH").put("USER_ID", …) 로 주입했는데 DMap.getMap() 은 copyMap() 으로 사본을 돌려준다 — 쓴 값이 버려져 첨부 목록 0 건. 서비스에서 SEARCH 를 한 번만 꺼내 그 인스턴스를 DAO 로 넘기도록 고쳤다(b15b1d3). ③ getBase64Image 만 USER_ID 주입이 빠져 있었다 — 매뉴얼 이미지가 전부 /FORM/ 이라 템플릿 면제로 살아 있었을 뿐, 아니었으면 null 행에서 NPE(500)였다. 주입 + null 가드 추가(f917015). ⇒ 교훈: 거절을 'N'/빈 결과로 설계하면 전달이 끊겨도 조용히 전부 차단된다. 세션 값을 쓰는 게 게이트면 SQL 단위 검증으로 끝내지 말고 로그인 계정으로 그 엔드포인트를 실제 호출할 것.
