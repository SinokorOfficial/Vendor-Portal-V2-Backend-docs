    2026-10 변경 이력¶

    파이썬 바이트코드를 git 에서 제외 (PR #210)¶

    MkDocs 훅(docs-tools/changelog_hook.py)을 빌드할 때마다 생기는 docs-tools/__pycache__/*.pyc 가 커밋돼 있어, 문서를 빌드하면 매번 변경으로 잡혀 다른 커밋에 섞여 들어갔다. .gitignore 에 __pycache__/ 를 넣고 추적 중이던 .pyc 를 제거했다(로컬 파일은 남는다). 프론트 레포는 이미 제외돼 있다.

    EIR 옛 토큰 경로 삭제 (PR #207, Infra #82)¶

    "사용 X" 표시로 남아 있던 ConcurrentHashMap 토큰 경로를 지웠다. 호출처는 주석뿐이었다.

    • EirTokenService(와 EirService 위임): getValidToken, getCachedToken, 메모리 캐시 tokenCache/expireCache, 그리고 getValidToken 만 부르던 checkTokenValidate(2026-09-15 PR #142 로 현행 경로에서 빠진 뒤 잔재).
    • EirService 의 안 쓰는 PartnerService partnersService 주입 필드.
    • 컨트롤러 2곳의 옛 호출 주석.
    • 엔드포인트 GET /api/eir/getCachedToken 은 그대로다(이미 Redis 경로 getRedisToken 을 쓴다, EirResponseLog 화면이 호출).
    • 테스트: 지운 메서드의 테스트 2건 삭제(나머지 EirServiceTest 26건 통과). 로컬 기동 후 getCachedToken 200 확인.
    • 에러 로그 문구 CALL POINT: EirService.sendSIPGNew(Exception Error) 를 실제 위치인 EirSipgClient.sendSIPGNew 로 바꿨다(#205 분리로 위치가 옮겨졌다). 운영 에러 로그(TB_CMS_ERROR_LOG)를 이 문구로 검색할 때는 배포 시점 전후로 두 문구를 함께 찾을 것.

    변경 이력을 PR 마다 파일 하나로 (PR #208, FE #254)¶

    PR 여러 개가 changelog.md 의 같은 자리(그 달 섹션 맨 위)에 항목을 끼워 넣어, 하나를 머지하면 나머지가 매번 충돌했다.

    • 항목은 docs/changelog/YYYY-MM/YYYYMMDD-<브랜치슬러그>.md 에 파일 하나로 추가한다. 새 파일만 생기니 PR 끼리 충돌하지 않는다. 작성 규칙은 같은 폴더 README.md.
    • 빌드 때 MkDocs 훅(docs-tools/changelog_hook.py)이 조각을 모아 changelog.md(월 목록)와 월별 페이지(changelog-YYYY-MM.md)를 만든다. 추가 패키지는 없다. 기존 changelog.md 링크는 그대로 동작한다. docs-deploy 트리거에 docs-tools/** 를 추가했다.
    • 형식을 프론트와 맞췄다. - **제목**(참조) — 본문 한 줄 + 들여쓴 불릿이던 것을 ## 제목 (참조) + 본문 + 불릿으로 바꿨다. 기존 100개 항목의 글 내용은 그대로다(YYYYMM00-NN-…, 원래 순서 보존).

    TransUtil 오픈소스 라이선스 고지 추가 (Infra #73 3차 조사 후속)¶

    이 파일은 crizin/korean-romanizer(MIT)의 두 파일을 합친 것인데 고지가 없었다. 파일 맨 위에 출처와 MIT 전문을 넣었다. 코드 변경 없음, 호출처 0 이지만 보전(사용자 결정).

    EirService 책임별 분리 — 동작 변경 없음 (Infra #73 3차)¶

    1,145줄 한 클래스에 토큰, 서명, SIPG 전송, 프로시저 호출, 응답 로그가 모여 있던 것을 책임별 빈으로 나눴다. EirService 는 파사드로 남아 컨트롤러(EirController, PartnerController)는 그대로다. 메서드 본문은 글자 그대로 옮겼다.

    • EirService(237줄): 이중발급 방지 락(tryIssueLock, releaseIssueLock)과 조회 오케스트레이션(updateEirInfo, getEirInfo4Web)은 그대로 두고 나머지는 위임.
    • EirTokenService(461줄): 토큰 발급/검증, Redis 캐시와 분산락, 캐시 조회/비우기. evictCachedToken 은 EirSipgClient 가 불러야 해서 private 을 패키지 공개로 풀었다.
    • EirSipgClient(372줄): 요청 서명, 발급/취소 전송(sendSIPGNew), 발급 후 조회(getEirInfoFromSIPG). 비멱등 방어(자동 재시도 끔, 통신 예외 rethrow)와 비JSON 응답 가드는 그대로다.
    • EirProcedureService(159줄): PKG_EEIR 의 SP_RTNJASON, SP_SET_EIRLOG, SP_GET_EIR_INFO 호출.
    • EirResponseLogService(57줄): TB_EIR_RESPONSE_LOG 적재. EirEsbSupport(40줄): 타임아웃 설정과 비JSON 응답 요약(static).
    • 프록시 영향 없음: EIR 서비스 쪽에 @Transactional, @Async, @Cacheable 이 하나도 없고, 바깥 빈 호출(VmsCommonService, AdminService.insertErrorLog)은 원래도 다른 빈 경유였다.
    • 운영 추적 주의: 로거 이름과 예외 스택의 클래스명이 새 클래스로 바뀐다(예: getValidTokenNew 는 이제 EirTokenService.java). 에러 로그 CALL POINT: EirService.sendSIPGNew 문구는 그대로 뒀다.
    • 테스트 EirServiceTest 28건(분리 전 원본으로 먼저 고정, 분리 후 무수정 통과). HTTP 는 정적 목으로 막아 ESB 로 나가지 않는다.
    • 문서의 EirService.java:줄번호 참조를 새 클래스 기준으로 다시 맞췄다(일부는 이전부터 어긋나 있었다).
    • 문서 code-walkthrough/eir.md 에 평문으로 적혀 있던 선사별 SIPG SALT 값을 지우고 설정 키 안내로 바꿨다(공개 발행 문서, 사용자 결정으로 값 삭제만 하고 종결).

    메뉴 삭제 시 매핑도 함께 삭제 (Infra #73, FE #249 짝)¶

    메뉴 관리 화면에서 메뉴를 지우면 TB_CMS_MENU 행만 지워져 역할 메뉴(TB_CMS_ROLE_MENU), 역할 버튼(TB_CMS_ROLE_BUTTON), 즐겨찾기(TB_CMS_USER_MENU)가 고아로 남았다(FK 없음). CmsMenuMgt-mapper.xml delete 를 네 테이블을 한 블록에서 지우도록 바꿨다(changeMenuId 와 같은 PL/SQL 블록 패턴). 방문 로그(TB_CMS_VISIT_LOG)는 이력이라 남긴다.

    • 확인: .100 에 임시 메뉴와 매핑 4행을 만들고 삭제 API 호출 → 네 테이블 모두 0, 다른 메뉴 매핑은 그대로.

    메뉴 관리 API 관리자 검사 (Infra #73 중 발견)¶

    /api/cms/comm/cmsMenuMgt/*(조회, 저장, 삭제, ID 변경)에 롤 검사가 없어 협력사 계정도 메뉴를 지울 수 있었다(.100 실측). CmsMenuMgtService 의 공개 메서드 5개 첫 줄에 requireAdmin()(ROLE_ID ADMIN, CmsFileIntegrityService 와 같은 방식). 화면 메뉴는 원래 ADMIN 롤에만 부여돼 있어 정상 사용자 영향 없음.

    • 확인: 협력사(TES01) 4개 API 모두 409 "administrators only", 데이터 변화 없음 / 같은 계정에 .100 에서 ADMIN 롤을 잠시 붙이면 저장, 삭제 200(매핑까지 0) — 롤은 원복.

    예외 처리 정리 — 동작 변경 없음 (Infra #72)¶

    넓은 catch (Exception|Throwable|RuntimeException) 97건을 전수 분류했다(재throw/변환 39, 로그·오류 기록 후 계속 36, 의도된 폴백 22). 로그 없이 예외를 버리는 곳은 없었다.

    • 이유 없이 폴백하던 19곳에 이유 주석(문자열·날짜 파싱 유틸, Azure 로그 셀 파싱, Trace, DMap, 컨버터 등록, 트리 정렬 등).
    • 원인 예외를 버리고 업무 메시지만 던지던 4곳에 던지기 직전 log.error(PartnerController EIR 취소 조회, PDFUtil, 프로시저 결과 CLOB/BLOB 변환). 응답 메시지는 그대로다 — 원인을 예외에 붙이면 GlobalHandlerExceptionResolver 가 그 원인을 핸들러 인자로 넘겨 응답이 달라질 수 있어 붙이지 않았다.
    • 에러 로그 요청 정보 구성 실패(AdminService)는 조용히 "" 를 돌려주던 것을 warn 로그로 남긴다.
    • 주석 처리된 옛 코드 3곳 삭제(JWT 검증 Provider 옛 authenticate, 공지 BLOB 변환, CRS 견적 엑셀 옛 파서). Graph 메일 첨부 주석은 보존.
    • core/encrytion/Aes256Module 삭제 — 암호화 실패 시 평문을 돌려주는 폴백이 있었지만, 생성·참조하는 곳이 0 인 레거시 이관 잔재였다(Bean 아님).
    • 문서의 줄 번호를 다시 맞췄다(이번 변경으로 밀린 것 + VmsCommonService 는 #195 이후 어긋나 있던 3곳).

    미사용 AWS S3 의존성·설정 제거 (Infra #78)¶

    코드에서 S3 를 쓰는 곳이 0 이었다(파일은 NAS/FTP).

    • build.gradle: spring-cloud-aws-starter-s3 + awspring BOM 3.4.2 삭제.
    • AwsS3Property(cloud.aws.*), StorageProperty.awsS3Location, FileUtil.getAwsS3Path() 삭제(사용처 0).
    • 스토리지 초기화 껍데기 정리: StorageService 와 구현 2개(AwsS3FileService = 빈 init(), FileSystemStorageService = 쓰지 않는 file 프로파일 전용), StorageException, VpApplication 의 CommandLineRunner 삭제. 운영에서는 원래 아무 일도 안 하던 경로다.
    • 설정 예시에서 spring.cloud.aws.*, cloud.aws.*, storage.awsS3Location, com.amazonaws 로그 레벨 삭제. 실설정(application*.yaml, GitHub secret APPLICATION_AZURE_YAML)에 키가 남아 있어도 읽는 코드가 없어 무해하다.
    • 이 PR 배포 후 인프라에서 AWS env 2개(SPRING_CLOUD_AWS_CREDENTIALS_*), secretRef, KV 시크릿을 지운다(Infra #78 순서).

CSM 은 대상 밖. ★④(완전 신규로 보고 통과)가 남는 노출이다 — 미식별 813 · 포탈 문서 186 · CFS 주문(BK_NO) 9. "첨부가 아직 하나도 없는 남의 번호에 첫 파일을 심는 것" 이고 열람 유출이 아니라 무결성 문제다. ★CFS 는 두 갈래 — 송장(GRP_INV_NO, COST_TP='CFS')은 ③이 잡지만 주문(TB_CFS_ORD.BK_NO)은 TB_TES_GRP_INV 에 없어 ④로 빠진다. 9건뿐이라 막지 않기로 결정(2026-10-02). 막을 땐 소유 축이 CUST_CD 다 — 그룹인보이스의 CORP_CD 와 다르니 통일 금지. 적용 지점 4곳이 전부 닫혔고, 검증 제외 4종은 보안 문서의 "첨부 소유 검증" 절에 적었다.

    • ★배포 직후 핫픽스 3건(2026-10-02) — 게이트 로직은 맞았는데 주체(USER_ID)가 매퍼까지 가지 않아 운영에서 드러났다. ① getSessionUserId() 가 getPrincipal() 을 봐서 null → FN_CAN_ACCESS_FILE(null, …) 이 전부 'N' → 업로드 전건 거절(PR #191). ② 컨트롤러가 param.getMap("SEARCH").put("USER_ID", …) 로 주입했는데 DMap.getMap() 은 copyMap() 으로 사본을 돌려준다 — 쓴 값이 버려져 첨부 목록 0 건. 서비스에서 SEARCH 를 한 번만 꺼내 그 인스턴스를 DAO 로 넘기도록 고쳤다(b15b1d3). ③ getBase64Image 만 USER_ID 주입이 빠져 있었다 — 매뉴얼 이미지가 전부 /FORM/ 이라 템플릿 면제로 살아 있었을 뿐, 아니었으면 null 행에서 NPE(500)였다. 주입 + null 가드 추가(f917015). ⇒ 교훈: 거절을 'N'/빈 결과로 설계하면 전달이 끊겨도 조용히 전부 차단된다. 세션 값을 쓰는 게 게이트면 SQL 단위 검증으로 끝내지 말고 로그인 계정으로 그 엔드포인트를 실제 호출할 것.
