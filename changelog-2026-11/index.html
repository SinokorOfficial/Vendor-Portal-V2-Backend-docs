    2026-11 변경 이력¶

    레플리카 바깥 경로를 10초마다 재는 프로브를 넣었다 (PR #313, Infra #75)¶

    레플리카 하나에서만 DNS, Redis, Oracle, NAS 가 함께 막히는 사건이 2026-10-04 부터 이어지고 있다. 지금까지 남는 기록은 전부 "실패했다" 뿐이라 원인을 좁히지 못했다. ACA 는 Consumption 공유 노드라 노드 지표도 kubelet 로그도 우리에게 열려 있지 않고(레플리카 정보에 노드 필드 자체가 없다), 사건은 각 30분 남짓이라 붙잡고 볼 수도 없다.

    호스트는 못 보더라도 우리 쪽 증거는 날카롭게 만들 수 있다. NetworkProbe 가 전용 데몬 스레드에서 10초마다 네 가지를 같이 잰다.

    재는 것 뜻
    lag 예약 시각과 실제 실행 시각의 차이. 이 스레드가 밀렸다는 뜻
    loop 자기 헬스 엔드포인트를 루프백으로 부른 시간. 네트워크를 안 탄다
    dns 리졸버에 A 레코드를 직접 묻는 시간
    tcp 방금 받은 IP 로 붙는 시간

    네 개를 같이 재는 것은 대조군을 두려는 것이다. 숫자 하나로는 구분이 안 된다.

    • lag 만 크다 → JVM 또는 CPU 정지(GC stop-the-world, 스로틀링)
    • loop 만 크다 → 톰캣 요청 스레드 고갈. ACA 프로브가 1초에 실패하는 것과 같은 원인
    • dns·tcp 만 크다 → 호스트 네트워크

    dns 는 InetAddress.getByName 이 아니라 JNDI 로 리졸버를 직접 친다. 전자는 JVM 이 30초 캐시하므로(이 이미지는 networkaddress.cache.ttl 미설정) 10초 간격으로 부르면 대부분 캐시를 읽어 0ms 가 찍힌다. tcp 는 호스트명이 아니라 방금 DNS 로 얻은 IP 로 붙는다. 호스트명으로 붙으면 DNS 가 죽었을 때 TCP 결과까지 같이 가려진다.

    대상은 Redis 하나다. 같은 VNet 의 Private Endpoint 라 VPN 도 인터넷도 지나지 않으면서 사건 때 함께 끊겼다 — 호스트 구간만 공유하는 가장 깨끗한 표본이다. Oracle 리스너와 NAS FTP 는 일부러 찌르지 않는다. 10초마다 붙었다 끊으면 상대 쪽 로그에 하루 8천 줄씩 쌓이는데 그 로그는 DBA 와 인프라팀이 읽는 것이다. DB 쪽은 Hikari 가 30초마다 남기는 Pool stats 로 이미 보인다.

    시끄럽지 않게 만드는 장치를 넷 뒀다.

    • 느린 회차만 WARN 으로 남긴다(기준 300ms). 평상시에는 5분마다 요약 INFO 한 줄뿐이다.
    • 시작할 때 리졸버 조회를 한 번 해 보고, 못 답하면 그 레플리카가 사는 동안 dns 칸을 비운다. 로컬에서 Redis 호스트가 /etc/hosts 에만 있는 이름이면 리졸버는 모르는 이름이라 매 회차가 실패로 찍히기 때문이다. 시작할 때만 보므로 "그 뒤에 DNS 가 망가지는" 사건은 그대로 잡힌다.
    • 시작할 때 루프백도 한 번 미리 친다. HttpClient 첫 호출의 준비 비용이 기준 300ms 에 바짝 붙어서, 그대로 두면 레플리카가 뜰 때마다 애먼 느림 한 줄이 찍힌다. 덤으로 헬스 경로가 열려 있는지 기동 로그(루프백 확인 — status=200)에서 바로 보인다. 경로가 틀려 404 가 나면 10초마다 매핑 없는 요청이 들어가 에러로그가 쌓이는데, 그걸 기동 때 알아차릴 수 있다.
    • 한 회차는 Throwable 까지 잡는다. ScheduledExecutorService 는 작업이 예외를 던지면 조용히 재예약을 멈춘다 — 한 번 터지고 영영 안 도는 프로브가 가장 나쁘다.

    로그 문구에도 제약이 있다. ERROR 로는 찍지 않는다(배포 게이트가 기동 중 ERROR 줄을 센다). unresolved, Failed to validate connection 같은 문구도 쓰지 않는다 — 재발 확인 KQL 이 그 문자열로 찾으므로 섞이면 집계가 오염된다. 줄마다 밀리초 타임스탬프를 직접 박는데, 콘솔 로그 패턴이 초 단위이고 아픈 레플리카는 로그 전송이 950초까지 늦은 적이 있기 때문이다.

    vp.netprobe.enabled 로 끌 수 있고 기본은 켜짐이다. 전용 스레드를 쓰는 이유는 스프링의 @Scheduled 스케줄러가 기본 한 스레드라, 여기서 DNS 가 몇 초 매달리면 같은 스레드를 쓰는 허용 목록 갱신까지 밀리기 때문이다.

    이것은 측정 장치이지 수정이 아니다. 어느 설명이 맞는지는 운영에서 사건이 한 번 더 날 때 숫자로 갈린다.

    로그가 안 들어오는 것으로 배포를 실패시키지 않는다 (PR #315, Infra #29)¶

    배포 게이트의 마지막 단계는 Log Analytics 에서 기동 로그를 읽어 ERROR 줄을 센다. 그 로그가 안 들어오면 배포를 실패 처리하고 있었다. PR #313 배포에서 실제로 그 일이 일어났다.

    success  Wait for new revision healthy
success  Smoke test via public domain
failure  Check startup logs for errors

    리비전은 Healthy, 레플리카 2개 RunningAtMaxScale, 트래픽 100%, 스모크 통과였다. 앱은 멀쩡히 서비스 중이었고 az containerapp logs show 로 컨테이너에 붙어 보면 로그를 제대로 찍고 있었다. 그런데 ContainerAppConsoleLogs_CL 에는 그 리비전 로그가 40분 넘게 0줄이었다. 같은 시각 ContainerAppSystemLogs_CL 은 그 리비전 이벤트를 정상으로 받고 있었으니, 앱도 설정도 아니고 수집 파이프라인 한쪽이 정체된 것이다.

    이걸 실패로 두면 두 가지가 나쁘다.

    • 안전이 늘지 않는다. 바로 앞 두 단계가 이미 리비전이 Healthy 하고 요청에 답한다는 것을 확인했다. 로그를 못 본다고 해서 나쁜 리비전이 나간 것은 아니다.
    • 빨간 빌드에 둔감해진다. 앱이 멀쩡한데 배포가 빨개지는 일이 반복되면 진짜 실패도 그냥 넘기게 된다. 게이트를 넣은 이유가 없어진다.

    그래서 못 봤을 때는 경고만 남기고 통과시킨다. 기다리는 시간은 5분에서 8분으로 늘렸다 — 평소 적재는 그 안에 끝나므로 대부분은 예전처럼 제대로 검사한다. 진짜 ERROR 줄을 찾았을 때 실패시키는 동작은 그대로다.

    게이트가 보장하는 범위가 그만큼 줄었다. "기동 중 ERROR 가 없었다" 가 아니라 "봤다면 없었다" 가 됐다. 로그를 못 본 배포는 워크플로 요약에 경고로 남는다.

    배포 뒤 기동 확인, 스모크, 기동 로그 확인 (PR #311, Infra #29)¶

    종전 게이트는 새 리비전의 provisioningState 가 Provisioned 인지까지만 봤다. 그건 "리비전이 만들어졌다" 는 뜻이라, 컨테이너가 떠서 실제로 동작하는지는 보지 않았다. 세 단계를 더 붙였다.

    기동 확인 — healthState 가 Healthy 가 될 때까지 기다린다. 레디니스 프로브(/application/health/readiness)를 통과했다는 뜻이다. 판정을 healthState 로 하는 이유는 정상일 때 runningState 가 Running 이 아니라 RunningAtMaxScale 로 나오기 때문이다. runningState 로 즉시 실패 판정은 하지 않는다 — Degraded 는 "레플리카 중 하나가 실패" 라 두 대가 차례로 뜨는 롤아웃 중 잠깐 나올 수 있다. 못 뜨는 배포는 타임아웃(600초)이 잡는다. 스타트업 프로브가 최대 310초를 쓰므로 그보다 커야 한다.

    스모크 — 백엔드는 ingress 가 internal 이라 러너에서 직접 칠 수 없다. 운영 공개 도메인으로 POST /api/session 에 JSON 헤더를 붙여 보내 401 이 오면 통과다. nginx 에서 백엔드까지 이어지고 스프링 보안이 응답한다는 뜻이다. 헤더가 없으면 302(/login)가 온다. 이 401 은 에러로그에 남지 않는다 — 매핑된 엔드포인트이고 InsufficientAuthenticationException 은 예외 리졸버가 insertErrorLog 앞에서 끊는다.

    기동 로그 확인 — Log Analytics 에서 새 리비전의 레플리카들이 Started VpApplication 을 남겼는지, 그 줄 이전 ERROR 가 0건인지 본다. 레디니스를 통과해도 기동 중 ERROR 가 있었으면 반쪽으로 뜬 것이다. 기동 뒤 ERROR 는 개수만 찍고 실패로 치지 않는다 — 운영 ERROR 줄은 대부분 요청 때문이라 배포 직후 창에서 세면 배포와 무관하게 빨개진다. 레플리카 키는 ContainerGroupName_s 다(ReplicaName_s 컬럼은 없다). 레플리카가 교체되면 그룹이 늘 수 있어 "레플리카 수 이상" 으로 판정한다. 권한은 CI 아이덴티티가 가진 리소스 그룹 Contributor 로 충분하다.

    같은 커밋을 다시 돌리면 이미지 문자열이 같아 새 리비전이 생기지 않는다. 그 경우 옛 리비전을 보고 판정하게 되므로 게이트를 통째로 건너뛴다.

    자동 롤백은 넣지 않았다. 단일 리비전 모드와 레디니스 덕에 기동에 실패하면 옛 리비전이 그대로 서비스하고, 일시적 끊김으로 스모크가 한 번 실패했다고 멀쩡한 배포를 되돌리면 더 나쁘다. 프로시저를 운영 DB 에 손으로 반영하는 배포라면 이미지만 되돌릴 때 화면과 DB 버전이 어긋난다. 게이트 실패는 잡 빨간불로 알리고 되돌리기는 사람이 한다.

    JWT 토큰을 쿼리 파라미터로 받지 않는다 (PR #290)¶

    JwtAuthenticationFilter 는 Authorization 헤더가 없으면 ?token= 쿼리 파라미터를 토큰으로 읽었다. 경로 제한이 없어 모든 API 를 쿼리 토큰으로 부를 수 있었다.

    이 통로는 레거시 SSO(/api/link) 전용이었다. 그 입구는 PR #288 로 닫혔고, 프론트의 호출도 함께 사라졌다. 남은 것은 쓰는 데 없이 열려 있는 입구뿐이었다.

    쿼리로 실어 보낸 토큰은 nginx 액세스 로그와 AppInsights 요청 URL 에 평문으로 남는다. 발급대장에 해시만 두고 메일 로그에서도 토큰을 가리는 원칙(PR #286)이 이 한 줄로 새고 있었다.

    바뀐 것¶

    • 토큰은 Authorization 헤더로만 받는다. ?token= 은 토큰이 없는 요청과 같아져, 익명이면 /login 302 이고 세션이 있으면 그 세션으로 판정된다.
    • 파트너 API 안내 메일은 전부터 Authorization: Bearer 로 적어 왔다 — 안내 문구는 그대로다.

    운영 90일 중 ?token= 호출은 스모크 테스트 2건(둘 다 401)과 2026-09-08 이후 끊긴 /api/link 진입뿐이다. 지금 코드에서 쿼리 토큰을 쓰는 곳은 없다.

    • RequestResponseBodyCachingFilter 는 debug 일 때 요청, 응답을 문자열로 만들어 log.debug 로 넘겼다. debug 는 !isProd() 였는데, isProd() 가 활성 프로필 문자열을 "prod" 와 통째로 비교해서 운영(prod,azure)에서 false 가 됐다. 그래서 운영에서도 매 요청 헤더와 본문(로그인 비밀번호 포함)을 문자열로 만들고, 로그 레벨이 INFO 라 그대로 버렸다. 큰 JSON 업로드는 본문을 문자열로 몇 번 더 복사했다.
    • 출력은 log.isDebugEnabled() 일 때만 한다. debug 플래그와 isProd() 는 지웠다(쓰는 곳이 이 필터뿐이었다).
    • 본문을 맨 앞에서 끝까지 읽는 것은 로그 레벨과 상관없이 유지한다. 에러로그 PAYLOAD 가 이 캐시를 읽기 때문이다. 그냥 끄면 컨트롤러가 본문을 읽기 전에 난 예외(보안 필터 단계 등)의 PAYLOAD 가 빈다. 읽는 순서(파라미터 먼저, 본문 나중)도 그대로다. 멀티파트는 파라미터 조회에서 Tomcat 이 파트를 먼저 파싱해야 한다.
    • 테스트 RequestResponseBodyCachingFilterTest: 체인이 본문을 읽지 않아도 캐시가 차 있고 뒤에서 다시 읽을 수 있다(INFO, DEBUG 모두), 파라미터를 본문보다 먼저 읽는다. 세 건 모두 고치기 전 코드(플래그 기본값)에서 실패한다.

    actuator 는 health 만 연다 (PR #296)¶

    Infra #91 판단 항목 "actuator".

    • management.endpoints.web.exposure.include 가 "*" 라서 /application/* 아래 actuator 엔드포인트가 전부 열려 있었다. health 말고는 로그인만 하면(협력사 포함) 부를 수 있었다.
    • heapdump 는 서버 메모리를 통째로 준다. DB 비밀번호, JWT 서명키, 로그인 요청의 비밀번호가 그대로 들어 있다.
    • loggers 는 로그 레벨을 바꾼다. 본문 캐싱 필터를 DEBUG 로 올리면 요청 본문이 로그에 찍힌다.
    • 외부에서 닿는 길은 없었다. 프론트 nginx 는 /api/ 만 백엔드로 넘기고, 백엔드 ingress 는 internal 이다. 심층 방어로 닫는다.
    • 이제 health 만 연다. 쓰는 곳은 ACA 프로브(/application/health/readiness, /application/health/liveness)뿐이다. 운영 이미지는 이 템플릿으로 기본 설정을 만들므로(Dockerfile de-bake) 이 한 줄이 그대로 반영된다.
    • docs 의 application.yaml.example 줄 번호 참조 중 이미 어긋나 있던 4곳(EIR 시크릿, Azure Monitor, PageHelper)을 실제 위치로 맞췄다.

    메일 로그에 임시 비밀번호와 API 토큰을 가려 남긴다 (PR #286)¶

    메일 로그(TB_CMS_EMAIL.CONTENT)에 보낸 본문이 그대로 쌓여, 비밀번호 찾기 메일의 임시 비밀번호와 API 토큰 발급 메일의 토큰이 평문으로 남았다(Infra #91 9). 계정 비밀번호(TB_CMS_USER.USER_PWD)는 BCrypt, 발급 대장(TB_CMS_JWT)은 sha256 이라 메일 로그가 유일한 평문 사본이었다.

    • VmsSendMicrosoftGraphMailService.sendMail: 호출부가 LOG_TEXT 를 넘기면 로그에는 본문(TEXT) 대신 그것을 남긴다. 받는 사람에게 가는 메일은 그대로다.
    • 비밀번호 찾기(AdminService.findPassword): 템플릿을 ******** 로 한 번 더 렌더링해 LOG_TEXT 로 넘긴다. 보낸 본문에서 값을 찾아 지우지 않는 이유는 템플릿이 특수문자를 이스케이프해(& → &amp;) 본문 표기가 원래 값과 다를 수 있어서다.
    • API 토큰 발급 메일(CmsJwtMgtService.sendToken): 토큰 자리를 ******** 로 바꾼 본문을 LOG_TEXT 로 넘긴다.
    • 메일 로그 화면(CmsEmailLog)에서 이 두 메일은 값이 가려져 보인다.
    • 이미 쌓인 행은 이 변경으로 바뀌지 않는다. .3 의 기존 행은 사용자가 2026-11-03 SQL 로 가렸다. 그 뒤 이 변경이 배포되기 전까지 쌓인 행은 배포 뒤 같은 SQL 로 한 번 더 가린다(Infra #91).

    견적 첨부 API 를 발급된 토큰으로만 부르게 한다 (PR #287)¶

    TB_CMS_API.TOKEN_CHK = 'Y' 는 "인증이 필요하다"는 뜻이었다. 세션 로그인도 인증이라, 포탈에 로그인한 브라우저로 주소를 열면 토큰 없이도 /api/partner/getEstAttachFile 이 열렸다.

    2026-11-03 운영에서 실제로 그렇게 불렸다. 호출 로그에 남은 사용자는 토큰 발급 대상이 아니라 그 브라우저의 세션 사용자였고, 그 API 는 토큰을 한 번도 발급한 적이 없었다.

    바뀐 것¶

    • TOKEN_CHK='Y' 의 뜻이 "발급된 API 토큰으로만 부를 수 있다" 로 좁아졌다. 세션 로그인은 403. SSO 핸드오프 토큰도 함께 걸린다 — 발급대장과 경로를 대조하는 것은 API 토큰뿐이다.
    • getEstAttachFile 에 USER_ID 파라미터가 생겼고 토큰의 발급 대상과 대조한다. 다르면 거절. 값 자체는 비밀이 아니라 인증 수단이 하나 더 생기는 것은 아니고, 남의 토큰을 돌려쓰는 것을 호출 시점에 잡는 장치다.
    • 호출 로그를 검증보다 먼저 남긴다. 잘못 부른 시도도 흔적이 남아야 "안 된다"는 문의를 로그로 푼다. 로그의 사용자 컬럼은 토큰에서 꺼낸 값(위조 불가)이고, 호출자가 보낸 USER_ID 는 비고에 적힌다.

    안내 메일¶

    호출 예시의 자리표시자가 <estimate no.> 여서 메일 클라이언트가 공백에서 주소를 잘랐다. 받는 사람이 링크를 누르면 ESTIMATE_NO=%3cestimate 까지만 전달돼 세 번 모두 빈손으로 끝났다.

    <ESTIMATE_NO> 로 바꾸고, 예시에 USER_ID 를 발급 대상으로 채워 넣었다. 응답 코드 설명에 403 을 더했다. 예시 주소에 공백이 들어가면 테스트가 깨진다.

    레거시 SSO 입구를 닫는다 (PR #288)¶

    레거시 포탈이 JWT 를 붙여 보내면 비밀번호 없이 로그인시키던 SSO 입구를 지웠다(Infra #91 10). 레거시는 2026-10-23 종료됐고, 운영 진입은 9/8 컷오버 뒤로 0건이었다.

    • /api/link 삭제. 받은 url 로 검증 없이 리다이렉트해서, 우리 도메인 링크로 다른 사이트에 보낼 수 있었다(오픈 리다이렉트).
    • JwtSwitchingLoginUserAuthenticationProvider 삭제. JWT 체인은 JwtVerifyAuthenticationProvider 하나만 남는다.
    • JwtVerifyAuthenticationProvider: jti SSO 토큰이 발급대장(TB_CMS_JWT) 검사를 건너뛰던 예외를 지웠다. 이 예외를 남기면 서명 키를 가진 누구나 대장에 없는 토큰으로 모든 API 를 열 수 있다. 이제 모든 토큰이 대장을 거친다.
    • JwtAuthenticationFilter: SSO 로그인만 쓰던 세션 저장과 로그인 로그 적재를 지웠다. API 토큰 인증은 종전처럼 세션을 만들지 않는다.
    • 프론트의 ssoToken 처리는 프론트 저장소에서 따로 지운다.

    첨부 다운로드가 남의 선사 파일까지 내려주던 것을 막는다 (PR #285)¶

    관리번호(MNGT_NO)는 선사별로 따로 채번돼 선사 간에 겹친다. 운영에 39,053건, .100 에 20,921건이 겹쳐 있었다. 그런데 첨부 조회가 선사를 보지 않고 관리번호만 봤다.

    FROM TB_CMS_ATFILE WHERE MNGT_NO = #{MNGT_NO}     -- 선사 조건이 없었다

    그래서 같은 번호를 쓰는 다른 선사의 첨부가 한 zip 에 함께 내려갔다. 007062508000096 을 SNKO 로 부르면 SNKO 13건과 HALK 10건, 모두 23건이 나왔다. 컨테이너 번호가 서로 다른, 완전히 다른 견적의 사진이다.

    조회에 선사 조건을 더했다. 적용되는 곳은 TB_CMS_ATFILE 을 보는 fileDownloadList 하나이고, 이를 거쳐 /api/partner/download, /downloadAll, /getEstAttachFile, 이미지 뷰어가 모두 같이 고쳐진다. 포탈 폴백(fileDownload{SNKO,HALK,HSLI}List)은 이미 선사별 스키마로 갈려 있어 손대지 않았다.

    세 가지를 함께 두었다.

    • COMP_CD 가 빈 행은 남긴다. 2024-11 이관분 388건이 비어 있어, 걸러내면 그 견적의 첨부가 통째로 사라진다. 값이 채워진 행에 대해서만 선사를 가린다.
    • 호출부가 COMP_CD 를 주지 않으면 조건을 걸지 않는다. 이미지 뷰어는 외부 딥링크로 열릴 때 선사가 비어 올 수 있어 종전 동작을 지켜야 한다.
    • UPPER 로 비교한다. 데이터에 HALk 같은 대소문자 오타가 있다.

    토큰 발급 메일로 실제 호출이 되게 고친다 (PR #283)¶

    발급 안내 메일의 "사용 방법" 블록만 보고는 호출을 만들 수 없었다. 세 가지가 겹쳐 있었다.

    주소에 도메인이 없었다. TB_CMS_API.API_URL 은 경로만 들고 있다(인증 경로 판정에 쓰이므로 도메인을 넣을 수 없다). 그래서 메일에도 /api/partner/getEstAttachFile 만 찍혀 받는 쪽이 어디로 보낼지 알 수 없었다. 설정 app.public-base-url 을 새로 두고 예시 앞에 붙인다. 기본값은 운영 도메인이다 — 이미지 빌드가 설정 템플릿으로 덮어쓰므로 여기 적은 값이 운영 기본값이 되고, 로컬에서 발급해도 받는 사람은 운영으로 호출한다. 비우면 종전처럼 경로만 적힌다.

    파라미터가 ... 로 생략돼 있었다. getEstAttachFile 은 선사와 견적번호가 둘 다 필수다. 예시에 그대로 적는다.

    견적번호 파라미터 이름이 MNGT_NO 였다. 외부 호출자가 뜻을 알 수 없어 ESTIMATE_NO 로 바꿨다. 저장소 컬럼명은 MNGT_NO 그대로다. 토큰을 아직 아무에게도 주지 않았고 화면에서 부르는 곳도 없어 깨질 호출자가 없음을 확인했다.

    GET https://partner.sinokor.co.kr/api/partner/getEstAttachFile?COMP_CD=SNKO&ESTIMATE_NO=<견적번호>
Authorization: Bearer <토큰>

    값이 빠졌을 때 500 이 떨어지던 것도 고쳤다. @RequestParam 필수 누락은 전역 처리에서 500 이 돼 호출자가 자기 실수를 서버 장애로 읽었다. 이제 첨부가 없을 때와 같은 형태로 사유를 돌려준다 ({"MSG": "COMP_CD and ESTIMATE_NO are required."}).

    응답이 늘 zip 은 아니라는 점도 메일에 적었다. 첨부가 없거나 값이 빠지면 JSON 이 오므로 받는 쪽이 Content-Type 으로 갈라야 한다.

    수리장 관리자 CRS00 — 사용자 관리만 연다 (PR #284)¶

    수리장 관리자 역할 CRS00 을 사용자 관리(CmsUserMgt) API 허용 역할에 더했다. 메뉴가 사용자 관리만 열려 있어서 관리 화면 역할 상수를 둘로 나눴다.

    • ROLES_USER_MGT = ADMIN, CFS00, CRS00, EIR00, TES00: cmsUserMgt/*, 그리고 사용자 관리가 부르는 mdmCorpMgt/selectCorpRel
    • ROLES_CORP_MGT = ADMIN, CFS00, EIR00, TES00: 회사 관리(mdmCorpMgt 의 selectTree select save delete). CRS00 은 거절

    역할 부여 범위(CRS01~CRS03)와 법인 범위(SYSTEM_DIV 가 CRS 인 회사)는 기존 모듈 관리자 규칙 그대로 따라온다. 역할 행(TB_CMS_ROLE, TB_CMS_ROLE_MENU, TB_CMS_ROLE_BUTTON)은 사용자가 .3, .100 에 등록한다.
